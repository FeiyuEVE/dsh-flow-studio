## 1. 设计结论

1. **一块地板、四根柱子**：全部数值建立在 4px 地板网格上；吸附 4px、视觉点阵 20px、卡片 208×96、列距 260——因为打回航道（03）需要比「好看」更硬的落位精度，4px 吸附让航道间距 28px 这种非 20 倍数的值也能精确对齐。
2. **字号 12/13/14/16/20 五档封顶，正文 12px 是地板不是建议**：Chrome 中文环境会把 <12px 强制放大到 12px 渲染，写小字不是「小」而是「布局计算失真 + 跨浏览器不一致」；中文笔画密度也撑不住 12px 以下。唯一例外是非正文徽标 11px（`--dsw-font-xxxs-11`，见 §2.1）。
3. **颜色零自设：每个语义都指到宿主 `--dsw-alias-*`，需要中间色时只允许两种混法**——与 `label-primary` 混（主题自适应加深/提亮）或与 `transparent` 混（tint/光晕）；禁止与 white/black 混（暗色即失效）。**没有例外。** 03 §4.4 的成员身份六色板（自设 12 个十六进制）违反本条，已作废——改为「形状 + 首字 + 同色系深浅梯度」，见 §4.4 更正。
4. **亮色主题的成功绿/警示琥珀直接上白底只有 2.2–2.3:1，不达标**：所有细描边与小号状态文字统一走配方 R1 `color-mix(in srgb, 状态色 70%, var(--dsw-alias-label-primary))`，亮色自动加深到 3.9–4.1:1、暗色自动提亮到 9.9–10.5:1，**单一表达式双主题合法**，不需要主题分支（§4.3）。
5. **「品牌蓝」是 `state-business-primary`，不是 `brand-primary`**：宿主 brand-primary 实测为中性黑/白（它服务于主按钮），**运行/焦点/活动线**用 business 蓝，**选中**用中性 `brand-primary`（§0.3 #4）——两者必须可区分，这是对 03/04 的事实性更正。
6. **节点卡片三变体同宽不同高**（紧凑 208×48 / 标准 208×96 / 展开 208×144），宽度恒定保证列距与航道几何不变；缩放 LOD 只降内容不改位置，与 03「运行时结构冻结」兼容（§3.1）。**世界边界与全览只按两档高计算：单 agent 96、主管+子 agent 116（`DESIGN §6`）；208×144 展开变体是 v0.3 预留形态，不计入包围盒。**
7. **密度诚实分层**：1440×900 三栏常驻时画布只有 880×824，8 列完整主干（世界宽 2028）fit 后 ≈38.7%——这是**地图模式**（精简档，形状/连线形态/位置承载，文字隐藏）；「全览」临时收起两栏把画布拉到 1396px 后 fit ≈64.1%（完整档临界，标题实渲染 ≈9px）；要逐字读标题需再放大到 ≥70%，此时不再承诺全纳。100% 时一屏理想工作集 8–12 个节点，正好覆盖典型流程（§2.4）。
8. **层级预算写成硬约束**：强强调（光晕/脉冲/≥2.5px 描边）同屏 ≤2 处、画布字号 ≤4 档、投影 0 种、饱和色实底只出现在 ≤Ø18 的角标内——防止运行态把结构淹没（§4.7）。

## 2. 布局与尺寸

### 2.1 排版刻度（A）

字体族：全局 `var(--dsw-font-family)`（宿主解析为系统栈：-apple-system / Segoe UI / PingFang SC / Microsoft YaHei…）；**数字与代码类内容**用 `var(--dsw-font-markdown-code-font-family)`（宿主解析为 SF Mono / JetBrains Mono / Consolas…），并一律加 `font-variant-numeric: tabular-nums`（计时器/token 数跳动时只变数值不挪位，此规则与 04 §2.3 一致）。

| 档位 | 字号/行高 | 字重 | 字距 | 用途 | 宿主 token 对应 |
|---|---|---|---|---|---|
| **T12** 微文字 | 12/16 | 400 | 0 | 徽标 chip 文字、轮次刻度数、状态行文字、检查器 label、提示文本、状态栏 | 对应宿主 `--dsw-font-xxs-12`（12px/18px）。**正文地板是 12px**（产品自设，见下）；**非正文徽标**（↺n、执行方式徽标、轮次「5+」）允许 11px = `--dsw-font-xxxs-11`（11px/14px），与 03 §2.4 逐个标注的口径一致——11px 不进正文，也不是第三档正文 |
| **T13** 正文 | 13/20 | 400 | 0 | 卡片角色摘要行、菜单项、检查器表单正文、左栏列表主文案 | `--dsw-font-xs-13`（13px/20px，完全一致） |
| **T14t** 标题 | 14/22 | 500 | 0 | **节点卡片标题**、检查器节标题、对话框标题、输入框文字 | 无整档 token，按值自设（行高 22 为卡片密度定制） |
| **T14b** 长文 | 14/24 | 400 | 0 | 检查器内的多行说明/备注 | `--dsw-font-markdown-base`（随用户 `--dsh-content-font-size` 设置缩放）。**仅检查器长文允许跟随用户字号**；画布内文字一律固定 px，否则用户调大内容字号会撑破卡片 |
| **T16** 面板题 | 16/24 | 500 | 0 | 面板/空态次级标题、大号按钮 | `--dsw-font-base-strong-16`（完全一致） |
| **T20** 页面题 | 20/28 | 500 | −0.01em | 空态主文案、运行摘要条主数值（mono）、对话框一级标题 | `--dsw-font-l-20`（完全一致；摘要条主数值用 mono 变体） |
| **M12** 数据 | 12/16 mono | 400 | 0 | 卡片指标行（token/耗时）、模型名、坐标读数 | `--dsw-font-markdown-code-font-family` + tabular-nums |
| **M20** 大数据 | 20/24 mono | 500 | 0 | 摘要条/指标块主数值 | 同上 |

**字重只用 400 / 500 两档**（宿主另有 600/700 档，如 `markdown-h1`/`xl-24`，本产品主动不用）：
- Windows 的微软雅黑没有 500 字重，浏览器会回落到 400——所以**标题与正文的区分不能只靠字重**，必须同时有「字号档差（14 vs 13）+ 颜色档差（label-primary vs label-tertiary）」双通道；在 macOS（PingFang SC Medium）上 500 正常生效，属于渐进增强。
- 禁用 600+：雅黑 600 触发合成伪粗（synthetic bold），中文笔画糊成一团。

**为什么 12px 是地板（任务书问题，三条硬理由）**：
1. **浏览器下限**：Chrome 中文语言环境默认「最小字号 = 12px」。写 `font-size: 10px/11px` 在 Chrome 里实际渲染为 12px——按 11px 算的 chip 宽度/padding 全部失真（文字溢出或 chip 变宽挤压布局）；Firefox/Safari 默认不放大，同一界面三种浏览器两个样。03 的 10px 刻度数、11px chip、9px 成员首字都踩了这条（裁决 #3），本文统一上调：chip 12px/h18、成员点内首字 12px/点径 Ø16。
2. **中文字形密度**：「需、审、回、缺陷」这类 10+ 笔画字在 12px 以下笔画间隙 <1 物理px，粘连成墨块。拉丁字母 10px 可读不代表中文可读——本产品是纯中文界面。
3. **DPI 缩放**：Windows 125%/150% 系统缩放叠加浏览器缩放后，10px → 12.5/15 物理px，非整数像素对齐发虚；12px 在 150% 下 = 18 物理px，仍清晰。

**例外（不算违反地板）**：SVG 图标路径内的形状不受字号限制（Ø18 角标里的 10px 图标是矢量路径，不是字体）；画布缩放 <45% 时文字整体**隐藏**而不是缩小到不可读（精简档，LOD 规则见 §2.4）——缩小是用户主动的临时行为，隐藏是系统的兜底；**非正文徽标**（↺n、执行方式徽标、轮次「5+」）允许 11px `--dsw-font-xxxs-11`（11/14），它们只放数字与固定词、不承载正文——这是唯一放宽，正文任何位置仍是 12px 地板。

**缩放与可读性的换算**（画布文字随 zoom 等比缩放；阈值与 §2.4 LOD 同一套）：

| zoom | T14t 标题实渲染 | T12 实渲染 | 判定 |
|---|---|---|---|
| 100% | 14px | 12px | 全信息 |
| 75% | 10.5px | 9px | 短标题（4–6 字阶段名）可读，正文费力 |
| 60% | 8.4px | 7.2px | **完整档下限**：内容全渲染，标题只保证字形轮廓可辨，细节靠角标与文字行 |
| 45% | 6.3px | 5.4px | **紧凑档下限**：标题+状态角标+↺n，完整语义靠 tooltip / aria-label |
| <45% | — | — | 精简档：文字退化为纹理，只读结构、连通性与状态形状 |

### 2.2 间距刻度与网格（B-1）

**间距刻度（px，4 的倍数，档位外取值视为 bug）**：

| 档 | 4 | 8 | 12 | 16 | 20 | 24 | 32 | 40 | 48 | 52 | 64 | 96 |

### 2.4 密度与缩放（F）

**画布区实测**（1440×900 面板，01 断点：≥1360 三栏常驻）：

```
面板 1440 × 900
├─ 顶栏 48 + 状态栏 28（01）        → 净高 824
├─ 左栏 240 + 检查器 320            → 画布 880 × 824（检查器常驻；空选中仍是 320，宽度不随选中变化）
└─ 全览（显式动作：左栏 44 + 检查器临时收） → 画布 1396 × 824
```

**世界边界（单一来源，不再写魔数）**：

- 世界包围盒 = 所有节点矩形的并集，再向外加 **48 屏幕 px** 边距（边距语义是屏幕像素，不随缩放变化）。
- 节点矩形：宽 208；单 agent 高 96，主管+子 agent 高 116（`DESIGN §6`）；列距 260 = 208 + 52 间隙。
- 8 列主干世界宽 = `7×260 + 208 = 2028`（**旧文的 1852 / 1940 作废**：前者把开始/完成按 120 宽特例算，后者是 `7×260+120` 的另一套端点坐标）。
- 世界高 = 主干高（96 或 116）+ 有打回时 `24 + 28×(航道数−1) + 32`；无打回时航道区不占位（03 §5）。六航道 = `96 + 24 + 28×5 + 32 = 292`。
- `fit = min((视口宽 − 96) / boundsW, (视口高 − 96) / boundsH)`，结果 clamp 到 **[15%, 100%]**（代码同值：`geometry.js` 的 `FIT_MIN = 0.15`、`FIT_MAX = 1`；不是 200%——200% 只是手动缩放上限，见 §2.4 缩放规格）；96 = 左右各 48 屏幕 px 边距之和。

**实测 fit**（1440×900 面板，8 列主干）：

| 场景 | 视口 | 计算 | fit | 落档 |
|---|---|---|---|---|
| 三栏常驻 | 880×824 | `(880−96)/2028` | **38.7%** | 精简档（地图模式） |
| 全览：收左栏至 44 + 收检查器 | 1396×824 | `(1396−96)/2028` | **64.1%** | 完整档（标题 ≈9px，可读临界） |
| 30 节点串行链 | 1396×824 | `(1396−96)/7748` | **16.8%** | 精简档（全纳但只读结构） |

**长链不承诺全纳**：缩放地板 **0.15**（原 25% 作废）。`fit < 0.15` 时固定 15%，并在画布右下提示 **「还有 N 列在视野外」**；N 按列去重、逐列判定（该列矩形左缘 <0 或右缘 > 视口宽即计入），与 `geometry.js` 的 `hiddenColumnsOf` 同口径；导航 = `Shift`+滚轮横移 / 中键或空格拖平移 / 「下一段」按「一屏宽 = 视口宽/0.15」跳列。30 节点链在 1396px 下是 **16.8%**（仍在地板之上，能全纳但落在精简档）——只能看结构与打回方向，标签/文字不可读，这是如实写明的降级表现。

**LOD（细节层次）规则**——只降内容渲染，不动任何坐标（与 03「运行时结构冻结」兼容，设计态同样适用）：

| 档 | zoom 区间 | 卡片渲染 |
|---|---|---|
| **完整档**（原 LOD-1） | ≥60% | 标准卡全信息（标题/摘要/徽标行；团队卡 116 含成员行） |
| **紧凑档**（原 LOD-2） | 45% ≤ zoom < 60% | 自动切**紧凑变体** 208×48：标题 + 状态角标 + ↺n（↺n 收进标题行右端 h18 chip），隐藏摘要/徽标/指标行 |
| **精简档**（原 LOD-3） | <45% | 隐藏全部文字与 chip：208×96（团队 116）轮廓剪影 + **状态形状**（✓ / ↺ / ✕ / ⊘ / ⏸，固定右上位置，按状态换形，不靠换色）+ **打回线形态**（正交折线 + 虚线节奏 + 箭头方向）+ 每个节点可聚焦的 `aria-label` 与 tooltip（「节点名 · 状态 · 打回目标」）。**只用角标色点不算双编码** |

**LOD 验收（灰度 + 60%）**：60% 与灰度截图中，打回边必须只靠「正交折线 + 虚线段节奏 + 箭头方向」就能认出方向与归属，颜色只作加速；精简档里每个节点与每条打回边都能被键盘 `Tab` 聚焦并读出 `aria-label`。这两条是验收项，不是建议。

**多条线汇入同一点的视觉处理**：

| 场景 | 处理 |
|---|---|
| 同一节点多条打回线共用底缘锚点（如「开发」同时被测试、审查打回） | **按 6 槽分配**：外侧 8/24/40/56/72/88，内侧镜像（03 §2.1）；槽位由 03 §2.2 的排序键（目标列升序 → 源列降序 → 同列节点序 → id 字序）确定性分配；超过 6 条走降级（并入最外航道、双线 1px、丢标签、末端 `+N` 汇总），不新增第 7 槽 |
| 两条打回线航道重叠（同源同目标多轮） | 不存在——多轮打回是**同一条线上的轮次刻度**（03 §3.3），不是多条线 |
| A→B 正常线与 B↢A 打回线并存 | 几何天然分离：正常线走右侧贝塞尔（列隙带），打回线走下方航道（03），永不共线 |
| 同列多条正常线汇入同一目标（合流） | 贝塞尔控制点按源序 ±16px 垂直错开，入点前 24px 内收敛为一点——「先并行后合流」的喇叭口，避免中段重叠 |
| 打回线跨越其他连线 | 桥拱：拱宽 12、拱高 6，打回线拱起（谁后画谁拱，z 序=航道深度）；正常线之间不拱（贝塞尔自然错层） |

> **不承诺任意手排零碰撞**：槽位与航道分配是确定性算法（排序 + 6 槽 + >6 降级），保证「同一输入 → 同一输出」，并让冲突可枚举、可用桥拱标出；用户手排出同列多行、非列对齐节点时仍可能出现无法消解的交叉，此时靠桥拱与线型降级兜底，状态栏提示「N 条打回线存在交叉」。不做全图自动避让（M10）。

**命中与选中**：命中区 = 沿线 12px 宽透明 stroke；hover 判定优先级：端口 > chip > 线 > 卡片（chip 压线时点 chip 不触发线 hover）；线选中 = 2.5px business + 两端端口浮现 business 环（Ø16 color-mix 35%）+ 检查器切换到该线。

| **R2 tint** | `color-mix(in srgb, <状态色> 8%, transparent)`（卡片染色）/ 12%（大块底） | 极淡 | 极淡 | 通过/失败卡片填充（03：只允许弱染色）；装饰级，无对比度义务 |
| **R3 光晕** | `color-mix(in srgb, <状态色> 25%, transparent)` | 运行中蓝晕 | 同 | 运行中外扩 6px（03）；选中用 15%（更收敛，区分「机器在跑」与「我选中了」） |
| **R4 幽灵** | `color-mix(in srgb, var(--dsw-alias-label-tertiary) 35%, transparent)` | ≈1.3:1（有意幽灵化） | ≈3:1 | 运行时未触发的打回线（03 的「0.35 灰」）；框选虚线 45% 变体 |
| **R5 网格** | `color-mix(in srgb, var(--dsw-alias-label-tertiary) 20%, transparent)` | 装饰 | 装饰 | 画布点阵（=01 口径） |

**为什么图形与文字要两个配比**：70% 混色在亮色下 warn 只有 3.94:1、success 4.14:1 —— 作为**图形**（线、描边、角标底）够用（门槛 3:1），作为**12px 文字**不够（门槛 4.5:1）。因此文字一律降一档到 62%：warn 4.72、success 4.95、error 7.37，暗色下分别是 9.54 / 9.08 / 6.55，两套主题都过。**同屏不要混用两档同色**（会显得脏）：线用 R1、文字用 R2 是稳定的搭配。

配比选择依据（扫描过 45–90% 全区间）：warn/success 混 label-primary 在 **70%** 时亮色首次同时越过 3.5:1（留 0.5 余量给宿主 token 微调），暗色仍有 ~10:1；80% 时亮色 3.17/3.35 贴线，65% 以下亮色开始发闷（warn → 土黄）。70/30 是双主题同时最优的单点。

### 4.4 成员身份：不用色相，用梯度（B02 更正）

宿主没有 categorical 色板；原方案自设 12 个十六进制违反 token 硬约束，**作废**。改法：

| 通道 | 做法 |
|---|---|
| 形状 | 主管 = 16×16 圆角方块写「主」；子 agent = Ø16 圆形写名字首字 |
| 顺序 | 圆点按团队数组顺序固定排列；检查器里成员卡用同一顺序、同一首字，两边对得上 |
| 深浅 | 第 i 个成员底 = `color-mix(in srgb, var(--dsw-alias-state-business-primary) (10 + i×5)%, var(--dsw-alias-bg-layer-2))`，上限 35% |
| 前景 | 一律 `var(--dsw-alias-label-primary)`；深底（≥20%）上改 `label-primary-foreground` 并复验 ≥4.5:1 |
| 超过 5 个 | 第 6 个起折叠为「+n」文字 chip |

代价：不能靠颜色一眼认出「谁是谁」，只能靠位置与首字。**接受这个代价** —— 成员通常 2–4 个，位置记忆比色相记忆更稳，换来的是一条不破的 token 纪律。

### 4.5 暗色模式下这些混色会不会失效？怎么兜底

**逐类判定**：

| 混色类型 | 暗色行为 | 判定 |
|---|---|---|
| R1（与 `label-primary` 混） | 混色伙伴自动反相：亮主题混入近黑→加深；暗主题混入近白→**提亮**。warn 暗色从 8.49:1 提到 10.48:1，success 从 8.00 提到 9.93——方向是「过冲」而非失效（暗色本底对比富余，提亮不跌破 3:1） | **不失效**，且这正是选 label-primary 当伙伴的原因：它是宿主保证的双主题极值色 |
| R2/R3/R4/R5（与 `transparent` 混） | alpha 合成结果跟随底色：暗色底更深，同百分比的状态色在暗色下**更醒目**（8% 绿在 #232324 上仍可见，在 #fff 上是淡绿）——两主题都成立，只是暗色存在感略强，属可接受偏差 | **不失效** |
| 实底角标（R1 底 + `label-primary-foreground` 前景） | 前景 token 自动反相（白↔近黑），对 R1 底双主题 ≥4.1:1 | **不失效** |
| `color-mix(…, white/black X%)` | **会失效**：混白在亮主题等于没混、混黑在暗主题等于没混。宿主自己的 `tooltip-key-bg` 混了 white 18%，那是宿主 tooltip 恒深底的私事 | **本产品禁用**（反例 §6-5） |

**残余风险与兜底通道**（按优先级）：
1. **宿主改版风险**：R1 是相对表达式，宿主把 green-500 换成别的绿，配方自动跟随——这是不写 hex 的核心收益。但若宿主把某状态色改到与 label-primary 明度极近（混色失去落差），70/30 会失效。**验收脚本口径**：CI 里对 §4.2 每行跑双主题实算（读 computed style → WCAG 相对亮度），图形件 ≥3:1、文字 ≥4.5:1，任何一档跌破即 fail。
2. **主题分支兜底（唯一合法用途）**：`body[data-ds-dark-theme] .fs-*{…}` 覆盖块——仅当验收脚本发现某配方单主题不达标时，为该组件写暗色特例（例如把 R1 配比在暗色下调回 85/15）。宿主选择器已实测存在（§0.2），这是文档中唯一允许出现主题选择器的地方。
3. **对比度富余说明**：暗色主题全线富余（最低档 business 7.83:1），亮色是短板——所有「亮色达标」的结论都比暗色更保守，双主题验收以亮色为准。

## 6. 反例（明确不建议做的 6 件事）

1. **不要把 `brand-primary` 当品牌蓝用**（03/04 已踩，裁决 #4）。它在亮色是近黑、暗色是近白——运行中节点在亮色主题会变成「黑光晕脉冲」，观感像故障而非运行。蓝只有 `state-business-primary` 一个来源。
2. **不要写 12px 以下的正文**，哪怕「只是刻度数字」。Chrome 中文最小字号会把它放大到 12px 渲染，你的 chip 宽度/padding 计算全部失真，且三浏览器三样。需要更小的视觉密度就删信息（折叠成 +n），不是缩字。**唯一例外**是非正文徽标 11px（`--dsw-font-xxxs-11`：↺n、执行方式、轮次「5+」），它不放正文、不参与 chip 宽度计算。
3. **不要给卡片加投影（box-shadow 灰影）**。宿主亮色主题是「全白分层 + hairline 边框」语言（layer-1..3 全 #fff，靠 border-l1..l4 分层），灰投影在这套语言里是异物；且画布平移/缩放时投影每帧重算，60 个节点就是 60 块脏矩形。层级用 bg-layer 档位（暗色）+ 边框（亮色）表达，状态用 R3 彩色光晕表达。
4. **不要大面积实底状态色**（整卡红底/绿底）。运行态是叠加在设计态之上的（任务书问题 3），大块换色会淹没结构信息，8% tint + 2px 描边 + Ø18 角标足够；这也守住「暗色下大面积高饱和刺眼」的暗色规则。
5. **不要用 `color-mix(…, white/black …)` 或任何 `--dsw-static-*` 变量**。混 white/black 是极性硬编码：亮色主题混白等于没混，暗色主题混黑等于没混，双主题必坏一边；static 层是宿主 primitive，绕过语义层等于私接原色，宿主改版即碎。混色伙伴只有两个：`label-primary`（要对比度时）和 `transparent`（要 tint/光晕时）。
6. **不要用换填充层（bg-layer-1↔2）表达状态**（04 已踩，裁决 #7）。亮色下两层同为纯白、毫无变化；暗色下运行/打回切换会让卡片「跳亮」一下——状态闪烁会被误读为数据刷新。状态只动描边/tint/角标三样。
