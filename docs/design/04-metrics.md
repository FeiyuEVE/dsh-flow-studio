## 一、设计结论

1. **节点卡片运行时最多显示 2 个「自由数字」（耗时 + 一个状态数字）+ 1 个固定格式徽标（skill x/y）+ 1 条 3px 构成条（token 三段）**。再多一律进 hover 或右侧检查器——因为人在 200ms 内扫一眼能可靠读出的独立数字就是 2 个左右，第 3 个开始需要逐一看，扫描成本陡增。
2. **单节点指标走右侧检查器，整次 run 的聚合走底部抽屉**，hover 卡片只是检查器内容的「只读预览」。不用在画布上堆数字，也不为单节点开二级页。
3. **指标看板放在画布底部的可折叠抽屉（40px 收起 / 200px 展开）**，运行中和运行结束时自动展开。四个候选里只有它不遮画布、不动三栏结构、又让「图和指标同屏」。
4. **不做「设计 / 运行 / 指标」顶部 Tab**。Tab 把聚合数字和画布拆到两个视图，直接违反「运行时要在图上看到现在在哪、卡在哪」这条核心需求。
5. **所有指标统一 tabular-nums（等宽数字）+ 1Hz 更新节流 + 200ms 克制过渡**，数字变而不抖、跳而不刺眼；长跑任务的「活着感」主要靠节点描边上的流动虚线，不是靠数字狂跳。
6. **审查缺陷这类带列表的数据，在小空间用「堆叠分布条 + 总数 + P0 数」表达**，完整列表只在右侧检查器展开，绝不在抽屉里逐行铺开。
7. **一句话结论用一张确定的判定表生成**，颜色映射到语义态（优=success / 良=success / 可=warn / 需返工=warn / 失败=error），不靠模型自由发挥；**必要质量证据缺失或未检测时一律不输出绿灯**，并在结论里显式写出缺哪一项（判定表见 §3.9，非旧表）。

## 二、布局与尺寸

### 2.1 总体布局

宿主外壳占满中间主区，本面板是三栏。指标看板是「第四块」——贴在**中间画布列的底部**，不压左侧流程模板列表、也不压右侧检查器。

```
┌──────────┬────────────────────────────────┬────────────┐
│ 流程模板 │        画布（可缩放平移）          │  检查器      │
│ 列表    │                                  │ (常驻，空选中 │
│ 240px   │                                  │  显示流程设置)│
│         │                                  │  320px     │
├──────────┼────────────────────────────────┼────────────┤
│          │  ▔▔▔▔ 底部指标抽屉 ▔▔▔▔▔         │            │
│          │  40px 收起 / 200px 展开          │            │
└──────────┴────────────────────────────────┴────────────┘
```

- 检查器**常驻 320px、可拖到 240px**，空选中时显示流程级设置，**画布宽度不随选中变化**（总案 §6 C09；旧「选中节点/连线才有」作废）。
- 抽屉只属于「画布」这一栏：展开时压缩画布垂直空间，但不影响左、右两栏的滚动与内容。
- 中间主区典型高约 900px；抽屉展开 200px 后画布仍剩约 700px，6–12 节点主干完整可见，30 节点靠缩放/平移仍可操作。

### 2.2 尺寸刻度

| 项目 | 数值 |

### 2.3 字号与行高

| 用途 | 字号/行高 | 变量 |
|---|---|---|
| 摘要条主数值 | 18px / 20px | `label-primary` |
| 摘要条副标签 | 11px / 14px | `label-tertiary` |
| 节点角标数字 | 12px / 14px（胶囊内行高），`--dsw-font-xxs-12` + tabular-nums | `label-secondary` |
| 节点标题 | 13px / 20px | `label-primary` |

> 所有会变的数字（耗时、token、计数、比例）一律 `font-variant-numeric: tabular-nums`，保证数字跳动时**只变数值、不左右挪位**。

### 2.4 收起条 40px 与展开明细 200px：信息怎么分层

总案 §6 C13：**40px 收起条只放一行主摘要**，不是「40 只管把手、另在 48px 摘要行里塞六个数字」。分层如下：

```
┌──────────────────────────────────────────────────────┐
│  ●   验收 7/9 · 78%                        [ 良 ]  ⌄ │
└──────────────────────────────────────────────────────┘
   ↑ 状态点   ↑ 主摘要（主值 = 验收条目通过率）  ↑ 结论 pill
```

| 位置 | 内容 | 规则 |
|---|---|---|
| 40px 收起条 | 左侧状态点 + 主摘要（验收条目通过率 `x/y` + 百分比）+ 右侧结论 pill | 一行、三件事；主摘要是 40px 内**唯一**的数字组，`tabular-nums`；状态点与 pill 同源（§3.9.3 结论） |
| 200px 展开明细 | 其余五项聚合（总耗时 / 总 token / P0 缺陷 / 意见采纳 / skill 采纳）+ 分阶段明细 | 五项用 §3.2 的迷你 stat 铺开；宽度不足时可换行/收进「…」，**不回流到 40px 条** |

- **主摘要永远可扫**：哪怕收起，`验收通过率` 与 `结论 pill` 始终在 40px 里，解决「收起后不知道这次 run 好不好」。
- **副标签 11px 不换行**，超出 `ellipsis`；主摘要 18px 是上限，200px 明细的 stat 主数值同为 18px，不再往上加。
- **每个 stat 用左边 2px 语义色竖条做类别锚点**（token=brand / 耗时=中性 / 缺陷=error / 质量=success），色条不占横向宽度。
- **五项 stat 的最小总宽 424px**（5×72 + 4×16）；明细区窄于 640px 时收进「…」展开，不回压主摘要。
- 未运行时：40px 条显示「尚未运行」，主摘要位置不放 0 占位；展开明细显示空数据说明。

## 三、组件规格

### 3.1 通用指标块结构

每个指标块（迷你 stat、检查器指标行）都用同一套结构：

```
┌──────────────────────────────┐
│▎ 副标签（11px, tertiary）      │   ← 2px 语义色竖条做类别锚点
│  42.3 s  ↑                   │   ← 18px 主数值 + 单位；↑↓ 是变化指示
└──────────────────────────────┘
```

**内容规格字段**（每个指标块必须回答的六件事）：

| 字段 | 定义 |
|---|---|
| 标题 | 副标签文案，中文，≤6 字 |
| 主数值 | 最显眼的那个数，tabular-nums |
| 副文本 | 主数值下方的补充说明（如缓存读占比、阶段进度、常态参考） |
| 单位 | s / 个 / 次 / % / k token |
| 变化指示 | 相对上次刷新或上次运行的 ↑ / ↓，累计单调量（token、耗时）默认隐藏，仅异常跳变（单次刷新 +5%）才亮 |
| 空数据态 | 未运行时显示「—」占位，不显示 0（0 是有意义的数字，别和空混淆） |
| 异常态 | 超过阈值时主数值换语义色 + 图标，见各指标具体规则 |

**状态规格表**（沿用 design-system 的 Property / Default / Hover / Active / Disabled 四列）：

| Property | Default | Hover | Active | Disabled |
|---|---|---|---|---|
| 背景 | 透明 / `bg-layer-1` | `interactive-bg-hover` | 同 Hover | `bg-layer-1`，opacity 0.5 |
| 主数值 | `label-primary` | 不变 | 不变 | `label-tertiary` |
| 副标签 | `label-tertiary` | `label-secondary` | 不变 | `label-tertiary` |
| 语义竖条 | 2px 类别色 | 不变 | 不变 | `border-l2` |
| 描边 | 无 | 无 | 无 | 无 |

### 3.2 展开明细里的五项聚合（40px 条只留验收通过率）

> 40px 收起条只显示「验收条目通过率 + 结论 pill」（§2.4）；下表是展开 200px 明细里的五项聚合 stat，验收通过率一行的主值同时是 40px 条的主摘要。

| 标题 | 主数值 | 副文本 | 单位 | 变化指示 | 空数据态 | 异常态 |
|---|---|---|---|---|---|---|
| 总耗时 | 42.3 | 运行时走秒，结束定格 | s / m | 运行中走秒（最强「活着」信号） | 「—」 | 超预期 P90×1.5 变 error + ⚠ |
| 总 token | 12.3 | 缓存读占比 51%（四桶见 §3.11.3） | k | 默认隐藏 | 「—」 | 单节点超常态见 3.6；total 不可推导时显示「—」，只报桶值 |
| 验收通过率 | 5/8 | 阶段 6/6 · 跳过不计（原「完成度」已改名为阶段进度） | — | 相对上次 run ↑↓ | 「—」 | 有失败/未检测时分别变 error/warn，见 §3.9 |
| P0 缺陷 | 0 | 后接当前未解决的 P1/P2 数 | 个 | 默认隐藏 | 「—」 | >0 变 error |
| 意见采纳 | 78% | 已采纳的 P0/P1 意见 / 应回应 P0/P1 意见 | % | 相对上次 run ↑↓ | 「—」 | <60% 变 warn；分母为 0 时显示「不适用」，不显示 100% |
| skill 采纳 | 7/9 | 唯一 skill 已加载 / 已声明 · 另列加载次数 | — | 默认隐藏 | 「—」 | 有节点 0 加载变 warn；次数与覆盖率分开显示 |

> 摘要条与展开明细只放「整次 run 的聚合」，不逐节点；单节点数字在图上角标和右侧检查器里。
>
> **两张口径不能混**：主值「验收通过率」回答「用户验收条目过了多少」；副文本「阶段 6/6」是原「完成度」改名的**阶段进度**。阶段通过不等于验收通过，反之亦然；两者定义见 §3.8。

### 3.3 节点卡片：图上最小化表达

节点卡片运行时在**设计态基础上叠加**，不重画结构（任务书 §3.3）：

```
┌──────────────────────────────────────┐
│ ↻2                            ▎ 42s  │  ← 左上回环角标 / 右上耗时角标
│  方案设计                             │
│  资深架构师 · 产出设计文档            │
│  🧩 2/3 skills                       │  ← skill 采纳徽标（3 声明，2 实际）
│                                      │
│▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎▎  │  ← 3px token 构成条
└──────────────────────────────────────┘
  ↑ 左侧 2px 竖条：缺陷语义色（缺陷>0 时 error，否则不显示）
```

**卡片上最多显示的东西（硬约束）**：

| 类型 | 内容 | 规则 |
|---|---|---|
| 自由数字 ×2 | ① 耗时（右上角，永远有）；② 状态数字（回环轮次 或 缺陷数，取更紧急的那个） | 第 3 个自由数字一律禁止 |
| 比例徽标 ×1 | skill 采纳「x/y」（实际加载 / 声明） | 固定格式、固定位置，不算自由数字 |
| 构成条 ×1 | token 未命中输入 / 输出 / 缓存读 / 缓存写四段 | 只给比例感，不标具体数 |

**为什么是 2 个自由数字**：① 人在 200ms 扫视里可靠读出的独立数字约 2 个，第 3 个开始需要逐个盯，扫描从「瞥一眼」退化成「读一遍」；② 极端 30 节点时卡片缩小、角标字号压到 11px 以下，2 个以上会互相挤压换行，破坏卡片高度对齐；③ 状态色（描边/竖条）是 pre-attentive 的，不占「数字槽」，2 个数字 + 状态色已经能回答「这个节点现在怎么样」的 90%。

**角标状态规格**：

| Property | Default | Hover | Active | Disabled（跳过） |
|---|---|---|---|---|
| 背景 | `bg-layer-2` | `interactive-bg-hover` | 同 Hover | 透明 + 虚线描边 |
| 文字 | `label-secondary` | `label-primary` | 不变 | `label-tertiary` |
| 耗时角标内容 | 运行中走秒（42s），结束定格（3:12） | 无额外 | 无 | 「—」 |
| 回环角标内容 | 「↻ n」，仅 n>0 显示 | tooltip「打回 n 次」 | 无 | 不显示 |

**token 构成条**（3px 高，四段，段间 1px 缝；四段 = 四个互斥计费桶）：

| 段 | 颜色 | 语义 | 色盲补救 |
|---|---|---|---|
| 未命中输入 | `brand-primary` | `inputTokens`（未命中缓存的输入） | 位置固定在最左 + hover tooltip |
| 输出 | `state-success` | `outputTokens`（含 reasoning，不另加） | 位置固定第二 |
| 缓存读 | `label-tertiary` | `cacheReadTokens`（读缓存；只报桶值） | 位置固定第三 + 中性灰 |
| 缓存写 | `label-caption` | `cacheWriteTokens`（写缓存；只报桶值） | 位置固定最右 + 另一种中性灰 |

> 四段互斥：`prompt = 未命中输入 + 缓存读 + 缓存写`，`total = prompt + 输出`。**缓存读/写不得称为「无成本」或「复用」**——没有计费证据就不作成本承诺，只报桶值（见 §3.11.3）。
>
> 构成条不标具体数字，hover 时 tooltip 报「未命中输入 4.2k · 输出 1.8k · 缓存读 6.0k · 缓存写 0.4k」。它借的是 Grafana stat 面板 sparkline 的思路——**数字是主角，条只是给比例感的背景**——但这里条表达的是「构成」而非「趋势」。

**缺陷竖条**（卡片左侧 2px）：

| Property | 无缺陷 | 有缺陷 |
|---|---|---|
| 显示 | 不显示（干净） | 2px `state-error-primary` |
| 数字 | — | 缺陷总数并入「状态数字」槽（与回环轮次二选一，取更紧急的） |

### 3.4 审查缺陷：带列表的数据在小空间怎么表达

小空间（收起条 / hover）**只给分布条 + 当前未解决总数 + P0**，不给列表。分布条按**当前未解决**的缺陷算，不按发现总数算：

```
缺陷 9（发现 12）  P0 0 · P1 3 · P2 6
███████████████████████████████░░░░
└─ P0(error)──┘└─P1(warn)─┘└─P2(中性)─┘
        12px 高堆叠条，段宽按「未解决」数量比例
```

| 段 | 颜色 | 说明 |
|---|---|---|
| P0 | `state-error-primary` | 发布阻塞项，**未解决** >0 直接进异常态并阻止通过 |
| P1 | `state-warn` | 需关注；未解决 >0 不阻止运行，但阻止「优/良」绿灯 |
| P2 | `label-secondary` | 建议级，只展示 |

- **色盲补救**：段间 1px 缝 + 固定左→右 P0→P1→P2 顺序 + hover 逐段 tooltip「P1 · 3 个未解决」，不靠颜色单独传义。
- **完整列表只在右侧检查器**的「审查」区展开：每条缺陷一行（严重级徽标 + 标题 + 所在节点 + 生命周期状态：发现 / 已采纳 / 已修复 / 复验通过 / 已关闭，附证据链接）。**采纳 ≠ 修复 ≠ 复验通过**：采纳只表示认可问题，修复只表示声称改了，只有复验通过才从「未解决」里移除（定义见 §3.10.4）。抽屉里永不逐行铺缺陷列表——那会把 160px 内容区撑爆。

### 3.5 抽屉收起条（40px 一行主摘要）

```
┌──────────────────────────────────────────────────┐
│  ●  验收 7/9 · 78%                     [ 良 ]  ⌄ │
└──────────────────────────────────────────────────┘
  ↑ 8px 状态点   ↑ 主摘要 18px/600 tabular-nums   ↑ 结论 pill + 12px 箭头
```

| Property | Default | Hover | Active | Disabled |
|---|---|---|---|---|
| 背景 | `bg-layer-2` | `interactive-bg-hover` | 同 Hover | `bg-layer-2` |
| 上边框 | 1px `border-l2` | `border-l3` | 不变 | 不变 |
| 主摘要文字 | `label-primary` | 不变 | 不变 | `label-tertiary` |
| 状态点 | 8px 圆：success / warn / error / `label-tertiary`（未运行） | 不变 | 不变 | 不显示 |
| 结论 pill | §3.9.3 结论的语义底 + 反色字（优/良=success、需返工/证据不足/未完成=warn、失败=error） | 提亮 8% | 同 Hover | 不显示 |
| 箭头 | `label-tertiary` | `label-primary` | 旋转 180°（展开时） | 不显示 |
| 高度 | 40px | 40px | 40px | 40px |

- **收起条只放一行主摘要**（总案 §6 C13）：左状态点、中主值 `验收条目通过率 x/y · 百分比`、右结论 pill；**其余五项（总耗时 / 总 token / P0 缺陷 / 意见采纳 / skill 采纳）全部在展开 200px 的明细里**（§2.4、§3.2）。
- 旧稿「40 只是把手 + 另 48 行摘要」作废：40px 内不放第二行，也不再单独存在 48px 摘要行。
- **收起条永远可见**（哪怕收起），所以「这次 run 好不好」这个最关键的回看信息始终有一行可扫。
- 未运行时空数据态：状态点用 `label-tertiary`，主摘要显示「尚未运行」，不显示占位数字，结论 pill 不显示。

### 3.6 右侧检查器·运行态区

选中一个节点时，检查器从「配置」切到「运行态」分页（用检查器顶部的分段控件「配置 / 运行」切换，默认落在「运行」当任务在跑）。**检查器本身常驻**：空选中时显示流程级设置，不做进出动画、不隐藏（总案 §6 C09）。运行态区内容：

| 区块 | 内容 | 形态 |
|---|---|---|
| 状态头 | 节点名 + 状态徽标 + 耗时 + 打回轮次 | 一行 |
| token | 未命中输入 / 输出 / 缓存读 / 缓存写四个桶 + prompt 合计；total 仅在可推导时显示 | 四个迷你 stat + 合计 |
| skill 采纳 | 唯一覆盖 x/y（声明去重）+ 加载次数 n + 失败 k；逐行列出声明 skill 的加载状态 | 列表，行高 32px |
| 审查缺陷 | 发现总数 / 当前未解决数 + 分布条 + 逐条生命周期（发现→采纳→修复→复验）与证据链接 | 分布条 + 列表 |
| 质量 | 规范检查四态（规则集 id@版本 + 证据链接）/ 测试通过率（通过/执行 + 报告链接）；缺证据显示「未检测」 | 两个迷你 stat |

> 检查器指标主值 20px，是「要看全」的地方；画布角标是「扫一眼」的地方；两者信息同源，不打架。

### 3.7 指标定义总则（六件事）

从 §3.8 起，每个指标都必须回答同样六件事。缺任何一项，该指标只能显示「未检测」，不能显示为通过，也不能拿 0 顶替。

| 字段 | 要求 |
|---|---|
| 定义公式 | 一行可复算的式子，分子、分母分别写出来 |
| 分子 / 分母口径 | 哪些算、哪些不算：跳过、不适用、未执行、重试、额外加载 |
| 数据来源 | 事件名 + 字段路径；没有事件源就写「未定义」，不拿近似值顶替 |
| 去重与归属 | 父子 agent、轮次（`attemptId`）、重试 / 重放分别怎么算 |
| 状态机 | 未检测 / 通过 / 不通过 / 不适用 四态及迁移条件 |
| 返工与旧结论失效 | 新 attempt 何时让旧结论作废、失效边界到哪、失效后计入哪一边 |

**四态的共同定义**（四个指标共用，后文不再重复）：

| 状态 | 判定 | 展示 | 会不会进分子 |
|---|---|---|---|
| 未检测 | 没有证据、证据不完整、来源不可达 | 「未检测」+ 缺什么 | 不进分子，进「未检测数」 |
| 通过 | 证据齐全且满足判定条件，带 `attemptId` + 证据链接 | 「通过」+ 证据链接 | 进 |
| 不通过 | 证据齐全但不满足判定条件 | 「不通过」+ 证据链接 | 不进 |
| 不适用 | 被**显式豁免**（跳过阶段 / 无代码变更 / 用户声明），必须记录判定人、理由、时间 | 「不适用（理由）」 | 不进分母，但必须列出 |

> **「未检测」不是「通过」，也不是「0」**。没有跑测试不等于测试 0 分，也不等于测试通过；没有审查报告不等于采纳率 100%。「不适用」只能由人显式记录，不能由前端根据「看起来没问题」自动推断。

**一句话验收的写法**：每个指标末尾给一句「给一份 run 记录，能独立复算出同一个数，且每个分子项都能追到 `attemptId` + 证据链接」。做不到这句，就说明定义还没闭合。

> 说明：本文件里的运行事件名（`run/start`、`node/end`、`verdict` 等）是 §3.12 的运行数据契约。**引擎尚未接入，这些事件当前没有实现**；在它们落地前，§3.8–§3.11 的指标一律显示「未检测」，不得用设计稿里的示例数字冒充真实运行数据。

### 3.8 M01 任务完成度：阶段进度 + 验收条目通过率

旧口径「完成度 = 通过阶段 / 总阶段」回答的是**流程走到哪**，不是**用户要的东西验收了没有**。本节把它改名为**阶段进度**，另立**验收条目通过率**。两个数并列，不合并、不互相替代。

#### 3.8.1 阶段进度（原名「完成度」）

| 六件事 | 定义 |
|---|---|
| 定义公式 | `阶段进度 = 当前有效 passed 阶段数 / (阶段节点总数 − skipped 阶段数)`；分母为 0 时「未检测」，不是 100% |
| 分子 / 分母口径 | 分子只算**当前仍有效**的 `passed`；分母 = 本次 run 的全部阶段节点，减去 `skipped` 阶段（跳过阶段单列，不计入分母）；开始 / 结束节点不算阶段 |
| 数据来源 | 契约事件 `node/end` 的 `data.status`（`passed` / `failed` / `skipped`）与 `attemptId`；节点集合来自流程 `nodes`。事件定义见 §3.12 |
| 去重与归属 | 每个阶段一票，取该阶段**最后一次有效** `node/end`；同一阶段重试只更新不累加；子 agent 的运行结果归到其所属阶段，不单独占一个阶段 |
| 状态机 | 未检测：没有该阶段的 `node/end`；通过：`passed` 且后续未被返工失效；不通过：`failed`，或旧 `passed` 被返工失效（显示「未通过（旧结论失效）」）；不适用：`skipped`（不计分母，必须列出） |
| 返工与旧结论失效 | `edge/reject` 触发 `attemptId + 1`。打回边 `S → T` 时，从 `T` 沿 next 边到 `S` 路径上的阶段（含 `T`、`S`）的旧 `passed` 全部失效，回到「未通过（旧结论失效）」，直到新 attempt 产生新 `passed`。路径外的阶段保留原结论 |

**阶段进度一句话验收**：给一份 run，能复算出 `passed / (阶段节点总数 − skipped)`，且每个计入分子的 `passed` 都能追到 `node/end` + `attemptId`；把某阶段打回后，路径内阶段的 `passed` 立即从分子消失、分母不变。

#### 3.8.2 验收条目通过率（任务完成度）

**验收条目**是用户/任务卡给出的、可逐条勾选的最小验收单位，必须先结构化，不能从自由文本里猜。

| 字段 | 必填 | 说明 |
|---|---|---|
| `itemId` | 是 | 稳定 id，跨 attempt 不变 |
| `sourceNodeId` | 是 | 该条目归属的阶段；阶段被跳过时整组条目不进分母 |
| `verdict` | 是 | `pass` / `fail` / `na`（`na` 只能由人显式判定） |
| `decidedBy` | 是 | `{ kind: 'human' \| 'auto', id }`；自动判定必须给执行器 id |
| `evidenceUrl` | 是（`pass`/`fail` 都要） | 证据链接：测试报告、审查记录、截图、产物路径 + 内容哈希 |
| `decidedAt` | 是 | ISO 8601 带时区偏移（存储用 UTC，见 §3.12.4） |
| `attemptId` | 是 | 该判定产生于哪一轮返工；用于区分「第几轮的通过」 |

| 六件事 | 定义 |
|---|---|
| 定义公式 | `验收通过率 = 当前有效 verdict=pass 的条目数 / (已声明条目数 − 跳过阶段条目数 − 显式 na 条目数)`；分母为 0 时「未检测」，不是 100% |
| 分子 / 分母口径 | 每个 `itemId` 一票，取**最后一次有效**判定；`pass` 必须同时有 `evidenceUrl` 与 `attemptId`，否则按「未检测」；`fail` 进分母不进分子；`na` 与跳过阶段条目移出分母但必须在结论里列出；重复判定不叠加，只替换 |
| 数据来源 | 契约事件 `verdict`：`{ scope: 'acceptance', itemId, attemptId, status, evidenceUrl, decidedBy, decidedAt }`。条目定义来自任务卡的验收清单（当前未实现，见下） |
| 去重与归属 | 父子 agent 不改变条目归属：条目只归 `sourceNodeId`；子 agent 的判定作为该阶段判定的证据，不新增条目；同一 `itemId` 跨 attempt 的旧判定按失效规则处理 |
| 状态机 | 未检测：没有判定，或判定缺证据链接 / `attemptId`；通过：`pass` + 证据齐全 + 未被失效；不通过：`fail`，或旧通过已失效（显示「未通过（旧结论失效）」）；不适用：`na`（人工 + 理由 + 时间）或整阶段 `skipped` |
| 返工与旧结论失效 | 打回后，`T → S` 路径及 `T`、`S` 上条目的旧 `pass` 一律失效，**从分子移除并计入分母的「未通过」**（不是「未检测」），直到新 attempt 重新判定。路径外条目的旧 `pass` 保留，但显示其 `attemptId`，例如「第 1 轮通过（本轮未重跑）」 |

**返工版本怎么显示**：每个条目、每个阶段结论都带 `attemptId`；卡片/检查器显示「第 2 轮通过」「第 1 轮通过（保留）」而不是笼统的绿勾。汇总行写「本轮通过 5 / 保留 2 / 未通过 1」，能一眼看出哪一轮的通过。

**一句话验收**：任取一次 run，能列出验收通过率 `x/y` 的每个 `itemId`、判定人、证据链接、判定轮次；对开发阶段触发一次打回后，开发/测试的旧通过自动从分子消失并标「旧结论失效」，需求/方案等路径外阶段的通过仍保留。

**当前未定义（如实标注）**：

- 验收条目从哪来：当前模型只有自由文本 `task`，没有结构化验收条目 schema；接入前该指标只能显示「未检测」。
- 自动判定器：需要可复现的检查脚本 + 证据产物；「模型说通过」不算自动判定。
- 证据链接协议：相对路径 / 产物哈希 / 访问权限尚未拍板；没有可达链接按「未检测」。

### 3.9 M02 质量评分：必要证据不过/缺失不得绿灯

#### 3.9.1 三条修法

1. **文案**：返工 ≥1 不得写「一次通过」；只有 `返工 = 0`（即 `attemptId = 1`）才允许「首轮通过」。
2. **必要质量证据失败/缺失不得绿灯**：测试、规范、审查采纳、P0/P1 未解决任一项不通过或未检测，结论只能是「需返工」或「证据不足」。
3. **「未检测」与「通过」分开**：缺证据按未检测处理，并在结论里显式列出缺哪一项；不允许用 0 或 100% 填补。

#### 3.9.2 必要质量证据表

先算证据状态，再走 §3.9.3 的判定表。`不适用` 必须带判定人 + 理由 + 时间。

| 证据 | 通过 | 不通过 | 未检测 | 不适用 |
|---|---|---|---|---|
| 验收条目 | 验收通过率 100%，每条有证据链接 | 任一条目 `fail` 或旧通过失效 | 分母为 0 / 缺判定 / 缺链接 | 整阶段 `skipped` 或人工 `na` |
| 测试 | 执行用例数 >0 且通过率 100%，有报告链接 | 通过率 <100% | 无执行记录 / 无报告链接 / 只跑了 0 条 | 本 attempt 无代码改动且人工豁免；须列出理由 |
| 规范 | 状态=通过，且规则集 id@版本、执行器、执行时间、报告链接齐全（§3.10） | 状态=不通过 | 状态=未检测 / 来源字段缺失 | 无代码改动或规则集不适用，人工豁免 |
| 审查采纳 | P0/P1 应回应数 >0 且采纳率 ≥60%；或应回应数 =0 且有「本轮无 P0/P1 意见」的报告证据 | 采纳率 <60% | 无审查报告 / 分母 >0 但采纳数缺失 | 本轮无审查需求且人工豁免 |
| P0/P1 未解决 | P0 未解决 =0（P1 另列；P1 >0 不阻止运行，但阻止绿灯） | P0 未解决 >0 | 缺陷数据缺失 | 无审查需求且人工豁免 |

- **采纳 ≠ 修复 ≠ 复验通过**：采纳率只衡量「审查意见有没有被回应」，P0/P1 是否真解决看 §3.10 的生命周期。
- **P1 >0** 不在「证据不通过」里，而是单独作为「遗留项」阻止「优/良」，落到「可」。
- **测试不适用**只允许「本 attempt 确实没有代码改动」且人工记录理由；「没时间测」不是不适用。

#### 3.9.3 判定表（自上而下，第一个满足的生效）

| 序 | 条件 | 一句话结论 | 颜色 |
|---|---|---|---|
| 1 | 任一阶段失败 | 「失败：{阶段名} 未通过」 | `state-error-primary` |
| 2 | 阶段进度 <100% 或 验收通过率 <100% | 「未完成：验收 {x}/{y}，阶段 {a}/{b}」 | `state-warn` |
| 3 | P0 未解决 >0 | 「需返工：{n} 个 P0 未解决」 | `state-warn` |
| 4 | 任一必要证据 = 不通过 | 「需返工：{失败项及实测值}」 | `state-warn` |
| 5 | 任一必要证据 = 未检测 | 「证据不足：{未检测项}，不能判定为通过」 | `state-warn` |
| 6 | 全部证据通过 + P1 未解决 =0 + 返工 =0 | 「优：首轮通过，质量证据齐全」 | `state-success` |
| 7 | 全部证据通过 + P1 未解决 =0 + 返工 1–2 | 「良：返工 {n} 轮后达标」 | `state-success` |
| 8 | 全部证据通过 + （返工 >2 或 P1 未解决 >0） | 「可：返工 {n} 轮、遗留 {m} 个 P1，建议复盘」 | `state-warn` |
| 9 | 其余（数据自相矛盾） | 「可：证据状态不一致，请复核」 | `state-warn` |

> 命中第 4/5 行时，结论里仍要**追加其余未检测项**（例如「另有规范未检测」），不能因为先命中失败项就隐藏缺证据项。第 6/7 行是唯一允许绿灯的两行，且都要求「全部证据通过 + P1=0」；**不适用项也必须在结论里列出**，绿灯时也不例外。返工 >0 时文案禁止出现「一次通过」。

#### 3.9.4 反例逐条演算（评审给的输入）

输入：完成 100%（阶段进度 6/6、验收通过率 8/8）、返工 1 次（`attemptId=2`）、P0 未解决 0、意见采纳率 0%（应回应 P0/P1 共 20 条、采纳 0 条）、测试通过率 50%（执行 10 条、通过 5 条）、P1 未解决 20、规范检查通过、各证据链接齐全。

| 步 | 检查 | 结果 |
|---|---|---|
| 1 | 顺序 1：任一阶段失败？ | 否 |
| 2 | 顺序 2：阶段进度 / 验收通过率 <100%？ | 否（6/6、8/8） |
| 3 | 顺序 3：P0 未解决 >0？ | 否（0） |
| 4 | 顺序 4：任一必要证据 = 不通过？ | **是**：测试 50% <100%；采纳率 0% <60% |
| 5 | 结论 | 「需返工：测试通过率 50%（要求 100%）、P0/P1 意见采纳率 0%（要求 ≥60%）；另有 20 个 P1 未解决」——`warn`，不是「良」，不是绿色 |
| 6 | 若测试证据缺失（而非 50%） | 顺序 4 不命中，顺序 5 命中：「证据不足：测试未检测」，仍不是绿色 |
| 7 | 反事实验证：测试 100%、采纳 100%，但 P1 仍 20 | 顺序 6/7 都要求 P1=0，不命中；顺序 8 → 「可：返工 1 轮、遗留 20 个 P1」，仍不是绿色 |
| 8 | 反事实验证：测试 100%、采纳 100%、P1=0、返工 1 | 顺序 7 → 「良：返工 1 轮后达标」（文案不写「一次通过」） |
| 9 | 反事实验证：同样条件、返工 0 | 顺序 6 → 「优：首轮通过，质量证据齐全」 |

> 结论：该反例在三条独立门槛上被拦下（测试 50%、采纳 0%、P1=20），不会再落到「良」。只要把「证据齐全且通过」当成绿灯前置条件，旧表的假阳性就被消掉。
> 若该 run 根本没有验收条目，`验收通过率` 是「未检测」而不是 100%，顺序 2 同样拦下；「没条目」不能变成满分。

#### 3.9.5 文案禁用清单

| 禁止写法 | 触发条件 | 正确写法 |
|---|---|---|
| 「一次通过」 | 返工 ≥1 | 「返工 {n} 轮后达标」 |
| 「通过」 | 任一必要证据未检测 | 「未检测（缺 {项}）」或「证据不足」 |
| 「符合规范」 | 规范状态未检测 | 「规范未检测」 |
| 「已修复」 | 缺陷只到「已采纳」 | 「已采纳，未修复」 |
| 「缓存命中，无成本」 | 任何缓存读/写 >0 | 「缓存读 {x} / 缓存写 {y}（只报桶值）」 |
| 「完成度 100%」 | 验收条目分母为 0 | 「验收未检测（无验收条目）」 |

#### 3.9.6 一句话验收

把上面的反例输入喂进判定器，输出必须是「需返工」并同时列出「测试 50%」「采纳 0%」两项，不能出现「优 / 良」或绿色；把测试与采纳改成 100%、P1 改成 0、返工改成 1，输出才允许变为「良：返工 1 轮后达标」。

**当前未定义 / 待校准（如实标注）**：

- 采纳率门槛 60% 沿用旧表，**没有样本校准**，是产品阈值不是统计结论。
- 返工 ≤2 才「良」、>2 转「可」也是产品选择，未用数据校准。
- P1 未解决必须为 0 才绿灯是**从严政策**；P1 积压到多少仍可接受，没有数据，标为待定。
- 测试通过率按「用例」还是「测试套件」计：本设计按用例；若项目只产出套件，需要显式映射，当前未定义。
- 自动判定器、证据链接格式、审查报告 schema 均未定义。

### 3.10 M03 编码规范与缺陷生命周期

#### 3.10.1 规范检查的来源（六项字段）

规范检查不是「跑了个 lint 没报错」，而是一次**可复现的执行**。以下字段缺任一，状态就是「未检测」：

| 字段 | 说明 |
|---|---|
| `ruleSetId` | 规则集标识（如项目 lint 配置 / 规则包名） |
| `ruleSetVersion` | 规则集版本或内容哈希；**不同版本的结果不可直接比较** |
| `executor` | 执行器与版本（工具名 + 版本号） |
| `executedAt` | 执行时间，ISO 8601 带时区偏移 |
| `targetTree` | 被检查的目标（commit / tree hash + 文件范围） |
| `reportUrl` | 证据链接：完整报告 + 内容哈希；只有摘要不算证据 |

#### 3.10.2 规范结果四态

| 状态 | 判定条件 | 计量 | 展示 |
|---|---|---|---|
| 通过 | 执行器在声明的 `targetTree` 上跑完声明的规则集，0 违规，六项来源字段齐全 | 通过检查点数 / 执行检查点数；分母 0 = 未检测 | 「通过 n/n」+ 规则集 id@版本 + 证据链接 |
| 不通过 | 至少 1 条违规；每条给 `ruleId` + 文件 + 行号 + 级别 + 证据链接 | 违规数按规则 / 严重级分组 | 「不通过：n 条」+ 可点开到具体位置 |
| 未检测 | 没有执行记录 / 执行器崩溃 / 只跑了部分 scope / 缺六项来源字段任一 | 不填 0，不算通过 | 「未检测（缺 {字段}）」 |
| 不适用 | 本 attempt 无代码改动，或规则集明确不覆盖改动类型；**必须人工记录理由 + 时间** | 移出分母，列出 | 「不适用（理由）」 |

- **通过检查点** = `passedChecks / executedChecks`（同时给 `passedChecks` 绝对值），与违规列表一起展示；`executedChecks=0` 时不是 100%，是「未检测」。
- 规范通过结论绑定 `ruleSetVersion + targetTree`；任一变化，旧通过失效（见 §3.10.6）。

#### 3.10.3 缺陷计量：发现总数 vs 当前未解决数

| 指标 | 定义 | 用途 |
|---|---|---|
| 发现总数 `foundTotal` | 本次 run 内所有 attempt 发现的**唯一 `defectId`** 数；同一 id 跨 attempt 不重复计 | 看「一共发现了多少问题」 |
| 本轮新发现 `foundInAttempt` | 当前 attempt 首次出现的 `defectId` 数 | 看返工是否引入新问题 |
| 当前未解决 `unresolved` | 截至当前 attempt 末，生命周期未到「复验通过 / 已关闭」的 `defectId` 数，按 P0/P1/P2 分组 | 看「现在还有多少雷」；收起条主摘要 / 明细分布条默认用它 |
| 本轮新解决 `resolvedInAttempt` | 从上一 attempt 的未解决集合中移除的数量 | 看返工是否真在收敛 |

- 两个数必须同时可查，不能拿「发现总数」冒充「未解决」，也不能反过来。分布条用**未解决**，列表默认按 P0→P1→P2 + 未解决优先排序。
- `defectId` 跨 attempt 稳定；回归时**重开同一个 id**，不新建一条，否则「发现总数」会被灌水。
- 严重级在发现时定；降级必须人工记录理由，不允许静默降级。

#### 3.10.4 生命周期状态机

```
发现(open) → 已采纳(accepted) → 已修复(fixed) → 复验通过(verified) → 已关闭(closed)
                    │                 │                  │
                    └── 不修(wontfix) └── 回归(reopen) ───┘
```

| 状态 | 进入条件 | 必带证据 | 计入未解决？ |
|---|---|---|---|
| 发现 open | 审查 / 测试产出 finding，含 id、级别、位置、理由 | finding 原文 + 位置 | 是 |
| 已采纳 accepted | 承认问题、承诺处理；**不代表改了** | 采纳人 + 时间 | 是 |
| 已修复 fixed | 有改动或明确修法说明，绑定 `targetTree` | commit / diff / 修法说明 + treeHash | 是（未复验） |
| 复验通过 verified | 独立复验通过，绑定 `defectId + attemptId + treeHash` | 复验记录 + 证据链接 | 否 |
| 已关闭 closed | verified，或 P2 的 wontfix（带理由）；P0 不允许自动 wontfix | 关闭人 + 理由 + 时间 | 否（P2 wontfix 仍列出） |
| 回归 reopen | 已验证的问题在新 `targetTree` 上复现 | 新的失败用例 + 位置 | 是（沿用原 id） |

> **采纳 ≠ 修复 ≠ 复验通过**：只有 `verified` 才把缺陷从未解决集合移除。`accepted` 和 `fixed` 都仍然算「未解决」；P0 尤其如此。

#### 3.10.5 P0 决定返工的口径

- **P0 未解决（open / accepted / fixed 未复验）> 0 → 本次 attempt 不能通过，必须返工。**
- P0 修复但未复验 → 仍算未解决 → 仍返工；只有 `verified` 才解除阻塞。
- P0 的 `wontfix` 不允许自动关闭；人工风险接受也必须显式记录，且在设计上仍**阻止绿灯**（P0 豁免策略见 §3.10.7）。
- P1 不强制返工，但 P1 未解决 >0 阻止「优/良」（§3.9）；P2 只展示，不阻止运行。
- 返工触发后 `attemptId + 1`；P0 在旧 attempt 的状态保留，直到在新 attempt 被复验通过。

#### 3.10.6 返工与旧结论失效

- 规范通过结论绑定 `ruleSetVersion + targetTree`；新 attempt 的 `targetTree` 变了 → 旧通过标 `stale`，回到「未检测」，必须重跑，不能沿用。
- 缺陷 `verified` 绑定 `defectId + attemptId + treeHash`；新 attempt 的 `treeHash` 变了 → 所有旧 `verified` 失效，回到「已修复待复验」并重新计入未解决。
- 例外：能用文件级哈希证明本次改动**没有触及**该缺陷相关文件时，可标 `carriedOver` 并保留复验结论，但必须记录「未触及」的证据；这是显式豁免，不是默认行为。
- 规范与缺陷的旧数字不跨 attempt 累计；`foundTotal` 累计的是「发现」，不是「通过」。

#### 3.10.7 一句话验收与未定义项

**一句话验收**：给定一个 attempt，能列出规范检查的 `ruleSetId@version` / 执行器 / 执行时间 / `targetTree` / 报告链接与 `n/n` 通过检查点；能同时报出「发现总数 12」和「当前未解决 9」；把一条 P0 从「已修复」改成「复验通过」之前，结论始终是「需返工」。

**当前未定义（如实标注）**：

- 具体规则集与执行器尚未选定；本设计只定义来源字段，不绑定工具。
- 规则集版本升级后的结果可比性未定义；跨版本数字禁止直接比较。
- 「独立复验」是否必须由不同 agent / 不同人执行，未定。
- P0 人工风险接受的展示与审批流未定义；当前默认不允许 P0 自动关闭。
- `targetTree` 的文件级哈希粒度、`carriedOver` 的判定脚本未定。

### 3.11 M04 skill 采纳率与 token

#### 3.11.1 skill 采纳率：唯一覆盖，不混次数

| 六件事 | 定义 |
|---|---|
| 定义公式 | `覆盖率 = #(成功加载的唯一 skill 集合 ∩ 已声明唯一 skill 集合) / #(已声明唯一 skill 集合)`（`#` 表示集合元素个数）；分母为 0 → 「不适用」，不是 100% |
| 分子 / 分母口径 | 分母 = 流程里**声明过的唯一 skill 去重数**（所有节点 `skills` 的并集，按名字精确去重）；分子 = 其中**至少成功加载过一次**的唯一 skill 数；跳过阶段声明的 skill 仍在分母里，但加载状态标「因跳过未加载」，另给「执行口径」（剔除 skipped 阶段）供参考；实际加载但未声明的 skill 单列「额外加载」，不进分子 |
| 数据来源 | `session/event`（`{ global: true }`）的 `tool/call`：`data.name === 'skill'`，`data.arguments` 是 JSON 字符串，解析后的 `name` 字段即 skill 名；用 `callId` 配对 `tool/result`，无 `error` 才算成功加载。宿主 skill 工具参数名就是 `name` |
| 去重与归属 | 覆盖率按 skill 名全局去重；父子 agent 各自会话的加载都算，全局只计一次；节点级分母 = 该节点声明的唯一 skill，分子 = 该节点执行期间成功加载的唯一 skill（声明在 A、由 B 加载时，全局算覆盖、A 节点级仍算未覆盖、B 记为额外加载，不回溯给 A）；轮次上主指标按整个 run 去重，另给「本轮新增加载」列；同一 `callId` 的重放去重，不重复计 |
| 状态机 | 未检测：没有 `tool/call` 证据 / 事件缺字段 / 会话到节点映射缺失；通过：该节点声明的 skill 全部成功加载；不通过：有声明但未全部加载（覆盖率 <100%）；不适用：该节点 / 流程没有声明 skill（分母 0） |
| 返工与旧结论失效 | 覆盖率是 run 级事实，不因 attempt 失效而回退；但「本轮新增加载」与节点级「本轮是否加载」按 `attemptId` 分段。旧 attempt 加载过、新 attempt 没加载，不改变 run 级覆盖，但节点级本轮显示「本轮未加载」 |

**加载次数另列**（不与覆盖率混用）：

| 量 | 定义 | 口径 |
|---|---|---|
| 尝试次数 | `tool/call` 中 `name === 'skill'` 的调用总数 | 含成功与失败；按节点 / 成员 / attempt 分组 |
| 成功加载次数 | 配对 `tool/result` 且无 `error` 的调用数 | 同一 skill 多次加载按次计 |
| 失败次数 | 尝试次数 − 成功加载次数 | 失败原因单列，不进覆盖率分子 |
| 额外加载 | 成功加载但未在流程中声明的 skill | 单列清单，不进分子、不进分母 |

> 覆盖率回答「声明的东西有没有被用上」，加载次数回答「用了多少次」。两者不能互相替代，也不能用一个 `7/9` 同时表达。

#### 3.11.2 skill 状态机与归属细则

- **父子 agent**：每个 agent 有独立会话；`tool/call` 归属发出调用的会话。子 agent 的加载归子 agent 的 `memberId`，再汇总到所属节点；主管（父 agent）自己的加载归主管 `memberId`；全局覆盖按 skill 名去重，同一 skill 被父子各加载一次只算一次覆盖、两次成功加载。
- **轮次**：`tool/call` 带 `turn/step` 与 `attemptId`；主覆盖率跨 attempt 去重；节点级和「本轮」视图按 `attemptId` 分组。返工后重新加载同一 skill，不增加覆盖率，只增加成功加载次数。
- **重试 / 重放**：同一 `callId` 的重放只算一次（按 `callId` 去重）；重试产生新 `callId` 时算一次新的成功/失败尝试，覆盖率不变。`arguments` 解析失败（非 JSON、缺 `name`）的调用记为「无效调用」，单列，不能猜一个 skill 名塞进分子。
- **跳过阶段**：其声明的 skill 仍计入全量分母，但状态显示「因阶段跳过未加载」；执行口径（剔除 skipped）另给一个数，避免把「没跑到」误读成「没采纳」。

#### 3.11.3 token：四个互斥桶

数据来源：`session/event`（`{ global: true }`）里 assistant 消息的 `assistant/message.data.usage`；缺失时取该次 `assistant/attempt.data.stream` 中最后一个 `usage` chunk；压缩摘要的用量在 `compaction/summary` 事件的 `data.usage`（背景里写作 `compaction/summary.usage`），是一次独立的模型调用，**要计入总量**。宿主 `normalizeUsage` 的字段与约束如下：

| 桶 | 宿主 `usage` 字段 | 投影字段 | 定义 |
|---|---|---|---|
| 未命中输入 | `inputTokens` | `uncachedInputTokens` | 未命中缓存的输入 token |
| 输出 | `outputTokens` | `outputTokens` | 输出 token（`reasoningTokens` 是它的子集，不另加） |
| 缓存读 | `cacheReadTokens` | `cacheReadTokens` | 从缓存读入的 prompt token |
| 缓存写 | `cacheWriteTokens` | `cacheWriteTokens` | 写入缓存的 prompt token |
| 可选 | `reasoningTokens` | — | 必须 ≤ `outputTokens`；只用于解释输出构成 |
| 可选 | `totalTokens` | — | 若给出，必须与 `prompt + output` 一致 |

**互斥与可推导性**：

- `prompt = inputTokens + cacheReadTokens + cacheWriteTokens`；`total = prompt + outputTokens`。
- 只有 `cacheReadTokens` 与 `cacheWriteTokens` **都存在**时才允许推导 total；缺任一且没有可信的 `totalTokens`，total 显示「—」，只报四个桶值。
- 字段缺失、非安全整数、负数、`reasoningTokens > outputTokens`、`totalTokens` 与 `prompt + output` 矛盾 → `normalizeUsage` 返回 `undefined`。该条 usage 按「未检测 / 数据矛盾」处理，**不补 0、不猜**。
- 宿主投影在累加时会把缺席的缓存桶按 0 处理（`bucketsFrom`），但 UI 不能把「投影里的 0」当成「事实上的 0」；缺桶时仍要标「未检测」。

**归属规则**：

- **父子 agent**：每条 usage 归产生该消息的会话，再映射到 `nodeId + memberId`；父 agent（主管）与子 agent 分开列，节点合计 = 该节点下所有成员的用量之和；无法映射的进 `unattributed` 桶，不摊派给任何节点。
- **轮次**：usage 归 `assistant/message` 落库时所在的 `attemptId`；跨 attempt 的飞行中调用（打回前发出、打回后落库）单独标「跨 attempt」，按落库时 attempt 计，并列出来。该边界情况尚未有真实样本，标为待验证。
- **重试 / 重放（按宿主实际语义）**：同一 `(turn, step)` 的重放走 `addReplacing` —— 先减旧桶值、再加新桶值，绝不重复累加；`llm/retry-started` 会清空该 `(turn, step)` 的上一份样本，随后新 attempt 的用量是**追加**（因为那是新的真实调用，不替换旧调用）。两条规则都要遵守：重放不叠加，重试不漏计。

> 口径说明：任务书要求「重试 / 重放按 `addReplacing` 语义替换而不是叠加」，指的是**同一份样本**的重放必须替换；`llm/retry-started` 是宿主显式清槽后的**新真实调用**，实现上是追加而不是替换。把重试也当替换会漏计第二次调用，和 `addReplacing` 的意图相反；这里以宿主源码为准并写明，避免实现时按字面误做。
- **压缩摘要**：`compaction/summary.usage` 归触发压缩的会话 / 节点；如果压缩发生在 run 级、没有节点归属，进 `unattributed`，并在检查器单列。

**成本**：本设计**不承诺成本**。缓存读 / 写不是「无成本」，也不是「免费复用」；没有 provider 价目表与计费时点，就只能报四个桶值与可推导的 total。成本字段标为「未定义」。

**token 状态机**：

| 状态 | 条件 | 展示 |
|---|---|---|
| 通过 | `normalizeUsage` 成功，四桶齐全，total 可推导 | 四桶 + total + 缓存读占比 |
| 不通过 | usage 自相矛盾（reasoning > output、total 不一致、负数/非整数） | 「用量数据矛盾」+ 原因，不累计该条 |
| 未检测 | 缺字段 / 无事件 / 截断 / 映射缺失 | 「未检测」；total「—」，桶值能报多少报多少 |
| 不适用 | 该节点本次没有模型调用（纯工具 / 纯人工） | 「不适用」 |

**缓存读占比**（不是成本指标）：`cacheReadTokens / (inputTokens + cacheReadTokens + cacheWriteTokens)`；分母为 0 时「未检测」。它只描述 prompt 侧构成，不推导命中率、更不推导节省金额。

#### 3.11.4 一句话验收与未定义项

**一句话验收**：给一份 `session/event` 事件流，能算出唯一覆盖 `7/9`、成功加载次数 `23`、四个桶值与可推导的 total；重放同一 `(turn, step)` 不增加总量，`llm/retry-started` 后的新调用增加总量；缺 `cacheReadTokens`/`cacheWriteTokens` 时 total 显示「未检测」而不是 0。

**当前未定义（如实标注）**：

- skill 覆盖率的目标阈值（比如低于多少算不达标）没有定；本设计只给事实，不给「通过/不通过」的产品线。
- 加载失败是否影响「采纳」：本设计只把成功加载计入分子，失败单列；失败是否算「尝试过」不参与覆盖率。
- run 级覆盖跨 attempt 去重的口径已定，但「只看本轮」是否作为主指标未定。
- 模型价目表 / 计费时点未提供，成本未定义。
- `memberId` 的分配规则未定（当前流程模型的团队成员没有持久 id，见 §3.12.1）。
- 压缩摘要的节点归属在 run 级压缩时未定。

### 3.12 M05 运行数据契约（最小集）

> **这是引擎接入前的契约，不是已完成实现。** 当前代码里只有 §3.13 的「新增字段持久化」落地；运行事件、SSE、指标计算都还没接。下面的事件名是契约占位，引擎实现时必须逐字段映射；映射不上就显示「未检测」。

#### 3.12.1 标识

| 字段 | 类型 | 来源 / 生成规则 | 缺失时 |
|---|---|---|---|
| `runId` | string | `run/start` 生成，整次运行稳定 | 无法关联 → 整次 run 不展示 |
| `attemptId` | int ≥1 | `run/start` 为 1；每次 `edge/reject` 后 +1，所有事件都带 | 归到「未归属」并标未检测 |
| `nodeId` | string | 流程 `nodes[].id` | 事件进 `unattributed` |
| `memberId` | string \| null | 主管 / 子 agent 身份；单 agent 节点为 `null`。当前流程模型的 `team` 成员**没有持久 id**，接入时暂用 `{nodeId}:{index}`（0 = 主管）占位，**这是未完成项** | 节点级合计仍可算，成员级标未知 |
| `seq` | int ≥1 | 每个 `attemptId` 内单调递增；用于去重与续传 | 丢弃该事件并触发全量重同步 |
| `flowRevision` | string | `run/start` 记录流程内容哈希，指标绑定设计版本 | 指标标「流程版本未知」 |
| `startedAt` | string | 节点 / run 开始时间，ISO 8601 带时区偏移（存储 UTC） | 缺 → 耗时「未检测」 |
| `endedAt` | string | 节点 / run 结束时间，口径同上；不得早于 `startedAt` | 缺 / 为负 → 耗时「未检测」 |

#### 3.12.2 事件信封

所有运行事件统一为：

```
{
  runId: string,
  attemptId: number,
  seq: number,
  type: string,
  at: string,            // ISO 8601，带时区偏移；存储用 UTC
  nodeId?: string,
  memberId?: string | null,
  data: object           // 各 type 自己的载荷
}
```

最小事件集：

| 事件 | 载荷 | 用途 |
|---|---|---|
| `run/start` | `flowId`, `flowRevision`, `startedAt` | 建 run，`attemptId=1` |
| `attempt/start` | `cause: 'initial' \| 'rework'`, `reworkFrom`, `reworkTo`, `startedAt` | 返工轮次开始 |
| `node/start` | `nodeId`, `memberId`, `startedAt` | 推到「运行中」 |
| `node/end` | `nodeId`, `memberId`, `status`, `endedAt`, `usageRefs` | 推到 passed / failed / rejected / skipped |
| `edge/reject` | `from`, `to`, `reason`（`attemptId` 已在信封里：本事件属于新 attempt 还是旧 attempt 必须写明） | 触发返工、轮次 +1 |
| `verdict` | `scope: 'acceptance' \| 'test' \| 'spec' \| 'review'`, `targetId`, `status: 'pass' \| 'fail' \| 'na'`, `evidenceUrl`, `decidedBy`, `decidedAt` | 质量判定与证据 |
| `run/end` | `status`, `conclusion`, `endedAt` | 收口，生成一句话结论 |

#### 3.12.3 状态取值与状态来源

| 状态 | 取值 | 推到该态的事件 / 条件 | 备注 |
|---|---|---|---|
| 待执行 | `pending` | 初始状态；或 `attempt/start` 后被返工目标尚未 `node/start` | 不计入「运行中」 |
| 运行中 | `running` | `node/start` | 子 agent 运行归到所属节点 |
| 通过 | `passed` | `node/end` 且 `data.status='passed'`，且该节点必需 `verdict` 均为 pass / 不适用 | 有未检测证据时**不得**显示通过 |
| 被打回 | `rejected` | `edge/reject` 的 `data.from` 节点；`data.to` 节点进入下一 attempt 的 pending 并 `reworkCount+1` | 计数归属按 §4.2 三口径：`↺n`（目标返工数）显示在 `data.to` 节点，`×n`（边触发数）标在对应线上，`data.from` 的源发起数只进检查器/抽屉——**不再**「轮次显示在打回发起节点」 |
| 失败 | `failed` | `node/end` 且 `data.status='failed'`，或任一必需 `verdict` = 不通过 | 质量失败与执行失败都进此态 |
| 跳过 | `skipped` | `node/end` 且 `data.status='skipped'`，或 `attempt/start` 显式标记跳过 | 不计入阶段进度分母 |

> `edge/reject` 事件本身属于**触发它的旧 attempt**；随后 `attempt/start` 携带新 `attemptId` 开始返工，旧 attempt 的结论按 §3.8/§3.10 的失效规则处理。

**归约优先级**（同一节点收到多个事件时，按序取第一个成立）：

```
1. node/end.data.status === 'skipped'            -> skipped
2. node/end.data.status === 'failed'             -> failed
3. 任一必需 verdict.status === '不通过'          -> failed
4. 最近一次 edge/reject 的 data.from === nodeId  -> rejected
5. 最近一次 node/start 且无 node/end             -> running
6. node/end.data.status === 'passed' 且 verdict 齐全 -> passed
7. 其余                                          -> pending
```

#### 3.12.4 时间口径

- `startedAt` / `endedAt` / `decidedAt` 一律 ISO 8601 **带时区偏移**；存储统一 UTC（`...Z`），展示按浏览器本地时区并标注偏移。
- 跨 run 比较、排序、时长计算一律用 UTC；`duration = endedAt − startedAt`，不得为负；为负或缺失 → 时长「未检测」。
- 时钟来源以宿主 / 引擎事件时间为准，不做客户端时钟校正；客户端只负责展示。

#### 3.12.5 用量证据与结论证据

- 每条 usage 必须带 `usageRefs: [{ attemptId, seq }]`（或等价的产物链接），指向 `assistant/message` / `compaction/summary` 事件；**没有 ref 的数字不展示**。
- 结论对象最小字段：

```
{
  verdict: '优' | '良' | '可' | '需返工' | '未完成' | '失败' | '证据不足',
  attemptId: number,
  decidedAt: string,
  evidenceLinks: string[],
  missingEvidence: string[],
  failedEvidence: string[]
}
```

- `evidenceLinks` 必须是稳定可打开的 URI（产物路径 + 内容哈希，或报告链接），不能是聊天文本；打不开的链接按「未检测」。
- `missingEvidence` / `failedEvidence` 用于 §3.9 的结论文案，不允许只给一个颜色。

#### 3.12.6 切页恢复与 SSE 重连去重

| 场景 | 规则 |
|---|---|
| 去重键 | `(attemptId, seq)`；同一键只应用一次。不同 attempt 的 `seq` 各自从 1 开始，不能跨 attempt 比较 |
| SSE 断线重连 | 客户端带 `Last-Event-ID`（格式 `attemptId:seq`）或 `?since=attemptId:seq`；服务端从该序号之后重放。客户端收到 `seq <= 已应用 seq` 直接丢弃 |
| 切页 / 刷新恢复 | 客户端持久化 `{ runId, lastSeqByAttempt, snapshot, flowRevision }`；重新挂载先取快照，再拉 `since` 之后的事件。快照的 `lastSeq` 更新则先替换快照，再补事件 |
| 缺口处理 | 发现 `seq` 不连续（缺少中间序号）→ 触发**全量重同步**，不猜测、不拼接；重同步期间 UI 显示「恢复中」，不显示 0 |
| 运行中切页 | 恢复后先显示「恢复中」，快照 + 重放完成后再显示指标；不得在快照未到时把指标归零 |
| 历史结果 | 每次 attempt 的结果**只追加、不覆盖**；切换 attempt 查看旧结果（含旧结论、旧证据、旧用量），run 级结论默认指向最后一个 attempt，但必须能回看每一轮 |

#### 3.12.7 一句话验收与未实现项

**一句话验收**：断开 SSE 后重连，客户端最终状态与「不中断」时**逐字段一致**：同一 `(attemptId, seq)` 不重复应用，缺口触发全量重同步，旧 attempt 的结论与证据仍可回看；每个指标都能追到 `runId + attemptId + nodeId + memberId + 证据链接`。

**未实现 / 未定义（如实标注）**：

- 运行事件流、SSE 端点、快照接口、指标计算**均未实现**；本节只是契约。
- `memberId` 的稳定分配未定：当前 `team` 成员没有持久 id，`{nodeId}:{index}` 只是占位；成员顺序变化会导致身份变化。
- 事件命名是提案，引擎落地时若与宿主 `session/event` 冲突，以宿主事件为准并做映射层。
- 跨 run 的历史保留策略（保留多少个 run / 多久）未定；本节只要求 run 内 attempt 全保留。
- 时钟偏移、跨 attempt 飞行中调用的归属、压缩摘要的节点归属，均标为待验证。

### 3.13 新增字段的持久化：已知字段显式处理 + 未知字段进 extras

流程模型的新增字段有两条路，不能靠「白名单外静默丢弃」：

1. **需要语义的字段** → 显式加入 `normalizeFlow` 的已知字段，补校验、默认值、迁移；这是唯一能让字段参与运行 / 指标计算的路径。
2. **暂时只需要往返保存的字段** → 进 `extras`：节点、边、团队成员各有一个 `extras`，保存 / 读回 / 再保存不丢。

**边界（与 `src/model.js` 实现一致）**：

| 限制 | 值 | 超限行为 |
|---|---|---|
| 键数上限 | 16（`LIMITS.extrasKeys`） | 超出的键丢弃 |
| 单条字符串上限 | 256 字符（`LIMITS.extrasTextLen`） | 顶层字符串截断；嵌套字符串同样按此截断 |
| 序列化总长上限 | 2048 字符（`LIMITS.extrasBytes`） | 放不下的键丢弃，不截断已知字段 |
| 嵌套深度 | 3 层 | 更深的值整体丢弃 |
| 数组 / 对象元素 | 最多 16 个 | 超出部分丢弃 |
| 值类型 | 仅 JSON 可序列化的值：字符串 / 有限数字 / 布尔 / null / 普通对象 / 数组（数组和对象里也只能放这些值） | 函数、`undefined`、`NaN`、`Infinity`、BigInt、Symbol、类实例、循环引用、含坏成员的复合值整体丢弃 |
| 失败行为 | 任何越界 / 异常只丢弃，不抛错 | `normalizeFlow` 永不因 extras 抛错 |

- 没有未知字段时**不挂** `extras`，既有节点 / 边形状不变。
- 往返稳定：`normalizeFlow(normalizeFlow(x))` 的 `extras` 与第一次一致（已被 `test/model.test.mjs` 覆盖）。
- **`extras` 是兼容通道，不是 schema**：它不参与校验、不触发运行、不做迁移；不要把需要语义的字段长期塞在 extras 里。
- **字段晋升**：当一个字段从「未知」变成「已知」时，必须一次性把旧 `extras.foo` 迁移到 `foo`；因为 `normalizeFlow` 对已知字段优先，旧 extras 里的同名值不会自动被读取。当前没有迁移脚本，标为未完成项。
- 实现位置：`src/model.js` 的 `normalizeFlow` / `collectExtras` / `withExtras`；测试位置：`test/model.test.mjs` 的「未知字段进 extras」「extras 有界」「extras 坏输入」「没有未知字段时不挂 extras」四组。

| 失败 | 1.5px `state-error-primary` | `bg-layer-2` | 定格耗时 + ⚠ | 节点标题变 error |
| 跳过 | 1px `border-l2` 虚线 | 透明 | 「—」 | 整卡 opacity 0.5，标题划线 |

### 4.2 打回计数：三个口径，各标各的位置

> 2026-11-06 裁决（总案 §6 C11）。旧稿的「目标累计返工 + 线上刻度」与「轮次标在被打回的源头节点、不在线上标数字」两种说法**都作废**。三个口径**互不替代**，都由运行契约（§3.12）的 `attemptId` 派生，都不含「预置的潜在路径」（设计态虚线打回边只表示结构，不计数）。

**共同数据源**：`attemptId`（§3.12.1）——`run/start` 为 1，每次 `edge/reject` 后 +1，所有事件都带；事件信封见 §3.12.2。所有计数只读运行事件，不读图结构。

| 口径 | 定义 | 标注位置 | 数据来源 | 去重规则 |
|---|---|---|---|---|
| **① 边触发数** | 这条打回边被触发的次数 | **在线上**：航道标签 chip 左侧的 `×n` 小刻度（沿用 03 §3.3：每轮一根 4×1.5px 竖棒，最多 5 根，超出写「5+」） | `edge/reject` 事件（`data.from`、`data.to`、信封 `attemptId`） | 同一 `(from, to, attemptId)` 只计一次；重连/重放/重渲染不重复累加；n=0 不画刻度、不显示 `×0` |
| **② 目标返工数** | 目标节点因收到打回而**重跑**的次数 | **目标节点的 `↺n` 角标**（n=0 不显示） | 目标节点侧：该节点每一次「因打回进入 reworking」的 `attemptId`（`edge/reject` 的 `data.to` = 该节点） | 同一 `attemptId` 只计一次；一个节点被多条边打回时，按**节点侧 attempt 序列**合并去重（不按边相加） |
| **③ 源发起数** | 源节点**发起**打回的总次数 | **只进检查器与底部抽屉**（检查器「打回」区 / 底部抽屉明细），**不标在节点卡上** | 源节点侧：该节点每一次「判定下游不通过并触发打回」的 `attemptId`（`edge/reject` 的 `data.from` = 该节点） | 同一 `attemptId` 只计一次；同一轮向多个下游发起，按**源节点 attempt** 计 1 次（不按目标数累加） |

**读法（可独立复算）**：

- 一条边看到 `×3` = 这条边触发过 3 次；目标卡 `↺2` = 目标只重跑了 2 次，差额来自「该次打回未导致目标重跑」（如超限阻断）；源节点卡上**永远没有**打回数字，发起了几次去检查器/抽屉看（③）。
- 三者不要求相等：`Σ边触发数` 可以 ≥ `Σ目标返工数`；`Σ源发起数` 与 `Σ边触发数` 的差来自「一轮打回向多个下游」。
- 卡片 tag 行只放 ② 的 `↺n`；① 是线元素、③ 是面板元素——三者不会抢同一位置。
- **旧表述一律作废**：「n = attemptId − 1，标在源头节点」、「轮次标在被打回的源头节点」、「目标累计返工 + 线上刻度互为印证」。

**每一轮的通过必须能区分**：节点 / 验收条目 / 规范 / 缺陷的结论都带 `attemptId`；检查器显示「第 2 轮通过」「第 1 轮通过（保留）」，汇总行写「本轮通过 5 / 保留 2 / 未通过 1」。返工后旧结论的失效边界见 §3.8、§3.10、§3.11。

**打回连线**用 `state-warn`，线粗 1.5px，回环方向从下游节点下方走「专用打回航道」（航道几何归 03 §3.1；本模块只负责**数字**）。

### 4.3 完成后的复盘视图

run 结束，抽屉自动展开到 200px，收起条主摘要定格、节点描边定格。用户最想先看的 3 个数字（按序）：

| 序 | 数字 | 理由 |
|---|---|---|
| 1 | 验收通过率（副显示阶段进度，或失败 / 未完成） | 唯一能立即回答「用户要的东西做完了吗、要不要行动」的数字；阶段进度只回答「流程走到哪」 |
| 2 | P0 未解决数 + 意见采纳率 + 未检测项数 | 「质量行不行」的代理；P0 是发布阻塞，采纳率说明审查是否真起了作用，未检测项说明这个结论有没有证据 |
| 3 | 总 token / 总耗时 | 成本与效率；前两项没问题时它才有意义 |

**「这次 run 好不好」一句话结论自动生成规则**：先按 §3.9.2 算必要质量证据状态，再按 §3.9.3 的判定表逐行判定。这里只保留摘要，**判定表以 §3.9.3 为准**：

| 序 | 判定条件（自上而下，第一个满足的生效） | 结论文案 | 颜色 |
|---|---|---|---|
| 1 | 任一阶段失败 | 「失败：{阶段名} 未通过」 | `state-error-primary` |
| 2 | 阶段进度 <100% 或 验收通过率 <100% | 「未完成：验收 {x}/{y}，阶段 {a}/{b}」 | `state-warn` |
| 3 | P0 未解决 >0 | 「需返工：{n} 个 P0 未解决」 | `state-warn` |
| 4 | 任一必要证据 = 不通过 | 「需返工：{失败项及实测值}」 | `state-warn` |
| 5 | 任一必要证据 = 未检测 | 「证据不足：{未检测项}，不能判定为通过」 | `state-warn` |
| 6 | 全部证据通过 + P1 未解决 =0 + 返工 =0 | 「优：首轮通过，质量证据齐全」 | `state-success` |
| 7 | 全部证据通过 + P1 未解决 =0 + 返工 1–2 | 「良：返工 {n} 轮后达标」 | `state-success` |
| 8 | 全部证据通过 +（返工 >2 或 P1 未解决 >0） | 「可：返工 {n} 轮、遗留 {m} 个 P1，建议复盘」 | `state-warn` |
| 9 | 其余（数据自相矛盾） | 「可：证据状态不一致，请复核」 | `state-warn` |

> 规则是确定性的：阈值（返工 0/1–2/>2、采纳率 60%、P0=0、P1=0、测试 100%、硬性要求证据齐全）写死在判定表里，不交给模型自由措辞，保证同一 run 每次给同一结论。**旧表「完成度 100% 且 返工 ≤1 → 优：一次通过」已废止**：返工 1 次不是一次通过，且旧表在采纳率 0% / 测试 50% 时仍会输出「良」，是 §3.9.4 反例要修掉的假阳性。

> 阈值来源：60% 沿用旧表、返工 ≤2 是产品选择，二者都**没有样本校准**；P1=0 才绿灯是从严政策。它们不是统计结论，标为待校准（见 §3.9.6）。

| 点收起条（主摘要、结论 pill 或箭头） | 收起态 ↔ 展开态 toggle |
| 拖拽收起条上边缘 | 高度 120–360px 连续调节，松开吸附到 200 / 320px |
| 键盘 `Ctrl/Cmd + \` | toggle 抽屉 |
| 开始运行 | 自动展开到 200px |
| 运行结束（成功或失败） | 自动展开到 200px，停留 2s 展示一句话结论；之后不自动收起 |
| 用户手动收起 | 收起，直到下次运行再自动展开 |

### 5.3 实时性（任务书 D）

- **刷新频率 1Hz**：运行中的数字 1 秒更新一次（后端 SSE 推送优先，前端兜底 1s 轮询）。理由：一个阶段跑几十秒到几分钟，1Hz 足够感知「还在动」；更高频数字会抖、浏览器重绘成本高、30 节点会卡。
- **数字不刺眼**：① tabular-nums 固定宽度，只变值不移位；② 数值变化做 200ms 淡入淡出 + 上下 2px 位移，不是瞬间替换；③ 只有变化的数字动，静止数字不动；④ 变化合并到同一次 `requestAnimationFrame` 重绘；⑤ `prefers-reduced-motion` 时关掉过渡动画、直接替换。
- **长跑（>10 分钟）体现「还在动」**：① 耗时角标持续 +1s 本身就是最强的活着信号；② 运行中节点的描边是沿轮廓流动的虚线（流动方向=数据流），比数字更能一眼看出「在跑」；③ 收起条主摘要的验收通过率随推进变化，阶段进度（如「开发 · 3/5 子任务」）在展开 200px 明细里更新；④ 卡住判定：节点耗时超过该阶段历史 P90×1.5 时，描边从流动绿变呼吸橙 + tooltip「可能卡住」。

### 5.4 空状态 / 错误态 / 悬停态汇总

| 状态 | 触发 | 表现 |
|---|---|---|
| 空数据态（未运行） | 从未运行 | 抽屉收起，收起条显示「尚未运行」；展开内容区显示「尚未运行，点「运行」开始」，不显示占位数字（0 是有意义数字，不与空混淆） |
| 错误态（指标获取失败） | 后端指标源断了 | 收起条主摘要位置显示「—」+ 右上角一个 error 小图标 + tooltip「指标获取中断，重试中」 |
| 异常态（token 异常高） | 单节点 token 超历史 P90×1.5 | 该节点卡片 token 构成条右端加 error 色警示段 + 检查器 token 主值变 error + ⚠ |
| 悬停态 | 见 5.1 | 150ms 延迟浮现，避免扫过即弹 |

## 六、反例（不建议做的事）

1. **在画布上画 token 热力图（节点卡片背景随 token 量变深/变色）**：卡片背景已被「运行状态色」占用（运行中绿 / 失败红 / 打回橙），再叠 token 热度会双重编码打架；30 节点时整张图糊成一团红绿。token 是事后看的指标，放抽屉即可。
2. **把 6 个指标全塞进节点卡片角标**：违反「最多 2 个自由数字」的约束，30 节点时挤爆卡片高度、角标换行破坏对齐，扫描从瞥一眼退化成读一遍。
3. **用弹窗展示运行日志或指标**：任务书 §2 明说本面板不是弹窗；弹窗遮挡画布，而过程监督需要「边看图上卡在哪、边看指标」，弹窗把它拆成模态，逼用户在两者间来回开关。
4. **为指标单独做一整个「指标 Tab」把画布切走**：让「图和指标不能同时看」，直接违反「运行时要在图上看到进度」的核心需求，也违反任务书 §3.3「同一张图，设计时看结构、运行时看进度」。
5. **数字变化用滚动式数字或大幅动画**：滚动数字/闪烁刺眼，30 节点同时动会引发注意力与性能双灾难；正确的「动」是 1Hz + 200ms 克制过渡 + tabular-nums。
6. **把「已采纳」当成「已修复」、把「已修复」当成「复验通过」**：这三个状态回答的是不同问题；混用会让 P0 在没复验时就消失，直接制造假绿灯（§3.10.4）。
7. **把缓存读/写说成「无成本」「免费复用」**：没有计费证据就不做成本承诺；只报四个互斥桶值（§3.11.3）。
8. **用 0 或 100% 填补「未检测」**：没跑测试不是 0 分、也不是通过；缺证据时结论必须写「未检测 / 证据不足」，不能给绿灯（§3.9）。
