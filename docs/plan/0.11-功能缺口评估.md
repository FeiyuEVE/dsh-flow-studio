## 8. 模型多样性：节点与成员分别换模型（用户 2026-11-07 提出）

**现状（已核）**：

- **节点级已经支持**：检查器「模型覆盖」有 provider + model 两个输入（`src/client/inspector.js:426-446`），引擎侧由 0.10 的 `resolveModelRoute` 统一解析，半对会 503。
- **成员级不支持**：`src/model.js:465-471` 的 team 归一化只保留 `name/role/task`，没有 `model`；`member.model` 是**观测值**（从子会话 `session.header.model` 读，`src/engine.js:6780-6783`），不是配置项。
- 成员模型实际由宿主插件 `subagent-child-model` 按「父供应商 → 子模型」全局映射决定（`~/.dsh/profiles/web/cordis.patch.yml:606-617`），粒度是供应商，落不到节点或成员。

**建议**（P1，0.12）：

1. `team[i]` 增加可选 `model`（与 `provider` 成对，沿用节点级同一套校验），归一化进 `MEMBER_KNOWN_FIELDS`。
2. 引擎把「成员模型映射表」写进节点提示词（主管调 `subagent` 时按表点名）；`node/start` / `member/start` / `summary.members` 记录实际模型（`member.model` 字段已能承接）。
3. 默认策略：主管用节点模型，成员默认跟随；只有「需要独立视角」的阶段（需求裁决、测试取证、代码审查）才给成员配异源模型。
4. 语义边界：这是**提示词约束**不是硬约束——spawn 由主管自己发起，插件只能要求并按回执核对；要做硬约束得让引擎自己 spawn 成员（更大改动，暂不排）。

**代价与注意**：异源模型会拉长团队等待（等最慢的那个）、增加合并成本；同一节点内 attempt 重跑必须沿用同一模型，否则历史不可比。**最有价值的一条是「审查节点与开发节点异源」**——同模型自查对「方案本身错了」这类问题基本无感。

**验收**：同一 run 里开发与审查节点的实际 model 不同且能在 run 详情看到；把审查配成异源模型时 `node/start.data` 记录实际 provider/model；成员回执里各自模型可见。

## 9. 运行期发现的补充缺口（真机实测）

> 以下四条来自 0.11 真机会话（2026-11-07 ~ 2026-11-08），编号沿用运行期清单的 G-A ~ G-D；**均不在 0.11 范围内**，记为 0.12 候选。

### G-A（P0）无人值守的节点会话会卡在审批上，没有任何超时或上报

**现象**（真机）：2026-11-07 22:11 哨兵巡检发现 run `r-mw6gcgbv-n5b3` 的 `n_req` 节点 **21 分钟零事件、零模型调用**。容器会话日志 seq 164 是：

```
{"type":"approval/asked","toolName":"bash","reason":"escalate sandbox to danger-full-access:
 基线测试在创建固定夹具目录 /root/tmp 时被文件权限限制中断…"}
```

之后引擎每 10 分钟往会话里投一条「节点自审闹钟」（seq 165/167/168），模型一次都没回——因为它的 turn 卡在审批上。**run.json 里看不到任何「正在等审批」的状态**，指标只显示 `running` + `live=n_req`。

**为什么是真缺口**（不是环境问题）：

- 节点会话由 `agents.create` 创建，权限预设/审批策略取宿主默认（`dsh-base` 的 `approval.policy = ask`），流程模型里**没有任何字段**能指定节点用哪个预设；
- 引擎侧也没有「审批未决超过 N 秒 → 收口/失败/上报」的处理，`nodeTimeoutMs`（本轮设的 45 分钟）是唯一的兜底，等于一次卡死烧掉 45 分钟；
- 面板 / run.json / 事件流都不暴露「在等审批」，人只能靠翻会话日志里挖 `approval/asked`。

**建议修法**（0.12）：

1. 流程模型加 `node.permissionPreset`（或 `extras.permissionPreset`），`agents.create/resume` 时传下去；容器/CI 场景显式给 `danger-full-access`；
2. 引擎监听会话的 `approval/asked` 事件：超过阈值（如 120s）无 `approval/decided` 就写一条 `node/notice` 事件并在 run.json 上标 `awaitingApproval`，同时支持可配置的 `approvalTimeout` 自动拒绝；
3. 面板节点卡与 run 详情页显示「等待审批中」+ 一句话原因。

**临时绕过**（本轮已做）：容器内 dsh 以 `DSH_PERMISSION_MODE=danger-full-access` 启动 —— `dsh-base` 里这一条同时把 `sandbox-policy.mode` 设成 danger-full-access、把 `approval.policy` 设成 `never`（`cordis.patch.yml:246` 与 `:262`），审批请求直接被拒而不是挂起，agent 会自己改路。

**验收口径**：在 `approval.policy = ask` 的宿主上触发一次节点审批，超阈值后 run.json 出现 `awaitingApproval`（或按 `approvalTimeout` 自动拒绝后节点自行改路），节点卡与 run 详情能直接看到「等待审批中」与原因；不再出现「21 分钟零事件、只能翻会话日志」。

### G-B（P2）续跑 run 的 tokenTotal 从 0 重新计数，成本口径断裂

`restart` 新建续跑 run（`r-mw6hhsd7-d9to`），旧 run 的 **2,697,887 tokens** 不继承，钱包/成本要跨两个 run 手工相加。

**建议修法**（0.12）：run.json 的 `restart` 块带上 `fromRunTokenTotal`，面板汇总时一并显示（旧 run 总量 + 本 run 增量）。

**验收口径**：续跑 run 的详情/汇总一次给出累计 token = `fromRunTokenTotal` + 本 run `tokenTotal`，不需要人工跨 run 相加。

### G-C（P1）打回上限触发后，整条 run 直接判 failed，没有「再给一轮」或「交人工后继续」

**现象**（真机）：2026-11-08 02:13Z，run `r-mw6nwxqb-0qt4` 收尾于
`run/end.status=failed, reason="超打回上限：目标「开发」已重跑 2 次（上限 2）", failedNodeId=n_dev`。
n_test 是**正常判定 reject**（944 组测试全绿，但仍有两条实质缺口：fencing 原子性、R5 篡改断言），dev 也正常返工了两轮——引擎按规则收口，**没有 bug**。问题是**收口之后没有出路**：

- 唯一的续跑方式是改流程 JSON 的 `node.maxRounds` 再 `POST /runs/<id>/restart`，等于让用户去改设计器里的字段才能「再给一轮」；
- 「交人工处理」在 run.json 里没有任何落点（只有 failed + reason 文本），面板看不出一轮人应该怎么做；
- 打回上限是**节点**属性，但把整条 run 判死是**run**级后果——粒度不匹配：一个节点到上限，其它节点（需求/方案/结构）的合格产物被一起作废，只能靠 restart 继承会话重来。

**建议修法**（0.12）：

1. 打回上限触发时给两种收口：`failed`（默认，现状）或 `paused`（新终态：run 挂起、保留租约外的全部现场，面板出现「再给一轮 / 放宽 N / 人工接管 / 放弃」四个动作）；
2. `POST /runs/<id>/resume-round`：只把该节点的 `rounds` 计数 +1 并按原会话继续，**不改流程 JSON**；
3. run.json 记 `blockedOn: {nodeId, reason, rounds, maxRounds}`，`flow_watch` 在 recommended 里提示「需要人决定是否再给一轮」。

**验收口径**：`n_dev` 到上限时 run 可停在 `paused` 并给出四个动作；`resume-round` 只增该节点 rounds、沿用原会话、流程 JSON 不变；`flow_watch` 的 recommended 出现对应提示。

### G-D（P1）结论里的派生数字不自洽，会把整条 run 判死（而不是归一化或只重问这一项）

**现象**（真机）：2026-11-08 02:48Z，run `r-mw6q811p-9mg8` 在**倒数第二个节点** n_review 收尾于
`run/end.status=failed, reason="tests 计数不自洽：passed(944) + failed(0) + skipped(3) !== executed(944)"`，`failedNodeId=n_review`。
审查模型给的结论是合法的 reject（F1–F7 七条实质问题），只因 `tests` 里 `executed` 与三项之和对不上（差了 3 条 skipped），整个结论被判「结构不合格」→ 重试一次 → 失败 → 2 小时、123M tokens 的 run 在最后一环被记账错误收掉。

**为什么是缺口**（不是模型单方面错）：

- `executed` 是**派生字段**（= passed+failed+skipped），和 passed/failed/skipped 重复表达同一事实；要求模型两边都写对、且引擎只做严格相等校验，是把「冗余」当「防伪」；
- 防伪真正需要的是「数字有没有报告文件支撑」（`test/report.reportRef` + provenance），而不是三个数和等于第四个数；
- 惩罚粒度错：一个字段写错，代价是整条 run 的终态，而不是「这一项不合格、请重报」。

**建议修法**（0.12）：

1. `executed` 允许缺省；给了就以 `passed+failed+skipped` **归一化**并记一条 `extra.normalized: ['tests.executed']`；
2. 真正要硬校验的是 `reportRef` 存在性 + sha256 + provenance（0.11 已经在做）；计数不一致降为 `warnings`；
