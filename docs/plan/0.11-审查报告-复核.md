## 1. 总判定

**REJECT**

一句话理由：P0 的**引擎调用面**（F1/F2/F6）确实闭合、新增用例在旧实现上可红；但 F4 的**判定层**仍给「无来源 legacy 证据」绿灯（审查报告 F4 引用的 `state=pass` 症状只修掉了 `authoritativePassed=1` 那一半），F3 对二进制/非法 UTF-8 报告仍把原始凭据原样复制到公开副本、`--token <value>` 形态仍进公开摘要/输出尾，F1 的兼容分支仍可被同 `pid@host` 的旧调用方续租/释放新 owner 租约。按「不引入错误授信 / 泄密」的口径，不能放行。

需要说明的是：F2/F5/F6/F7 本节点**未发现可复现缺口**，F1 的生产引擎路径也已被 ownerId+epoch 与跨进程锁闭合。返工范围是窄的（F4 的状态闸门、F3 的非文本报告策略、F1 的回退分支），不是推倒重来。

### F1 细节

已修的部分是真实的：`claimLease`、`renewLease`、`releaseLease` 都改成 `withLock(loc.id) → withMetaLock(loc)`（[runstore.js:1987](../../src/runstore.js#L1987)、[2040](../../src/runstore.js#L2040)、[2083](../../src/runstore.js#L2083)），claim 先推进 `run.json.execution`（epoch+1、随机 ownerId）再发布 `lock.json`（[runstore.js:2000](../../src/runstore.js#L2000)–[2016](../../src/runstore.js#L2016)）；lock.json 也带 epoch（[runstore.js:1573](../../src/runstore.js#L1573)–[1585](../../src/runstore.js#L1585)、[2005](../../src/runstore.js#L2005)）。`renewLease` 在锁内两次读 lease 并核对 `ownerId`/`epoch`/`acquiredAt`（[runstore.js:2054](../../src/runstore.js#L2054)–[2058](../../src/runstore.js#L2058)）。

测试方面，`F1-①` 同 pid@host 异 ownerId、`F1-②` claim 半途崩溃、`F1-③` 持 meta.lock 期间子进程 renew/release 必须等待、`F1-④` 真子进程接管后旧 renew 409 且旧业务写 0 条，四组在 HEAD 全绿（`npm test` exit 0）；把 runstore.js 换回 `29db62b` 后四组全红，红点正是「旧 owner（ownerId 不符）不得续租新 owner 的租约」「租约身份与持久 execution 不一致时…」等断言。这说明测试确实咬住了修复，不是空转。

但 `leaseHeldBy` 的兼容分支没有身份证明：不传 `ownerId` 时只比对调用方的 `pid`/`host`，再要求 `lease.ownerId === execution.ownerId` 自洽（[runstore.js:1650](../../src/runstore.js#L1650)–[1665](../../src/runstore.js#L1665)）——这两个值在「新 owner 已接管」后都是新 owner 的，所以旧调用方照样通过。探针（`/tmp/probe-f1.mjs`，见 §3 N2）实测：接管后 `renewLease(..., {pid,host})` **成功**并刷新了新 owner 的心跳，`releaseLease(..., {pid,host})` 返回 `true` 删掉了新 owner 的租约。另外 [engine.js:4451](../../src/engine.js#L4451) 在 start 失败收尾时仍然 `releaseLease(this.runsRoot, runId)` **不带 ownerId**（同文件 [4777](../../src/engine.js#L4777)、[5263](../../src/engine.js#L5263)、[5830](../../src/engine.js#L5830) 都带了）。所以：**引擎正常路径闭合，兼容/回退路径未闭合**。

### F2 细节

`settleInstance` 在异步清理前用 `executionMatchesGeneration(meta.execution, generation)` 核对持久世代（[runtime.js:1339](../../src/runtime.js#L1339)–[1344](../../src/runtime.js#L1344)），不匹配就只摘自己的资源；写 `supervision.enabled=false` 时再带 `ownerId+epoch` fence（[runtime.js:1352](../../src/runtime.js#L1352)–[1354](../../src/runtime.js#L1354)），被 409/`LEASE_FENCED` 拒绝就保留接管者登记。Engine 侧失权分支本来就不释放接管者的租约（[engine.js:5247](../../src/engine.js#L5247)–[5254](../../src/engine.js#L5254)），`_notifySettled` 仍会通知 runtime（[engine.js:5274](../../src/engine.js#L5274)），这正是 F2 描述的路径；现在由 runtime 的世代核对兜住。

测试 `F2：旧实例失权后 settle 不能关掉接管者的 supervision`（[runtime.test.mjs:2233](../../test/runtime.test.mjs#L2233)）断言：旧实例 settle 后 `runtime.supervision.status().enabled` 仍为 `true`、`run.json.supervision.wakerSessionId` 保留、下一轮 tick 真的发出 1 条 followup。HEAD 绿；旧 runtime 红在「旧实例 settle 不能同步摘掉接管者的调度登记」。判定：**已闭合**。

残余（N5）：`executionMatchesGeneration` 对缺失字段返回 `true`（[runtime.js:196](../../src/runtime.js#L196)–[208](../../src/runtime.js#L208)），且 `meta.execution` 缺失时 `fence` 退化为 `{}`（[runtime.js:1352](../../src/runtime.js#L1352) + [generationFence:211](../../src/runtime.js#L211)）。对没有 epoch/ownerId 的旧 Engine/自定义 Engine，这一步等于无 fence。生产 Engine 在 `startReserved` 里于 `engine.start()` 返回后立刻抓 lease（[runtime.js:1531](../../src/runtime.js#L1531)–[1536](../../src/runtime.js#L1536)），正常长跑能被覆盖；这是低可达性的兜底缺口，不是本次的主要阻断点。

### F3 细节

顺序是对的，没有「拿源文件 hash 冒充最终副本」：`redactReportCopy` 先把独立 buffer 解码、脱敏、重新编码，再对**最终字节**算 sha256/长度（[host-check.js:169](../../src/host-check.js#L169)–[183](../../src/host-check.js#L183)）；`reportSha256/reportBytes/reportByteLength` 都来自 `publicReport`（[host-check.js:782](../../src/host-check.js#L782)–[788](../../src/host-check.js#L788)）。Engine 把这同一份 `reportBytes` 写成公开副本（[engine.js:6764](../../src/engine.js#L6764)–[6779](../../src/engine.js#L6779)），验证器再重读该副本算 sha256 与私有登记的 `record.reportSha256` 比对（[runstore.js:2243](../../src/runstore.js#L2243)–[2253](../../src/runstore.js#L2253)）。`F3：宿主检查的 commandSummary 与报告副本脱敏，reportSha256 绑定最终副本`（[engine.test.mjs:5903](../../test/engine.test.mjs#L5903)）还断言了 `record.reportSha256 === sha256(落盘文件)` 且源工作区报告未被改写。这三处一致，没有顺序/口径 bug。

问题在覆盖面：`redactReportCopy` 对无法无损 UTF-8 往返的 buffer **直接原样 finalize**（[host-check.js:177](../../src/host-check.js#L177)–[179](../../src/host-check.js#L179)），二进制/非法 UTF-8 报告里的 canary 会原样进入公开副本；探针实测 `state=pass`、副本含 `canary-bin-2`（§3 N3）。此外共享脱敏规则只认 `Bearer` / `sk-` / `key:value|key=value`（[engine.js:417](../../src/engine.js#L417)–[445](../../src/engine.js#L445)），`--token <value>` 这种空格形态既不进 `commandSummary` 也不进 `outputTail` 的替换。文本 `token=canary` 路径确实闭合（[host-check.test.mjs:124](../../test/host-check.test.mjs#L124) 与旧实现红都验证过），所以判**部分闭合**。

### F4 细节

计数层确实改了：`classifyEvidenceAuthority` 把无 `extra` 归 `legacy`（[runlog.js:1511](../../src/runlog.js#L1511)–[1527](../../src/runlog.js#L1527)）；三个指标只在 `source === 'host'` 时加 `authoritativePassed`，`legacy` 单列 `legacyPassed`（[runlog.js:1691](../../src/runlog.js#L1691)–[1692](../../src/runlog.js#L1692)、[1866](../../src/runlog.js#L1866)、[2045](../../src/runlog.js#L2045)）；`computeQuality` 用 `unverifiedMix = claimedPassed > 0` 把 host+claimed 混合降为 `unknown`（[runlog.js:2511](../../src/runlog.js#L2511)、[2563](../../src/runlog.js#L2563)–[2566](../../src/runlog.js#L2566)）。`F4 legacy 无来源 pass` 与 `F4 host + claimed 混合` 两组在 HEAD 绿，旧 runlog 红（连同 4 组 R4/R6 断言），测试是有效的。

但审查报告 F4 的原始探针写的是「`state=pass, authoritativePassed=1`」——现在只修掉了后者。`computeQuality` 的 `pass` 分支（[runlog.js:2553](../../src/runlog.js#L2553)–[2554](../../src/runlog.js#L2554)）不看 `authoritativePassed`/`authorityCoverage`；legacy 又恰好不被 `claimedPassed` 计数，于是 `legacyPassed=3, authoritativePassed=0, authorityCoverage=0` 仍能 `state=pass, label='优：首轮通过'`。独立探针 `/tmp/probe-f4b.mjs` 输出：

```
summary.quality.state = pass | label = 优：首轮通过 | authoritativePassed = 0 | legacyPassed = 3
```

而客户端结论 pill 只认 `quality.state`，`pass → tone:'success'`（[logdrawer.js:1566](../../src/client/logdrawer.js#L1566)–[1600](../../src/client/logdrawer.js#L1600)，关键行 [1598](../../src/client/logdrawer.js#L1598)），audit 也直接转述 `quality.state`（[audit.js:746](../../src/audit.js#L746)）。也就是说：**一条没有任何来源的假 report/acceptance，会在 UI 上显示绿色「优：首轮通过」，旁边同时写着权威覆盖 0%**。这正是审查报告说的「无来源…仍能错误授信」。

更反直觉的是新/旧口径倒挂：同一份证据内容、同样 1/3 覆盖，把 `extra.provenance` 标成 `model-claim` 的新 run 得到 `state=unknown`，而无 `extra` 的 legacy 旧 run 得到 `state=pass`（探针 `/tmp/probe-f4c.mjs`，见 §3 N1）。代码注释说「纯 legacy 旧 run 保留旧版 quality 判定以兼容历史」（[runlog.js:2507](../../src/runlog.js#L2507)–[2511](../../src/runlog.js#L2511)），但[方案 §8](0.11-方案.md) 的判定表明确写的是「旧无来源报告… claimed/unknown 不绿」。现有测试 [runlog.test.mjs:710](../../test/runlog.test.mjs#L710)–[712](../../test/runlog.test.mjs#L712) 也仍断言 legacy 全量 `state=pass`，等于把这个偏差固化进了基线。判**部分闭合**。

### F6 细节

`finalizeEpoch` 把「扫 loss key → 判终态 → 判权 → append」全部放进同一个 `withLock + withMetaLock` 事务（[runstore.js:2158](../../src/runstore.js#L2158)–[2206](../../src/runstore.js#L2206)，扫描在 [2161](../../src/runstore.js#L2161)，判权带 `requireActive: true` 在 [2173](../../src/runstore.js#L2173)–[2177](../../src/runstore.js#L2177)），追加走 `appendEventsInLock`（[2197](../../src/runstore.js#L2197)），后者明确要求调用方已持锁、不再二次抢锁（[runstore.js:3757](../../src/runstore.js#L3757)–[3772](../../src/runstore.js#L3772)）。全文件只有 `appendEvents`（[3754](../../src/runstore.js#L3754)）和 `finalizeEpoch`（[2197](../../src/runstore.js#L2197)）两个调用点。两组测试（并发同 loss key 只落一条、接管后只写 instance 事实且不改新 owner）HEAD 绿，旧 runstore 红（`实际 2 条`）。判定：**已闭合**。

针对你点名的死锁/自锁，我查了：所有持锁组合都是 `withLock(runId) → withMetaLock(dir)`，没有反向的「持 meta.lock 再抢 withLock」；`withLock` 不会被同一调用链重入（`appendEventsInLock` 已拆出）；跨进程锁等待有 15s 上限、超时 409（[runstore.js:1834](../../src/runstore.js#L1834)–[1841](../../src/runstore.js#L1841)），不会无限互等。`guard` 回调只在测试里注入，产品代码没有。**未发现死锁或自锁**。但临界区变长了（扫全量事件）与 10s 陈旧锁 TTL 的配合见 N4。

### F7 细节

`dispose()` 对每个活跃 Engine 先 `engine.stop/abort` 拿到终止 promise，再把 `termination.then(() => releaseSlot())` 挂上去（[runtime.js:2016](../../src/runtime.js#L2016)–[2023](../../src/runtime.js#L2023)），`releaseSlot` 是启动时按本次 run 捕获的包装（[1967](../../src/runtime.js#L1967)–[1969](../../src/runtime.js#L1969)），不会被之后同 runId 的新 run 误用。超时只告警、不还槽；无终止信号的桩才按已终止处理（[2024](../../src/runtime.js#L2024)–[2027](../../src/runtime.js#L2027)）。两组测试（不响应 abort 的 Engine 仍占额度、N+1 被 429；迟到终止后还槽且新 run 可启动）HEAD 绿，旧 runtime 红。判定：**已闭合**。

## 3. 新发现

### N1（阻断）F4 判定层：legacy 全绿、新 run 反而 unknown

**现象**：`authoritativePassed=0`、`authorityCoverage=0` 的 legacy 事件集，`computeQuality` 仍返回 `state=pass / label=优：首轮通过`；客户端把它渲染成绿色 pill。与此同时，同样覆盖度但带 `provenance:'model-claim'` 的新 run 被 `unverifiedMix` 降成 `unknown`。方向正好相反。

**最小复现**（容器内，`/tmp/probe-f4c.mjs`）：

```bash
docker exec dsh-flow-dev bash -lc 'cd /testbed/workspace/dsh-flow-studio && node /tmp/probe-f4c.mjs'
```

输出（节选）：

```json
{
  "model_claim_run": { "state": "unknown", "label": "证据不足：2 条 claimed 通过未获宿主独立验证，不能判定为通过", "claimed": 2, "authoritative": 1, "total": 3, "coverage": 0.3333333333333333 },
  "legacy_run": { "state": "pass", "label": "优：首轮通过", "claimed": 0, "authoritative": 1, "legacyPassed": 2, "total": 3, "coverage": 0.3333333333333333 }
}
```

**影响面**：0.10 历史 run 打开即显示绿色「优：首轮通过」，而权威覆盖是 0%——正是审查报告 F4 要消灭的错误授信；同时如果「新 run 是否应该有可能变绿」的答案是肯定的（方案 §8 的 `authoritative peer` 行），当前实现没有任何路径能让 acceptance/tests 成为权威（引擎对它们一律写 `provenance:'model-claim'`，[engine.js:6902](../../src/engine.js#L6902)/[6926](../../src/engine.js#L6926)/[6951](../../src/engine.js#L6951)），绿色对新 run 不可达。

**建议修法**：在 `computeQuality` 的 `pass` 分支前加一道状态闸门——`authoritativePassed < authoritativeTotal && claimedPassed === 0 && legacyPassed > 0` 时降为 `unknown`（标签写「历史来源未知」）；或把 legacy 在**判定层**等价于 claimed，只在展示层保留 `legacyPassed`。若产品确实要求新 run 可绿，按方案 §8 落 `authoritative peer`（引用同 run 有效宿主执行链的 acceptance/tests），否则应在方案里明写「quality pass 仅在全部三项都有 host 执行链时可达」，避免实现与文档继续分叉。

### N2（阻断）F1 兼容回退：不传 ownerId 时洞还在；engine.js:4451 是实例

**现象**：新 owner 接管后，旧调用方只要不传 `ownerId`（同 `pid@host`）就能续租并刷新新 owner 的心跳，甚至 `releaseLease` 删掉新 owner 的租约。

**最小复现**（容器内，`/tmp/probe-f1.mjs` 的核心）：

```js
const old = await store.claimLease(root, id, { pid, host, ownerId: 'owner-old', ttlMs: 1, now: t0 })
const fresh = await store.claimLease(root, id, { pid, host, ownerId: 'owner-new', ttlMs: 60000, now: plus10s })
await store.renewLease(root, id, { pid, host, now: plus20s })   // 不带 ownerId
await store.releaseLease(root, id, { pid, host })              // 不带 ownerId
```

实测输出：

```
old epoch 1 fresh epoch 2 fresh owner owner-new
RESULT renew(no ownerId) = SUCCESS, lease.ownerId = owner-new , heartbeat = 2026-11-06T12:00:20.000Z
RESULT release(no ownerId) = true
RESULT unfenced append = ACCEPTED, events 0 -> 1
```

**影响面**：仓库内引擎正常路径都传了 ownerId（[engine.js:4777](../../src/engine.js#L4777)、[5263](../../src/engine.js#L5263)、[5830](../../src/engine.js#L5830)），所以 P0 的线上主路径不复现；但 [engine.js:4451](../../src/engine.js#L4451) 的 start 失败收尾仍裸调 `releaseLease`，外部/旧插件调用方也能走兼容分支。审查报告 F1 明确要求「旧 renew/释放与新 claim 可控交错：新锁与 epoch 必须属于新 owner」，兼容分支等于给这条要求留了后门。

**建议修法**：`renewLease`/`releaseLease` 在非 `force` 时**要求** `ownerId`（缺了直接 409，不做 pid@host 回退）；确实要兼容的旧调用方走显式 `force` 或一次性迁移。顺手把 [engine.js:4451](../../src/engine.js#L4451) 改成传 `active.lease.ownerId`。再补一条「旧调用方不传 ownerId」的红测，锁死这个分支。

### N3（阻断）F3 非文本副本与空格分隔凭据仍泄漏

**现象一（二进制报告）**：报告文件含非法 UTF-8/二进制字节时，`redactReportCopy` 直接原样返回，公开副本保留 canary。

```bash
docker exec dsh-flow-dev bash -lc 'cd /testbed/workspace/dsh-flow-studio && node /tmp/probe-f3.mjs'
```

实测（节选）：

```
binary state: pass | copy: "ÿþ\u0000token=canary-bin-2" | contains canary: true
```

**现象二（空格形态）**：共享脱敏规则只认 `key:value|key=value`，`--token <value>` 原样进 `commandSummary` 与 `outputTail`：

```
summary: "curl --token canary-space-4 http://x"
outputTail: "--token canary-tail-7\n"
```

**影响面**：公开副本是 run 目录里的 artifact，可被详情/导出读取（[engine.js:6764](../../src/engine.js#L6764)–[6779](../../src/engine.js#L6779)）；PDF/PNG/二进制报告或 `--token` 形式的命令行都会把凭据带出去。方案 §5（第 78 行）说「未识别的任意秘密不承诺自动识别」，但二进制路径不是「规则没覆盖」，而是**明知不可脱敏仍完整复制**；要么把它标成 opaque 并留在私有目录，要么在公开侧拒绝发布。

**建议修法**：对非文本报告，公开副本只写一个「opaque，未脱敏，已留私有副本」的占位并保留长度/hash 绑定（或干脆不生成公开副本、让 `reportRef` 指向私有 verification 目录）；如果业务必须公开原字节，至少在方案/测试里明确接受该泄密面并加一条 canary 二进制用例。空格形态可扩共享规则（如 `(?:--?|/)(?:token|password|secret|api[-_]?key)\s+(\S+)`），或至少在 `commandSummary` 层做一次按 argv 的键值脱敏。

### N4（残余，低概率）F6 的锁内全量扫描 vs 10s 陈旧锁 TTL

**现象**：`finalizeEpoch` 现在在持有 `meta.lock` 时调用 `readAllEventsUnlocked` 扫全量事件（[runstore.js:2161](../../src/runstore.js#L2161)）；`withRunFileLock` 只在创建时写一次文件、临界区内不刷新 mtime，而 `META_LOCK_TTL_MS=10s`（[runstore.js:141](../../src/runstore.js#L141)）。若一次扫描（大 run / 慢盘 / 长 GC）超过 10s，另一个进程会按「陈旧锁」走选举接管，出现两个写者，F6 的「同一锁事务」保证失效。

**最小复现**：在 5000 事件 × 慢 I/O 上让 `finalizeEpoch` 的扫描超过 10s，再由另一进程 `appendEvents`；或临时把 `META_LOCK_TTL_MS` 调到 50ms 跑并发 finalize 用例（本节点未改产品代码，故只做代码级论证）。

**影响面**：只在极慢存储/超大 run 下出现；本地 SSD 上 5000 事件远低于 10s。但这是 F6 修复把临界区从「几行 JSON」扩大到「全量事件扫描」后新引入的耦合，建议记入残余风险。

**建议修法**：持锁期间周期性 `utimes` 刷新 mtime（心跳），或把 TTL 提高到与最大扫描时长匹配并加监控；更彻底的是单独的幂等索引文件，避免在锁内扫全量。

### N5（残余，低概率）F2 的无世代路径会退化成无 fence 写入

**现象**：`executionMatchesGeneration` 在 `generation` 为 null 或 `meta.execution` 缺字段时返回 `true`（[runtime.js:196](../../src/runtime.js#L196)–[208](../../src/runtime.js#L208)）；`settleInstance` 又在 `meta.execution` 不存在时把 fence 设为 `{}`（[runtime.js:1352](../../src/runtime.js#L1352) + [generationFence:211](../../src/runtime.js#L211)）。对没有 ownerId/epoch 的旧 Engine/自定义 Engine，迟到 settle 仍可能无 fence 地写 `supervision.enabled=false`。

**影响面**：生产 Engine 在 start 返回后立即抓 lease，正常路径有世代；只有旧 Engine/注入的桩 Engine 或 run.json 被旧二进制抹掉 execution 时才可达。属于兜底缺口，不是本次主路径。

**建议修法**：真实 Engine 必须有世代才允许走「关闭 supervision」分支；拿不到世代时只摘本地资源、不落盘（或按 `meta.execution.epoch` 从 run.json 现取一个保守值）。另外把「无世代」写进日志与测试。

### 已检查、未发现问题的角度

- `withLock` + `withMetaLock` 嵌套：无反向加锁顺序、无同链重入、跨进程等待有界；`appendEventsInLock` 只有两个已持锁调用点。**未发现死锁/自锁**。
- `requireActive` 默认不查：`appendEvents` 的业务写确实允许 `execution.state=settled` 的旧世代追加，但引擎在写 run/end 前已封口 + drain，产品路径没有迟到写；`finalizeEpoch` 自己用了 `requireActive:true`。**未发现当前可达的错误写入**，后续新增异步写路径时需要复核。
- 报告 hash 顺序与验证器口径：`reportSha256` 绑定最终脱敏副本，验证器重读同一副本；**一致**。
- dispose 的 release 捕获：按本次启动捕获、幂等包装，**无串新 run 还槽**。
- F5 的 realpath 键、F7 的真实终止还槽：变异均能红且 HEAD 绿，**未发现绕过**。

## 5. 残余风险（本节点认为可接受或需显式记录的）

1. **F8 被接受，但它是现在的授信边界**：`buildHostExecutionVerifier` 只核对 `runId/nodeId/attempt/reportSha256`，不绑定 `checkId`、命令摘要、预期/实际退出码与 `state`（[runstore.js:2219](../../src/runstore.js#L2219)–[2255](../../src/runstore.js#L2255)）。模型若能在**同一 node/attempt** 里引用一条真实登记过的 host 执行（哪怕那次是 exit 1 / fail），伪造的 `check/form state=pass` 仍可能被归为 host 权威。F8 已 accepted，故不计入阻断，但它应是下一轮优先补的字段绑定；当前攻击需要拿到同 node/attempt 的 executionId，实际可达性低。
2. **legacy 全绿**：如果产品坚持「历史 run 兼容优先于方案 §8 的不绿」，可以接受，但必须把「权威覆盖 0% + 绿 pill」的组合写进已知差异，并让 UI 至少并列显示覆盖率为 0；否则用户会把它当成可信结论。
3. **非文本报告不脱敏**：如果团队确认 reportPath 只允许文本（JSON/LOG/MD），把这条限制写进 `normalizeNodeCheck` 或方案并加拒绝逻辑；否则按 N3 处理。
4. **meta.lock 10s TTL**：见 N4；本地 SSD 上可接受，慢盘/超大 run 需要心跳或更长 TTL。
5. **同 uid 的本地文件篡改不在本期防线内**：方案 §7.3 已明确「宿主与模型同 OS 用户，文件权限不构成敌对本地进程隔离」，本节点接受；`verification/` 私有登记只能防事件/产物自报洗白，不防同 uid 直接改文件。
6. **测试环境性跳过**：root 权限档与 git `--orphan` 档未执行；它们与 0.11 的可信六条无直接关系，接受。
