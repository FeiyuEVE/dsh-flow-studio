- 文本多字节中文前后内容保留（探针 ⑨）。

### 4.3 未修部分（可复现）

**（a）二进制里非空白前缀的 `--api-key` / `--password` / `--secret` 原样泄漏。**

`SECRET_FLAG_PATTERN` 要求标志位前面是 `^` 或 `[\s"'`;|&(=,\[]` 之一（[host-check.js:121](../../src/host-check.js#L121)）。文本命令里标志位前面通常是空格；但二进制记录的字段前是 NUL、长度前缀、protobuf tag 等任意字节，不满足这个字符类。探针：

```text
## ③b 二进制 + \x00\x01 后直接 --api-key（前缀不是空白/引号/括号）
{
  "state": "pass",
  "reportOpaque": true,
  "copyLatin1": "\"ÿþ\\u0000\\u0001\\u0002--api-key canary-api-leak-3 --verbose\"",
  "copyLength": 44,
  "sourceLength": 44,
  "reportSha256MatchesCopy": true,
  "byteIdentical": true
}

## ③c 二进制 + \x12（长度前缀）后直接 --password
{
  "state": "pass",
  "reportOpaque": true,
  "copyLatin1": "\"ÿ\\u0000\\u0012--password canary-pw-leak-3b end\"",
  "copyLength": 36,
  "sourceLength": 36,
  "reportSha256MatchesCopy": true,
  "byteIdentical": true
}
```

`--token` 没在这个清单里，是因为规则 1 的 `Token` 认证方案（大小写不敏感）意外把它覆盖了；`--access-token` 同理。`--api-key` / `--password` / `--secret` / `--secret-key` / `--private-key` / `--credentials` / `--authorization` / `--cookie` / `--session-key` / `--ssh-key` 在非空白前缀下全部漏。等号形态（`--api-key=...`）会被规则 4 接住，所以漏的只是**空格分隔**形态——但命令行的标准形态恰恰是空格。

**（b）UTF-16LE 报告整段不脱敏。**

```text
## ④ 二进制（UTF-16LE）里的 token=/--api-key
{
  "state": "pass",
  "reportOpaque": true,
  "copyLength": 96,
  "sourceLength": 96,
  "reportSha256MatchesCopy": true,
  "byteIdentical": true
}
```

`t\0o\0k\0e\0n\0=\0...` 里没有连续的 `token`，规则全部不命中；latin1 映射本身没问题，问题是模式只认单字节 ASCII 连续串。UTF-16LE 报告在 Windows 工具（PowerShell 5.1 的 `>` 重定向）里很常见；宿主检查本身在 win32 会 skipped，但 Linux 上的工具也可能显式写 UTF-16LE。这条至少应在发布说明的「已知残留」里明确，不能写成「二进制按字节脱敏」。

**（c）值后无空白时吞掉后续非凭据字节。**

规则 3 的空格形态值类 `([^\s"'\`;|&)]+)` 与规则 4 的 `[^\s,;&}；，]+` 都把 NUL / 控制字节当值的一部分，直到遇到空白。NUL 终止串（C 字符串、定长二进制记录）因此会把后面的内容一起替换掉。探针：

```text
## ③d 二进制 + token=canary\x00SIG（值后无空白，NUL 终止）
{
  "state": "pass",
  "reportOpaque": true,
  "sourceHex": "fffe746f6b656e3d63616e6172792d6e756c2d3364005349472d41018081",
  "copyHex": "fffe746f6b656e3d225b52454441435445445d22",
  "copyLength": 20,
  "sourceLength": 30,
  "reportSha256MatchesCopy": true,
  "byteIdentical": false
}
```

这不是理论问题：**项目自己的 engine e2e 夹具**就是这种形状（[engine.test.mjs:5984-5988](../../test/engine.test.mjs#L5984-L5988)，`printf '\377\376token=<canary>\000tail' > report.json`）。我用同一命令复现，公开副本从 28 字节变 20 字节，`\000tail` 整段消失：

```text
state: pass opaque: true
source bytes: fffe746f6b656e3d63616e6172792d62696e2d39663231007461696c
copy   bytes: fffe746f6b656e3d225b52454441435445445d22
copy latin1: "ÿþtoken=\"[REDACTED]\""
tail preserved: false
copyLength: 20 sourceLength: 28
sha binds copy: true
```

现有测试只断言 `copyBytes[0]===0xFF`、`[1]===0xFE`（[engine.test.mjs:6013-6014](../../test/engine.test.mjs#L6013-L6014)），没有断言 `tail` 还在，所以「非凭据字节逐字节保留」这条承诺在**自己的夹具上就已经不成立**。

### 4.4 小结

N3 的两个原始症状里，「二进制原样复制」已不再成立（有命中时确实替换、有 opaque 标记），「`--token <值>` 空格形态」在 commandSummary/outputTail/文本报告里已闭合；但二进制路径的形态覆盖与字节保留都不完整，见 N6/N7。判 **PARTIAL**。

## 5. 新发现

### N6（P1，阻断）二进制公开副本仍会泄漏 `--api-key` / `--password` 等空格形态凭据

- **现象**：`SECRET_FLAG_PATTERN` 的「前导分隔符」是文本假设；二进制记录里标志位前的字节通常是 NUL/长度前缀，规则不命中，公开副本与原报告逐字节相同（探针 ③b/③c，`byteIdentical: true`）。
- **最小复现**：报告内容 `\xFF\xFE\x00\x01--api-key canary-api-leak-3 --verbose\x80\x81`，命令只是 `cp seed.bin reports/probe.bin`；`runHostCheck` 返回 `state=pass`、`reportOpaque=true`，`reportBytes` 含完整 `canary-api-leak-3`。
- **影响面**：公开副本落在 run 目录的 `artifacts` 下，可被详情/导出读取（[engine.js:6774-6789](../../src/engine.js#L6774-L6789)）；任何二进制报告里带 `--api-key`/`--password`/`--secret` 空格形态的命令行都会把凭据带出去。发布说明写的是「只覆盖内置高置信形态」，但 `--api-key` 正是内置形态之一；这不是「无 recognizable 形态的裸随机秘密」那条已知残留。同一个 lead 字符类也被 `process-output.redactText` 复用（[process-output.js:93-103](../../src/process-output.js#L93-L103)），所以外部 executor 的输出里若有 NUL 分隔再跟 `--api-key`，outputTail/事件同样会漏。
- **建议修法**：二进制分支不要复用文本的 lead 字符类——对 latin1 串按「`--<name>` 出现在任意位置」扫描（或把 lead 放宽为 `^|[^\x21-\x7e]`），同时把值限定为可打印 ASCII（见 N7）；补一条 `\x00--api-key <canary>` 与 `\x12--password <canary>` 的 canary 用例。UTF-16LE 要么识别（按 0x00 间隔扫描）要么在发布说明里明确不覆盖。

### N7（P2，应修）脱敏值越界吞掉非凭据字节，违反「逐字节保留」

- **现象**：NUL/控制字节不被当作值终止符，`token=canary\0tail` → `token="[REDACTED]"`，`tail` 8 字节消失；公开副本长度从 28 变 20，sha256 绑定的是被截短的副本，验证器/审计看不出内容缺失。
- **最小复现**：见 §4.3(c) 与 [engine.test.mjs:5984](../../test/engine.test.mjs#L5984) 的官方夹具；同一输入下 `copyBytes.includes('tail') === false`。
- **影响面**：所有 NUL 终止/定长二进制记录里的凭据值都会连带丢掉后续字段；这是证据完整性问题（不是泄漏），且与本次修复声明的「非命中字节逐字节保留」直接矛盾。文本路径（合法 UTF-8 里含 NUL）同样受影响。
- **建议修法**：值类改为可打印 ASCII（如 `[\x21-\x7e]+`）并排除 `\x00`/控制字符；引号值也加同样边界；补断言「`tail` 必须保留、副本长度 = 源长度 − 被替换值长度 + 标记长度」。现有测试只验首两字节，建议补完整 tail 断言。

### N8（P2）`reportOpaque` 没有进持久事件，也没有进私有 verification 登记

- **现象**：engine 只在 check/form 的 `extra.verification` **嵌套对象**里放 `reportOpaque`（[engine.js:6809-6823](../../src/engine.js#L6809-L6823)，同段注释还写着「可信元数据必须同时有扁平键，嵌套对象仅作兼容」），但没有扁平键；`runlog` 的 `boundExtra` **丢弃嵌套值**（[runlog.js:267-292](../../src/runlog.js#L267-L292)），所以落盘事件里没有 `reportOpaque`。私有登记 `recordHostExecution` 的白名单也没有该字段（[runstore.js:2308-2326](../../src/runstore.js#L2308-L2326)，我实测 `verification/<id>/record.json` 输出里没有 `reportOpaque`）。
- **最小复现**：用真实事件形状（无扁平 `reportOpaque`）过 `normalizeEvent`，`event.extra` 只剩 `provenance/producer/authority/verificationId/verificationState/verificationKind/reportSha256/registryPath`；`recordHostExecution` 写出的 `record.json` 同样没有。唯一带该标记的是 engine 自写的公开记录 `host-check-<id>.json`。
- **影响面**：事件流/审计/导出/未来的报告解析器拿不到「这份副本不可当文本解析」的信号；如果它们按文本读 `reportRef`，会得到乱码或误判。当前没有消费方读它，所以是 P2，不是当期泄漏；但 commit 声称的「事件 extra 的 verification 嵌套对象同步」是无效接线。**catch/降级路径本身是一致的**：`runHostCheck` 抛错时 engine 造的合成 verification 带 `reportOpaque:false` 且没有报告副本（[engine.js:6699-6706](../../src/engine.js#L6699-L6706)），`_runHostCheckOnce` 的 catch 直接返回 null 不落记录；不一致只发生在「有报告副本」的正常路径的持久化环节。
- **建议修法**：在 `extra` 加扁平 `reportOpaque: true/false`（与 `verificationId` 同级），并把它加进 `recordHostExecution` 的白名单；补一条 normalizeEvent/record 断言。

### N9（P2）`process-output.redactText` 的 `Authorization: Basic/Token` 泄漏，且与 engine 已不同源

- **现象**：engine/host-check 的规则 1 已扩到 `(Bearer|Basic|Token)`（[host-check.js:145-148](../../src/host-check.js#L145-L148)），`process-output` 仍只有 `Bearer`（[process-output.js:95-103](../../src/process-output.js#L95-L103)）；规则 4 的 guard 也只放行 `Bearer`（[process-output.js:113](../../src/process-output.js#L113)）。于是 `Authorization: Basic <base64>` 被改成 `Authorization: "[REDACTED]" <base64>`——只抹了 scheme，凭据还在。
- **最小复现**：

```text
IN : -H "Authorization: Basic dXNlcjpwYXNzd29yZA=="
  process-output: -H "Authorization: "[REDACTED]" dXNlcjpwYXNzd29yZA=="
  engine        : -H "Authorization: Basic [REDACTED]"
IN : -H "Authorization: Token canary-basic-token"
  process-output: -H "Authorization: "[REDACTED]" canary-basic-token"
  engine        : -H "Authorization: Token [REDACTED]"
```

- **影响面**：`process-output.redactText`/`redactDeep` 用于外部 executor 的输出、stderr tail、错误链、final text（[executor.js:731](../../src/executor.js#L731)、[751](../../src/executor.js#L751)、[814](../../src/executor.js#L814)、[958](../../src/executor.js#L958)、[1027-1028](../../src/executor.js#L1027-L1028)）；这些内容会进事件/面板/导出。该漏洞在新 N3 接线前就存在（当时 engine 也只认 Bearer），但 5c0ca19 把 engine 扩到 Basic/Token 后，`process-output` 的「规则 1–3 与 engine 逐字一致」注释已不成立，同一次「同源」重构没有收口。
- **建议修法**：把 `process-output` 规则 1 改成 `(Bearer|Basic|Token)`，规则 4 guard 改成 `(Bearer|Basic|Token)`；或直接复用 host-check 的 `redactSensitiveText`（注意保留它自己的规则 5 精化）；补 `Basic`/`Token` 两条 canary 断言。

### N10（残余，低可达）N2 兼容回退只看 execution 缺失，不看 lock.json 是否仍是 0.10 形状

- **现象**：`leaseHeldBy` 的兼容分支仅要求 `meta.execution` 缺失；如果 `run.json` 因回滚/半写丢了 `execution`，但 `lock.json` 仍是 0.11 形状（带 ownerId/epoch），缺 ownerId 的调用方仍能按 pid@host renew/release。探针 ⑤：`lock 仍有 ownerId=owner-011 epoch=1` 时，`renew(no ownerId)` 成功、心跳刷新、`release(no ownerId)` 删掉租约。
- **影响面**：要求异常状态（0.10 进程重写 run.json、手工删字段、磁盘损坏），不是主路径；但它跟 N2 要消灭的 ABA 是同一类，只是入口更窄。
- **建议修法**：兼容分支再加一条 `lock.json` 也没有 `ownerId`/`epoch`（0.10 双缺形状）才放行；或把「execution 缺失」视为不可信、只允许 `force` 释放。

### 已检查、未发现问题的角度

- **N1 方向一致性**：legacy 与 model-claim 在 1/3 覆盖下同为 unknown（探针 ⑤）；legacy 不再有 pass 路径。
- **N2 合法调用方**：engine 的 claim/renew/release/start 失败收尾全部带 ownerId；runtime 的 force 只在 `leaseIsReapable` 或自己 claim 后；没有死锁/自锁。
- **N2 claim 半途崩溃**：execution 新 + lock 旧时旧 owner 409，TTL 后可接管，无永久锁。
- **N3 sha 绑定**：host-check 与 engine 都对**最终副本**算 sha256（探针 ①、[engine.test.mjs:6017-6019](../../test/engine.test.mjs#L6017-L6019)），没有「源文件 hash 冒充副本」。
- **N3 二进制误伤**：不含凭据的 64 位 hex 二进制逐字节不变（探针 ②），latin1 映射在命中段之外不损坏多字节 UTF-8 字节（探针 ⑨，前缀/后缀中文保留）。
- **N3 参数名边界**：`--token-file` / `--tokens` / `--tokenize` / 裸 `--token` 不被误吞（探针 ⑧）。
- **N3 quoted header**：`-H "Authorization: Bearer X"` 的外层收尾引号保留（探针 ⑧）。
- **N1 客户端**：`coverage<1` 的 pass 给 warn；无 coverage 字段的旧 Host 摘要保持 green（兼容选择，见残余）。

## 7. 残余风险

1. **`force:true` 仍是租约的万能逃生口**（N2 设计内）：任何拿到 `runstore` 模块的插件都能删活租约；HTTP 层未暴露，属可信本地代码边界，记录在案。
2. **N10 的 execution 缺失兼容窗口**：回滚/半写 + 同 pid@host 时可 ABA；低可达，建议按 N10 收紧。
3. **G-E 不可达**：真实 run 的「优/良」不可达，质量结论恒为「证据不足」；方向正确、已登记 0.12，但发布说明必须保留这段，且不要把它说成「质量结论正常」。
4. **文本路径的 ≥32 启发式**：合法 UTF-8 报告里的 64 位 hex（含 sha256）会被替换成 `[REDACTED]`（探针 ⑦），二进制路径不会；同一份证据按编码不同被不同处理。这个分歧是修复前就有的，N3 让它正式化；如果审计需要保留报告里的哈希，文本路径应考虑只对「像凭据的混合串」替换。
5. **F8 未闭合的字段绑定**：`buildHostExecutionVerifier` 只核对 run/node/attempt/reportSha256，不绑定 `checkId`、命令摘要、退出码、state（上一轮已 accepted）。N8 的事件缺口让「报告不可解析」更难被发现，两者叠加时审计信息不足。
6. **`META_LOCK_TTL_MS=10s` vs `finalizeEpoch` 锁内全量扫描**（上一轮 N4）：超大 run + 慢盘仍可能被按陈旧锁接管；本轮未复测，沿用上一轮记录。
7. **旧 Host 摘要的客户端兼容**：`conclusionOf` 在没有 `authorityCoverage` 字段时仍允许 green；同版本部署下不会遇到，但混合升级/缓存的旧摘要会保留一次假绿。记录在案。

## 8. 结论

**不能按现状发 0.11.0。**

- N1、N2：**通过**，不需要返工。现有实现与反向用例咬得住，探针复现了原始攻击并全部被 409 / unknown 挡住。
