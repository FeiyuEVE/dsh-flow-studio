## 8. 新发现（N11、N12、N13）与观察项

> 前缀声明：以下都是**我能复现的**；都**不是**这两轮提交引入的回归（N11 是复核2 给过「要么修、要么写进发布说明」二选一的遗留），我把它们按「是否阻塞 0.11.0」分开写。

### N11（残余，建议发布说明补一句或 0.11.1 修）UTF-16LE 编码的标志位不被识别，凭据原样进公开副本

- **现象**：二进制/文本两条路径都按「1 字节 = 1 字符」或 UTF-8 解码处理，UTF-16LE 里 `-` 与 `-` 之间夹着 `\0`，标志位名被打断，任何规则都不命中；副本逐字节等于源文件。
- **最小复现**（`.tmp/probe3/p9-utf16.mjs`）：

```
UTF-16LE + BOM: 106->106 opaque=true byteIdentical=true
  原样 utf16le 解码仍含 canary = true
  utf16le 解码片段 = "﻿curl --api-key CANARY-utf16-9f3a --verbose http://x/"
UTF-16LE 无 BOM: 104->104 opaque=false byteIdentical=true
  原样 utf16le 解码仍含 canary = true
  utf16le 解码片段 = "curl --api-key CANARY-utf16-9f3a --verbose http://x/"
UTF-8 + 尾随 0x80（二进制路径）: 含 canary = false
  副本 = "curl --api-key [REDACTED] --verbose http://x/"
```

  注意「无 BOM」变体是**合法 UTF-8**（NUL 合法），走的是**文本路径**（`opaque=false`）也照样漏——所以这不是「二进制分支的 bug」，而是「所有规则都不认 NUL 间隔字符」。
- **可达性**：Windows PowerShell 5.1 的 `>` / `Out-File` 默认写 UTF-16LE；宿主检查支持 win32（`CAN_DETACH` 有平台分支），一份被重定向进报告的 UTF-16LE 日志/命令行就会带出凭据。Linux 上要显式 `iconv`/`pwsh` 才有。
- **判定**：0.11.0 发布说明只写了「latin1 1:1 映射 + 只吃可打印 ASCII」，**没有声称**覆盖 UTF-16，所以不算「说了没做到」；但复核2 已明确给过「要么识别、要么在发布说明里明确不覆盖」的出口，**两件事都没做**。建议：发布说明加一句「二进制副本的高置信规则按单字节/UTF-8 判读，UTF-16（含 PowerShell 默认输出）不在覆盖范围」；要做就 0.11.1 按 0x00 间隔扫描。**不阻塞本轮判定**，但这是唯一一条我建议在发版前落文档的。

### N12（残余，设计内）前一个字符是 `[A-Za-z0-9_-]` 时不命中

- `deadbeef--api-key <v>`（十六进制/长度前缀紧贴标志位）、`1--api-key <v>`、`abc_--token <v>` 在文本与二进制两条路径都**原样保留**（§1 的 p8 表）。这是为避免 `foo--api-key` 词中误判而选的取舍；复核2 的建议原本是「按任意位置扫描（或 lead 放宽为 `^|[^\x21-\x7e]`）」，实现选了更保守的 `[^A-Za-z0-9_-]`。
- 影响：只有「标志位紧贴一个 ASCII 字母数字/下划线/连字符、且用空格而不是 `=` 分隔」时才漏；`=` 形态仍被 key:value 规则兜住（`1--api-key=<v>` → 认）。记为残余，不阻塞。

### 观察项（不算缺陷，记录在案）

1. **标记形态不一致**：`--flag <v>` → `[REDACTED]`；`key:v` / `--flag=<v>` / `--password='<v>'` → `"[REDACTED]"`（规则 4 二次处理会把单引号改双引号、`--token=` 变 `--token="[REDACTED]"`）。凭据都抹掉了、长度差异可解释，但审计若要求「逐字节等于只把值换成 `[REDACTED]`」会看到 2 个引号字节的差。
2. **引号值内含 NUL** 会产生不平衡引号（`token="[REDACTED]"\0tail"`），见 §2。
3. **`redactDeep` 不做键名判据**：`redactDeep({ token: 'TOK-deep-0024' })` → 值原样（只有值里**自带**凭据形态才会被抹）。这是既有设计边界（它是文本模式清洗器），不是本轮改动；但如果将来有 executor 用结构化字段名承载裸凭据，需要单独处理。
4. **`force:true` 仍是租约万能逃生口**（N2 设计内，HTTP 层未暴露）。
5. **`URL userinfo`（`https://user:pass@host`）三处都不覆盖**——既有 gap，不是分叉。

## 10. 结论

**能发 0.11.0（PASS WITH RESIDUALS）。**

- **N6**：闭合。`\x1c\x00--api-key`、`\x12--password` 及我自选的 `\xff--secret`、`\x00\x00--access-token`、`=` / 引号 / 缓冲区首位全部按字节替换，非命中字节逐字节保留；文本侧同样成立。「`foo--token` 不会被误判成标志位」成立（规则 3 不命中；观察到的替换来自既有的规则 1 松散形态，三处一致、方向是多抹）。
- **N7**：闭合。文本/二进制两条路径的 `token=<canary>\0tail` 都**逐字节精确**等于「只把凭据段换成标记」，`\0tail` 原样在；NUL 在值中间、空格形态值后跟 NUL、`,`/`;`/`0x7F`/`0xFF` 边界都保留；6410 段批量对比里 NUL 分隔符一个不少。唯一的装饰性残余是「引号值内含 NUL」会产出不平衡引号。
- **N8**：闭合。真引擎 e2e 的 `check/form` 事件 `extra.reportOpaque` 是**扁平布尔**（文本报告为 `false` 且键存在），`verification/<id>/record.json` 有该字段，`readHostExecutions` 与 `readAllEvents` 都读得回来；模型自报的 `check/form` 没有这个键，不能冒充。
- **N9**：闭合。`Basic` / `Token` / `Bearer` 三方案凭据都不在输出里、scheme 保留、不再产出 `Authorization: "[REDACTED]" <凭据>`；`Basic usage` / `WWW-Authenticate: Basic realm=` 的误伤与 host-check/engine **同口径**（按用户口径不算缺陷）。
- **N10**：闭合。半抹除状态（execution 缺失、lock 仍 0.11 形状）下无 ownerId 的 renew/release 都 409、lock.json 一个字节不改；只缺 ownerId 或只缺 epoch 的变体同样 409；**真 0.10 旧租约的 pid@host 续租/释放照常**；`force:true` 仍能释放；0.11 正常路径不受影响。
- **回归面**：没有发现这两轮修复引入的功能回归；二进制仍然不跑 ≥32 启发式，无凭据二进制（含 64 位 hex）逐字节不变、sha 不变；`process-output` 的 key:value 收窄没有弄坏普通文本/路径/URL/ANSI；host-check 文本与 process-output 在 5600 条组合上 0 差异，文本 vs 二进制在 6410 条上 0 条 canary 级分叉。
- **发版前建议（唯一一条硬建议）**：把 **N11（UTF-16LE 不覆盖）** 写进 0.11.0 发布说明的「已知残留」，或直接排进 0.11.1；其余残余（N12/N13/观察项）按现状记录即可。

### 本轮没有证的

- 没有验证 N1/N2 的行为（按要求不在范围；只在 N10 探针里顺带确认 0.11 正常路径与真 0.10 兼容路径没坏）。
- 没有做跨进程真实并发压测（N10 的结论来自锁内状态机 + 探针，不是多进程竞争注入）；复核2 已做过 N2 的跨进程侧，本轮不重复。
- 没有验证 Windows 上 UTF-16LE 的真实产生路径（只在探针里手工构造编码），N11 的「可达性」是平台默认行为的推断，不是实测产物。
