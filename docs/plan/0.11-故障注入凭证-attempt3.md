## 结论：reject

**R1 当前代码存在可控跨进程竞态，确知 lease-lost 后旧业务事件仍提交。** 在真实跨进程夹具中，父进程旧 owner 的 `appendEvents` 已持 `meta.lock` 并挂起在 guard；子进程建立新的 `lock.json` 租约但阻塞在 `withMetaLock` 写 epoch；第三进程对旧 owner `renewLease` 得 409。此时元数据仍为 epoch 1，释放旧 append 的 guard 后事件成功提交 1 条，子进程才把 epoch 写为 2。重放命令 `node /tmp/fi4-race.mjs > /tmp/fi4-race.log 2>&1` 实际 **exit 1**，日志记录 `renewStatus:409,epochDuring:1,oldResult:{committed:1},childCode:0,epochAfter:2`，失败断言 `old write must be blocked once new lease is visible and renew returns 409`（1 !== 0）。这是**修复版真实负测**，不是只看源码的理论窗口；夹具目录 `/tmp/fi4-race-gshPlT`。第一次尝试同进程续租被本地 withLock 挡住、夹具 exit 13，已改用独立续租进程复测；exit 13 未计作功能红。根因 [claimLease](../../src/runstore.js) 在 `createExclusive(lock.json)` 之后才进入 meta.lock，而 [appendEvents](../../src/runstore.js) 只在自身 meta.lock 内查旧 epoch，不核新的 lock owner。

## 未验证边界

父进程 guard/子进程 claim 的现有用例没有检查在旧 append 放行前新 `lock.json` 已建立、旧续租已经 409。runtime 自审共用验证器的源码链可见，但本节点未独立注入真实 supervision 正常/删除报告的端到端对照；不能把 summary/export 的 HTTP 绿测说成 runtime 自审已端到端验证。并发 `finalizeEpoch` 同 epoch 重复写 end 未测试，不把它算通过。此次未运行全量 `npm test`/build/verify-build，交由父测试主管或质量工程师复核。
