## 3. R1：失权同步取消、条件写与唯一收口

### 3.1 新增租约世代与跨进程事务

当前 `withLock` 是进程内 Promise 串行化，不能作为跨进程所有权证明。新增每 run 的 `withRunMutationLock`，以文件系统独占创建实现跨进程互斥，`claim/renew/release/append/meta/业务文件提交/finalize` 共用这把锁；锁获取有界等待，失败返回可识别 I/O/锁忙，不允许无锁继续写。锁与租约分离，不能把业务租约文件当写入锁；不能持锁等待节点、进程或会话 dispose。锁拥有者记录随机 token 和进程身份；正常释放核 token。崩溃恢复仅在能够证明原进程已死且 token 未变化的短回收临界区内回收；同 PID 活跃、PID 重用身份不明或远端存活不可证时保守拒写，不按简单 TTL 抢走仍在执行的写锁。恢复后的 JSONL/元数据重建亦持同锁；在目标本地文件系统上须有双进程互斥取证，网络文件系统语义不明确时不宣称支持。

租约新增 `ownerId`（每次 claim 随机生成）和单调 `epoch`。元数据持久化 `execution={epoch,ownerId,state}`，在 release 后仍保留世代；active 保存完整 lease，不能再只保存 true。`renew/release` 比较 ownerId+epoch，防同 pid@host 的 ABA。内部写调用传不可从 HTTP body 获得的 fence capability；存储在同一锁内核对当前持权者再提交。人工 stop/外部观察按各自受控入口授权，不得伪造 engine capability。

`epoch`、终态作用域及幂等键是本期必需的 R1 局部 fencing；通用分布式调度优化不在范围内。已接收但仍排队的旧写也必须在实际提交时复核：失权后丢弃 eventQueue 中的旧业务任务，不能 drain 成落盘。JSONL 之前已完成提交的事实保留。

### 3.2 409 与 finally 不竞争

双循环统一调用 `_handleLeaseLost(active,error)`：同一 catch 回调内按顺序设置 `leaseLost/writeClosed`、封会话观察入口、清续租 timer、abort controller（原因 `LEASE_LOST`），然后交由一次 `_finalizeRunOnce` Promise 收口。禁止在 timer 回调直接追加 end；catch/finally/stop 都等待同一个 finalizer。失权原因优先于 timeout、stop 和迟到 done，必须得 failed 而非 aborted。续租非 409 的 I/O 只 warn，保留下一次续租机会；不把文件系统瞬时异常误译为失权。

finally 先取消 host check/外部进程组、detach/取消会话与成员订阅，有限等待 dispose，隔离不能完成的迟到回调，再等待已进入存储事务的写完成。所有尚未提交的旧业务写因 fence/writeClosed 被拒绝。失权分支只调用 `finalizeEpoch`，完全跳过旧的 `_append(end)`、`writeRunMeta(live:null)`、`_patchRunBinding` 和 `releaseLease`。`runtime.settleInstance` 仍幂等摘本实例、还配额、清本地调度，但不再无条件 `saveSupervision`；持久化清理必须服从当前 epoch。正常/用户 stop 路径沿用“封口→取消→drain→唯一 end→清 live→条件释放→摘实例”。

续租采用 single-flight，settling 后不再启动下一次续租；已在飞续租的晚到 409 必须先由存储确认该 epoch 是否已经正常提交终态，不能把已完成 run 重分类。`Engine.start` 的 catch 同样委托该 finalizer，不能另外 write failed/release。`settledHook` 仅允许只读通知或带 fence 的写入，失权时不能借钩子保存接管者 supervision。`_writeExecutorSchema`、收件箱执行状态和绑定队列也纳入写门；产物最终 rename 与发布在持权事务内提交（或先写 epoch 隔离路径再条件 publish），不能只挡 artifact/write 事件而放行文件覆盖。锁内调用 unlocked 提交函数，禁止嵌套获取同锁造成死锁。

### 3.3 失权失败事实与接管者状态协调

`finalizeEpoch({expectedEpoch,ownerId,cause:'lease-lost',idempotencyKey:'loss:<epoch>'})` 是存储专用接口。每个失权 epoch 恰有一条 `run/end`，`data.status='failed'`、reason 含 `lease-lost`、`extra.code='LEASE_LOST'`；这是唯一允许的失权后追加例外。接管者正常完成还能有它自己的 run 级 end，不能把“一个失权 end”误解为所有 epoch 合计只有一条 end。

在同一个 mutation 锁里判定：若元数据 current epoch 仍等于失权 epoch（例如 lock 缺失/损坏且尚无新 owner），关闭此 epoch，写 run 范围失败终态、清本 epoch live/supervision。若 current epoch 已更新，即使接管者已完成释放了 lock，也只追加 `extra.terminalScope='instance'` 的失权审计事实，不改变接管者 status/live/binding/supervision/lease；run 范围终态为 `terminalScope='run'`。scope 与 epoch 由 store 生成，来客不能指定。claim 和 finalize 原子竞争：claim 先赢则旧 end 只能是 instance；finalize 先赢则 run 已 failed，后续 claim 必须拒绝重新打开，恢复需另建 run。

新增统一 `isProjectedRunEvent(event,currentEpoch)`：旧无 epoch 的历史生命周期按原语义读取；新 instance end 永远不投影为 run 终态。必须同时适配 [runstore](../../src/runstore.js) 的 append reducer/`repairRunStates`、[runlog](../../src/runlog.js) 的 progress/quality/summary/导出、[restart](../../src/restart.js) 的终态和失败节点推导、[audit](../../src/audit.js) 的 end 检测、[engine](../../src/engine.js)/[状态机](../../src/flowmachine.js) 的恢复与重放、[抽屉](../../src/client/logdrawer.js) 的事件状态回退，以及 [supervision](../../src/supervise.js) 的终态判断。客户端优先使用服务器投影的 run.status；时间线仍显示“旧执行实例失权失败”。任何按最后一条 end 取终态的旁路都必须移除。

幂等不能仅靠内存 once：锁内以 loss key 扫描/恢复已提交 end，JSONL 为追加事实日志；模拟“JSONL 写成而 meta 尚未更新”后重试，从现有日志恢复索引和投影，不能重复追加。部分尾行恢复走现有损坏行处理并取证；磁盘不可写时诚实报持久化失败，不保证物理介质故障下必有 end，保持 writeClosed、绝不降回成功。新 epoch 不得复用旧失权 end 的 key。

## 4. R2：runtime 准入与有限 FIFO

配额只在 runtime 统一判定。index 附加路由限流无法覆盖 flow_start、restart、收件箱和多 runtime。进程共享 controller 用 `globalThis[Symbol.for(...)]` 保持单例（包括模块重载），生产 limits 在第一次初始化固定；后续 runtime 传不同 limits 则拒绝初始化并说明既有 effective limits，不能创建第二个“全局”配额器。单元测试通过显式测试控制器注入隔离状态，不暴露公共绕过参数。

同步登记 `(realpath(runsRoot),runId)` 的 resolving ticket 防 await 穿透；完成只读 preflight 后，以原始工作区 realpath 原子 reserve。来源工作区来自绑定而非新 worktree；restart 沿旧 run 来源 workspace 计量，即使 cwd 使用旧 worktree。`reserved/starting/running` 都占额度，`resolving/queued` 不占活跃槽；resolving 请求有超时与调用取消，不能持有 Engine。重复 runId 在所有上述状态均 409。

preflight 解析身份、工作区、合法流程与检查配置并冻结 flow/check 快照；不创建 Engine/worktree/session，不写 run/start，不先修改工作区绑定。出队后 Engine 使用这份私有快照，避免排队期间保存流程改变实际检查命令。runtime 外直接构造 Engine 只作为内部低层测试 API，生产注册/路由不得绕过 runtime。

工作区满立即 429。仅全局满、该工作区尚未满且队列有位时 queued；队满或 queueMax=0 立即 429。队列严格 FIFO：队头出队前再次核对两级额度，队头因 workspace 满则等待其释放或超时，不越过队头悄悄启动后者。只读 `admissionOf(runId)` 返回实时位置，保持既有 `runtime.get` 仍为 Engine|null。

启动 promise 仅在实际 Engine.start 成功后成功。GET run 详情合并内存 `admission={state:'queued',queuedAt,position,timeoutMs}`；不伪造新持久状态，run 仍 pending。HTTP 在配置的等待上限内等待（默认 15000ms），超时返回 429；显式合法等待值可高于默认。监听 `req.aborted` 或 `res.close && !res.writableEnded` 取消排队，不能将正常 req.end 当断连。超时/stop/dispose/断连用同一个 cancel 原子摘票，之后 release 不得再启动它。

release 由 ticket 一次性方法拥有：start 抛错、settled、stop 完成、dispose 等竞争仅释放一次；stop 发出取消但进程尚未收口时不能过早还槽。dispose 必须取消排队并等待已占槽实例清理。进程崩溃队列不恢复，pending 元数据可再次显式 start，详情不再显示 queued。

取消同时覆盖 resolving/preflight/reserved/starting：ticket generation 不可逆失效，abort 启动信号；每个 realpath、worktree、claim、startRun 异步步骤返回后重查 generation。晚到 Engine.start 成功不能返回成功或留下后台 run，立即走统一收口并等待资源退出再释放。grant 与 cancel 同 tick 只能一个赢家。进程进入 terminating 时仍占槽，直到 close/确认进程组消亡；超强杀期限则显示 cleanup 故障并保留占位，不因 runner 提前 resolve 就允许遗留进程无限累积。

restart 避免扩大 0.10 孤儿缺陷：`restartOnce` 先按父 run 登记 provisional reservation，允许预建 pending 子 run 以便详情可查询；未写 run/start 的失败写 `restart.startRejected={code,at,retryable:true}` 并保留审计，不删除目录。后续原 restart 识别该子 run，复用同 childRunId/已保存 resumePlan 重新准入，不能被“存在任意 child”永久挡住；返回错误保留 childRunId。子 run 一旦开始过，仍沿原世代规则只能续跑该 child。初始化其它步骤失败也使用此可重试路径；不借本期实现评估中 E2/E3 完整跨进程 restart 原子索引。

## 5. R3：流式有界输出与脱敏

共享 runner 在 data 入口使用 Buffer 原始字节计数 stdout+stderr，计量在 decode/复制前；恰好等于 B 允许，超过 B 的 chunk 仅接受剩余 slice 并进入 OUTPUT_LIMIT。累计 receivedBytes 不能因 ring 淘汰回退。规范化事件累计超过 E 同样中断。单事件仍受既有 8KiB 事件边界，脱敏后再裁剪/拆分，不能先裁出 token 前缀再脱敏。

明确内存预算：原始字节 ring≤B；stdout 半行≤B 且与 ring 共用预算；解析后的 finalText/structured/event JSON 总保留≤B；事件对象≤E；诊断 tail≤min(B,16KiB)。解析的对象、异步 onEvent 待提交队列也计入对应保留预算，不能把 ring 搬空后无限堆 Promise。整体 O(B+E)，不再保留另一份无界 stdoutAll。合法限额内输出必须完整；ring 仅用于诊断/受限重放，不能淘汰正常结果后仍假称输出完整成功。单个超长行不等 EOF 才限制，JSON 序列化扩张也受保留预算。

为避免无限长敏感值跨 chunk 泄露，可见文本按完整逻辑记录发布；未结束行在有界原始 ring 内等待，EOF 时才处理半行，超 B 直接失败。对 stderr 非记录流缓冲有界内容至结尾/中断，再整体脱敏。若需保持更细粒度实时输出，状态化脱敏器必须在识别 Bearer/token/sk- 前缀后把后续敏感段全部替换直到分隔符，不用固定 N 字符 lookbehind 假装安全。本期优先完整记录发布，跨记录敏感键值由共享脱敏状态连续处理；结构化 JSON 原始输入可以在内存解析，但传给 onEvent 的对象、text/structured/message/tail/error cause 全部递归按共享规则脱敏。公开终止结果不能附 raw buffer。未识别的任意秘密不承诺自动识别，测试覆盖现有规则及随机 canary。

中断先原子设置 `interruptReason='OUTPUT_LIMIT'`、`writeClosed`，再 SIGTERM 进程组，限时 SIGKILL 兜底、销毁管道、detach 回调，最后唯一 settle。迟到 close/error 不得成功、不再 onEvent；不能为 emitStderr 再突破 E。返回 `code/reason='OUTPUT_LIMIT',truncated:true`、累计与保留计数、killScope；节点和 run 错误包装不丢 code。日志和诊断输出先脱敏后 clip。POSIX 记录父/孙进程都退出；非 POSIX 标 process 降级和 orphanWarning，不把未验证杀组写成通过。

## 6. R4：外部来源与可信索引隔离

POST /events 保留原白名单与整批校验，生命周期 kind 仍整批 400、零追加。服务端覆盖每条 `extra.source='external',producer='external',authority='unverified'`，剥离来客授信 token、执行登记和 terminalScope/epoch 等受保护元数据；data 原文仅作未验证观察。来客 executionId 可以展示为声明值，但不能登记可信执行。

聚合在 artifact/hash/owner、latest、conflict、current attempt、stale fail、review/findings 等任何索引之前先分区 external。外部同 path、同 itemId、同 ruleSetId 的 pass/fail 均不能覆盖内部证据、制造内部冲突或清掉宿主失败。外部统计和时间线可增加，权威 headline、通过率、质量 state 和 run.status 不变。旧无 source 的事件进入 legacy 来源未知，不猜测为 host。

摘要、UI、markdown 导出统一显示“外部未验证”；导出保留观察附录但权威通过计数排除 external。禁止只改后端字段却让前端根据裸 verdict 自行渲染绿色。后续可信签名集成另立契约，本期没有“信任全部 external”开关。

## 7. R5：保存的检查命令与宿主执行报告

### 7.1 配置与防注入

```json
{"check":{"command":"npm test","expectExitCode":0,"reportPath":"reports/unit.json","timeoutMs":600000}}
```

`node.check` 仅允许 stage 节点，command 必填非空≤2000 字符，拒 NUL；expectExitCode 默认 0、整数 0–255；timeoutMs 默认 600000、整数 1000–1800000；reportPath 可选、安全相对普通文件路径。拒绝绝对路径、Windows drive/UNC、NUL、`..` 穿越，拒绝全路径链软链；执行前后都核 cwd 包含关系。`normalizeNodeCheck` 必须保留可诊断非法配置供 validate 报错，不能丢为未配置；空 UI 表单显式删除 check。旧 `extras.check` 不自动升级为可执行命令。

只有保存流程显式配置可执行，模型 prompt、run inputs、产物和 HTTP start body 不得覆盖 command/env/cwd；队列快照固定，restart 是新 run 使用当前保存配置。独立 `FLOW_STUDIO_ALLOW_HOST_CHECKS=1` 默认关闭，配置 check 而开关关则启动前 400/HOST_CHECKS_DISABLED；只读令牌不能保存或启动含 check 流程，复用现有全权鉴权，不添加执行旁路。

需求明确支持静态 shell 字符串和 `exit 1`。POSIX `buildHostCheckInvocation` 固定产生 `file='sh',argv=['-c',savedCommand]`，`spawn(...,{shell:false,stdio:['ignore','pipe','pipe'],cwd:actualNodeCwd,env:filteredEnv,detached:true})`。完整静态 command 是一个 argv，不 split、不插值、不走 custom 的 `{prompt}` 模板、不注入 prompt 文件/stdin。shell:false 防 Node 再套一层 shell，不意味着 shell 脚本被沙箱隔离；显式全权命令本身可以执行 shell 语义。使用实际节点 cwd，worktree 开启时即 worktree；保留 PATH/必要项目变量，仅剔除认证凭据及已登记敏感变量，不粗暴删除全部 DSH/FLOW_STUDIO。命令摘要脱敏，digest 对精确命令字节计算。无 POSIX shell/cwd、stub 环境则 skipped/unknown，不能伪造成功。

### 7.2 执行时序与状态

`_executeNode` 取得正式结构化结果并 `_writeStructured` 后，await `_runHostCheckOnce`，宿主结果持久化完成后才让循环写 node/end 和调度 next/reject。去重键为 `(runId,nodeId,attemptId,checkId)`，先缓存 Promise 再 spawn，重复 idle/close 回调共享同一执行；新 attempt 重新执行。节点业务已失败则不启动检查，持权时记录 skipped 和原因；stop/timeout 取消既有检查；lease-lost 只允许 R1 的 end，不能为了 skipped 再写 check/artifact。

宿主检查失败只影响 quality，保留 agent 原 verdict 和 next/reject；在线性流程中应能出现 node/end passed、后继正常执行、run/end done 与 quality fail 并列。不得悄悄新增自动打回。宿主结果写失败时不得继续装作已检查过：将检查状态 unknown 并记录运行错误，若存储完全不可写则按正常 I/O 失败路径收口，绝不制造 authoritative pass。

### 7.3 可信执行记录与报告

宿主私有 `verification/<executionId>/` 存储执行记录和报告副本，由 runstore 专用接口创建、写入和验证；普通 `_writeArtifactFile`、HTTP artifact/write、模型指定路径均不能覆盖或登记它。可信登记来自宿主内部 capability 和实际 spawn 完成记录，不能从 `producer='host'` 字符串导入。宿主与模型同 OS 用户，文件权限不构成敌对本地进程隔离；本期防的是事件/产物自报洗白，摘要验证还要核对受控登记与哈希。若要抵抗同 uid 任意宿主文件篡改须独立进程密钥/隔离，超出本期能力，不能声称实现。

执行记录最小载体：`executionId,runId,nodeId,attemptId,checkId,commandDigest,expectedExitCode,exitCode,startedAt,finishedAt,reportPath,reportSha256,state,reasonCode,killScope,truncated`。随机 executionId，实际 cwd 用脱敏摘要；`run.checks` 保存本次私有命令快照和 digest，公开详情仅回安全摘要，原命令不直接回显。

没有 reportPath 时，宿主生成的完整执行 JSON 是报告；有 reportPath 时，执行前捕获 fingerprint，执行后要求新建或更新，检查 inode/mtimeNs/ctimeNs/size/hash，不能只凭 startedAt 或内容 hash（重写相同内容应合法）。安全打开同一 fd 后有界读、前后 fstat 确认未变，复制到专用目录；报告上限定 1MiB，读 limit+1 检出超额，禁止 readFile 无界读取。报告先脱敏完整复制，`reportSha256` 绑定最终持久化副本字节；若保留源 hash 则另记 `sourceReportSha256`，不得混用。过大不截断后判 pass；缺失、未更新、越界、读取时变化均不通过。原 cwd 文件后续变化不覆盖已捕获宿主副本；副本删除或 hash 破坏使证据 unknown，保留实际执行事实。

报告执行前 fingerprint 同样先核普通文件，安全 nonblocking/no-follow open + fstat，拒绝 FIFO/socket/device；存在的大文件执行前也只读 limit+1，不做无界 hash，缺失允许本次生成。执行前后文件读取都服从可取消检查时限，不能先 open FIFO 永久挂住。spawn 前后均复查组合 AbortSignal，避免注册监听窗口漏取消；spawn 成功但缺 pipe/初始化失败也必须杀已创建进程。

沿用 `check/form` 和 `artifact/write` 指向 verification 报告，不新增 kind。check/form 必填固定 `ruleSetId='host:<nodeId>'`、`executor='host'`、`ruleSetVersion='0.11'`：成功 data.state=pass、passedChecks=1、totalChecks=1；exit/报告/spawn/timeout/OUTPUT_LIMIT 失败为 fail、0/1；无法执行/取消/节点先失败为 skipped、0/1，聚合将 skipped 当 unknown；既有 CHECK_STATE 没有 unknown，禁止写该值。`extra` 加 source/producer/authority/verification 元数据，reasonCode 承载细因；失权后禁止追加。宿主 pass 条件是实际 exitCode==expectedExitCode、执行完成且报告条件全满足；非零期望退出码同样支持。

## 8. R6：权威规则和 quality 判定表

`authority` 是验证结果，不是调用者可声明的权限。保留原 claimed 计数与 verdict，新增 `claimedPassed/authoritativePassed/authoritativeTotal/authoritativePassRate` 和 `coverageRatio`。authoritativePassRate 的分母是已验证权威条目数；coverageRatio 的分母为应验条目数，缺项不得因缩小分母刷绿。旧 `passed` 仅可标“自报”；主通过率/绿 pill 使用权威通过数除应验总数，不拿 claimed 补分子。未明确分母时主通过率 unknown。

`resolveVerifiedExecution` 同时核对宿主登记、run、生产 node/attempt/checkId、固定 commandDigest、真实结束结果和报告完整 hash；peer 引用保存 producerNodeId/producerAttemptId，允许消费者节点不同，但生产 attempt 必须仍有效。跨 run、伪 executionId、旧 attempt、缺文件、损坏 hash、仅 executedAt/tool 名称/普通写文件/自填 producer 都不授权。本期签名验证可不实现；未验签一律 claimed。纯函数无文件验证器时不默认通过，客户端消费服务端验证摘要。

| 来源/现象 | evidence authority/状态 | 对 quality 的影响 |
|---|---|---|
| 当前有效宿主执行失败（退出码不符、超时、输出限制、报告缺失/陈旧/过大） | authoritative failure；报告后来损坏则验证 unknown，原执行失败事实仍保留 | fail，优先于任何 claimed pass、无关 host pass 和 missing |
| 当前宿主执行且对应报告验证成功 | authoritative host pass | 仅对应 check/验收映射可通过，不外推其它测试/验收 |
| 独立节点引用同 run 有效宿主执行链 | authoritative peer | 仅该报告明确覆盖的项可通过；不能借一项 host check 让全部模型计数变权威 |
| tests 29/29 无 ref、engine 自写报告、跨节点转写/正确 sha256 | claimed；权威状态 unknown | 无当前/待复验 host 失败及其它内部失败时 quality unknown，不绿；存在失败仍 fail；并列展示自报 29/29 |
| external pass/fail/伪 host/同 path | unverified | 不进入权威指标、冲突或质量优先级；显示外部未验证 |
| 旧无来源报告、只有 executedAt 或工具名、验证器缺失 | claimed/unknown | 不绿，展示历史来源未知/缺执行链 |
| 新 attempt 无检查结果或只报 pass | unknown；旧宿主失败为待复验未解除 | 旧 fail 不能被更大 seq 或更高 attempt 的自报洗白；新有效相同 check 执行成功才能解除 |
| 全部应验项有权威 pass，覆盖完整、执行完成 | authoritative pass | 未解决 P0→fail，P1/P2→warn（不能绿）；无阻断时才按既有返工/进度规则判 pass 或 warn |
| stub 或平台无法实际执行 | unknown/skipped | 永不据此 pass |

聚合优先级：当前有效或尚未解除的 host fail → fail；其后缺权威覆盖/校验失败 → unknown；其后既有进度、返工、未解决发现规则 → warn/pass。保留模型失败声明作为风险来源，不把它转写为宿主失败；未被权威复验解除的内部失败仍阻止绿色。review/findings 的程序性结论可以保留，但不能代替 tests/checks/acceptance 的执行来源。summary/quality/audit/flow_watch/UI/导出必须共用上述投影，不能保留浏览器的旧“任一 peer 即全指标通过”算法。

## 12. 实现顺序与可审查提交边界

1. **C0 契约与测试骨架**：固定 env/error/schema、可注入续租/时钟/runner；列全生命周期读者、外部索引、写入入口。新增模块进入构建清单；每个新增用例先登记 mutation。先不宣称功能完成。
2. **C1 R1**：跨进程 mutation 锁、持久epoch/owner、条件写、finalizeEpoch 与所有读端一批完成；双循环 finally 统一。先通过旧实例零写及双owner/崩溃窗口测试，才能接入新host check。
3. **C2 R2**：进程共享admission与runtime所有入口、HTTP/工具429、排队查询取消、restart可重试child；验证无Engine/worktree/session提前创建及幂等release。
4. **C3 R3**：共享有界输出与脱敏、真进程RSS/杀组，再改外部executor包装；此基础供R5复用。
5. **C4 R4+R6信任底座**：强制stamp、索引分区、可信执行登记验证接口、旧run降级和UI/导出；暂时没有host执行记录时都unknown，不能补造pass。
6. **C5 R5+R6正向链**：保存检查配置/快照、宿主runner/报告、新attempt复验、UI并列执行与质量。验证真正spawn与exit 1反例，再启用权威正向通过路径。
7. **C6 独立测试/审查**：全量门禁、逐用例mutation、R1×R5联测、R4×R6洗白攻击；独立节点验收报告签收后方可发布。无push/publish/服务重启。

C1、C3、C4可按文件分工实现但须顺序合并依赖；R5不能先于R1取消链和R3限额上线，R6不能在R4入口隔离前信任producer。每组提交都须保持旧测试绿；最终23文件/855组是已复验基线，新增用例后按实际汇总增加，不固定新总数。
