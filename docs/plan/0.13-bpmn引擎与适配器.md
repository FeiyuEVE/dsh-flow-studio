# 0.13 需求：BPMN 流程引擎 + 可插拔 agent 适配器（草案）

> 状态：**草案，等用户拍板 §0 的五个问题后进入实现**。性质：0.13 是一次引擎内核与画布的双重替换，不是增量优化。
> 依据：用户在 2026-11-11 的方向指令；`docs/design/08-state-machine.md` §10 的旧否决记录（本次**主动反转**，理由见 §1.3）。

## 0 已拍板（2026-11-11，用户口头决定）

1. **画布体积：不设限制。** 不走双 chunk、也不抬门槛——直接把 `scripts/build.mjs` 的硬失败改成**只报数**（继续打印 `lib/client.js` 字节数，超了不拦）。依据：用户明确「不要加限制」，且宿主侧本就没有大小硬限制（`scripts/build.mjs:183-186` 已实测 combo 路由 428 KB 仍 200，524,288 是我们自设的）。
   **补充（2026-11-11 实测后）**：虽然不设上限，但真的按单文件装会把首屏 gzip 从 151 KB 抬到 278 KB（每次都付，即使从不打开工作流面板），所以仍按**懒加载 chunk** 做：主包 ≈247 KB / gzip 72 KB，画布 chunk `client.bpmn.js` ≈677 KB / gzip 206 KB，首次开画布才加载。这是性能选择，不是限制（宿主原生支持 `client.<name>.js` chunk，实测 `dsh-client-ui-schedule` 的 785 KB 单文件也照常 200）。
2. **旧模板：一次性迁移到 BPMN。** 写转换器把 `flows/<id>.json` 转成 BPMN XML（节点 / 边 / 分支条件 / 节点配置全映射），转完旧 JSON 归档只读，不双轨。
3. **打回：不保留一等语义，彻底条件化。** 引擎只认 BPMN 标准：回退就是「带条件的反向 `sequenceFlow`」；现有 `reject` 概念与 `reject/trigger` 事件退役，改为按「实际走过的 sequenceFlow」记录（`flow/taken`）。旧模板的 `verdict === 'reject'` 输出契约迁移成普通 FEEL 条件；旧 `maxRounds` 落到回退连线上的 `fs:maxRounds`，按通用的「连线通过次数上限」执行（模板层约束，不是引擎的打回概念）。
4. **hook 不对等：能力协商 + 显式降级留痕**（不假装三者能力一样，不支持的能力写进运行记录与 UI）。
5. **人工任务：GUI 待办面板 + HTTP 双入口**，一套状态与一份待办表、两个入口（GUI 用宿主登录态鉴权，HTTP 走插件令牌）。新引擎没有独立状态机：实例 `status` 是普通字段，由 runtime 按事件写；取值对齐 Camunda 8 的 `ACTIVE/COMPLETED/SUSPENDED/CANCELED`，没有 failed、也没有「卡住」状态（卡住是业务判断）。

这五条决定了下文 §3 / §5 的形态；研究结论只补事实、不改这五条。


## 1 为什么要换（问题陈述）

### 1.1 现状的硬限制

- 引擎只有两种路由语义：`next` / `reject`（`docs/design/08` §8 已经排了 P2 条件分支、P3 并行 join 但没做）。用户要的「多路分支、人工节点、HTTP 节点、按条件汇聚」在现模型里没有位置。
- 节点只有「agent 角色」一种类型，`executor` 只有 `dsh | codex | custom` 三种，且 `executor` 只是命令行差异，**没有适配器抽象**（`src/executor.js` 1229 行里三种实现揉在一起），无法承载「per-provider 的 hook / skills / 系统提示词」。
- 流程模板与运行实例**共用一套 JSON 形状**（模板 `flows/<id>.json`、实例 `runs/<runId>/run.json`），模板改了、历史实例的语义就跟着漂。

### 1.2 用户要的五件事

1. 引擎换成 **BPMN 2.0**（`bpmn-engine`），画布换成 **bpmn.io**，侧栏可自定义。
2. 节点类型可配：**人工参与** / **agent 参与**（agent 再选 provider/适配器：codex、Claude Code、DSH…）。
3. 每个 agent 节点可配：**生命周期 hook 脚本/插件**、**skills**、**系统提示词/角色设定**、**是否团队（多 agent）**。
4. **hook 必须按 adapter 分别抽象**（codex 的 hook 机制与 Claude 的明显不同），各自做适配器。
5. **模板域与实例域彻底隔离**；**HTTP connector** 做扎实，方便和外部系统联动。

### 1.3 与旧决策的关系（诚实记录）

`docs/design/08-state-machine.md` §10 的否决表把 `bpmn-engine` 否掉了，理由是「BPMN 2.0 子集 + XML 建模，收益同 Camunda 但维护面更小」——**当时的需求只有 pass/reject 两种路由，引入 BPMN 是纯成本**。现在需求变了（多路条件、人工任务、HTTP 节点、per-adapter hook），这条否决的前提不成立，因此反转。旧结论保留在 08 册里不改写，本次反转在 0.13 的版本说明里记一笔。

## 2 领域隔离（模板 vs 实例）

两个域**不同的目录、不同的 id 空间、不同的生命周期**：

```
$DSH_HOME/flow-studio/
  definitions/<definitionId>/           # 模板域：不可变、可版本化
    meta.json                           # {name, version, hash, createdAt, tags, owner}
    <version>.bpmn                      # BPMN 2.0 XML 正本（sha256 进 meta）
  instances/<instanceId>/               # 实例域：一次运行一个目录
    instance.json                       # {definitionId, definitionVersion, definitionHash, status, variables…}
    events/<activityId>/<attempt>.jsonl # 事件流（沿用现有分片模型）
    variables.json                      # 变量快照（可选，便于恢复）
```

硬规则：

- 实例启动时**冻结** `definitionId + version + hash`；模板后续被编辑**不影响**已有实例。
- 实例只读模板（快照副本进实例目录，防定义被删）。
- 事件流与 `instance.json` 沿用现有 append-only + 原子写 + 跨进程 `meta.lock`（`src/runstore.js` 的成熟部分保留）。
- BPMN XML 是**模板正本**；JSON 只作为「解析后的投影」存在内存里，不再落盘成第二个真相源。

## 3 引擎语义映射（研究已定稿，实测报告见 `0.13-研究-bpmn-engine.md`）

`bpmn-engine@26.0.6` 的实测结论先摆三条：**挂起/恢复是原生的**（`getState()` / `recover()` / `resume()`，已在独立进程跑通「等人工 → 落盘 → 杀进程 → 重启 → 接着跑」）；**活动事件只从 `execute({listener})` 的 listener 出来，`engine.on(...)` 收不到**；**自定义命名空间入口是 `moddleOptions`（26.x 里 `moddleExtensions` 已失效）**，扩展属性会被序列化进 `activity.behaviour`、`extensionElements` 以 `values[]` 可读（均已实测）。

| 需求 | BPMN 元素 / 做法 | 实测状态 |
|---|---|---|
| 人工参与节点 | `bpmn:userTask`（本质是永久 wait 的 signal task） | ✅ 实测。完成 = `execution.signal({id, executionId, payload})`；查询「谁在等人」= `execution.getPostponed()`。**没有** assignee / 认领 / 表单 / 超时，任务表必须我们自己做（与 §0.5 的 GUI+HTTP 双入口重合） |
| agent 参与节点 | `bpmn:serviceTask` + `dsh:` 扩展（节点类型 / provider / adapter / skills / hooks / 角色提示词） | ✅ 实测。handler 两种注册法；未注册 → fatal `<id> service not defined` |
| HTTP connector | `bpmn:serviceTask` + `dsh:nodeType="http"` | 由我们自己的 handler 实现（fetch + 超时/重试/变量映射/鉴权头脱敏），不引第三方 connector |
| 分支 | `exclusiveGateway` + `sequenceFlow.conditionExpression` | ✅ 实测。**表达式必须走 FEEL**（见下方红线） |
| 打回 / 回退 | 反向 `sequenceFlow` + 条件 | ✅ 实测（exclusive 默认流回指上游 serviceTask，重跑后再次进入 userTask，循环计数正确） |
| 并行 | `parallelGateway` / `inclusiveGateway` / 多实例 | ✅ 支持，但**有开放 bug**（见红线 2）→ MVP 禁用 |
| 超时/兜底 | boundary `timerEventDefinition`（中断式/non-interrupting） | ✅ 实测（`PT0.15S` 150ms 触发并中断 userTask）；cron 需扩展，先用 ISO duration |
| 子流程复用 | `callActivity` / embedded / event subProcess | ⚠️ 支持但有坑：`calledElement` 解析不到时**变成 wait-state 而不是报错** |

### 3.1 两条红线（研究实测出来的，不是理论风险）

1. **FEEL 条件会静默恒真。** 不装 FEEL 扩展时，`language="feel"` 或 Camunda 8 风格的 `= a > 1` 被当成**字符串/路径**，实测 `amount=0` 仍走 `yes` 分支，**流程走错且不报错**。而内置的 `language="javascript"` 走 `node:vm`，实测可逃逸到 `process`（`this.constructor.constructor('return process')()`），**不是沙箱**。
   → 定策：**只允许 FEEL**，依赖 `feelin@8.2.0`（MIT，非那个周下载 72 的 `@0dep/bpmn-extensions`）自己注册表达式处理器；**加载期做语言白名单**（出现 `javascript`/裸 `=` 无语言 → 拒绝发布），并留一条反例单测：`= false` 必须走默认流。
2. **「并行汇聚 + 成环」会提前通过**（上游 issue **#204**，2026-11-05 仍 open）。我们的核心模型正好是「回退边重跑」，一旦上层有 parallel join 就会多跑/错跑。
   → 定策：**MVP 禁用 parallel / inclusive join**；团队（多 agent）走**节点内 fan-out**（适配器层起 N 个会话/进程），不用 BPMN 并行网关。将来要并行，先自己 fork `ParallelGateway` 用 token 计数重写并补回归。

### 3.2 变量、IO 与快照（决定实现细节）

- **输出写回**：`settings.assignOutput:'id'`，活动输出落 `environment.output[id]`；变量作用域是 definition 环境的克隆，**不要读 `engine.environment.variables`**（实测恒为 0），要经 `execution` / activity api 读。
- **IO 映射**：`camunda:inputOutput` **零支持**；统一用 `zeebe:ioMapping` 的语义（我们自己解析，不引 `@0dep`）。
- **快照**：`engine.getState()` 7–18KB 且**不可裁剪**（issue #137：裁掉 broker/queue 就恢复不了）。只在 `activity.wait` 与 `activity.end` 落盘 + 去抖，state 存 `instances/<id>/state.json`（复用现有原子写 + `meta.lock`）。
- **内存**：实测 ≈**450 KB/实例**、1000 常驻 ≈435 MB、单线程同步启动 3.4s。→ 活跃实例 LRU（上限 100–200），其余只留 state JSON、按需懒恢复；`sourceContext` 必须缓存（不缓存 7.8ms/实例，缓存后 3.4ms）。
- **恢复**：`recover()` 只能给非运行中的 engine（`cannot recover a running engine`）→ 重启路径固定为「新 Engine + `recover(state)` + `resume({listener})`」。

## 4 Agent 适配器与 hook 抽象（研究已交付，见 `docs/design/09-agent-adapter-hooks.md`）

### 4.1 关键更正（推翻本计划初稿的前提）

初稿写的是「codex 没有原生 hook，只能进程级包装」——**这是错的**，实测 `codex-cli 0.167.0` 已有完整 hooks 框架（本机 `--dangerously-bypass-hook-trust` 存在；官方文档 <https://learn.chatgpt.com/docs/hooks.md> 实测 200）：
`SessionStart/End`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`Pre/PostCompact`、`Stop`、`SubagentStart/Stop`、`Pre/PostModelRequest`、`Interrupt`；`PreToolUse` 支持 `permissionDecision:"deny"` 阻断与 `allow + updatedInput` 改写入参；`exit 2` + stderr 也能阻断；非 managed hook 按 hash 信任，自动化可 `--dangerously-bypass-hook-trust`（只在「hook 源可证是我们自己生成的」时用）。

Claude Code 的 hook 面更宽（还多 `PostToolBatch`、`Notification`、`InstructionsLoaded`、`TeammateIdle`、`MessageDisplay`、`StopFailure` 等，5 类 handler）。**两家都不是「有/没有」，而是事件面、阻断/改写能力、信任模型不同**——这正好印证「分别抽象、各自适配」。

DSH 侧：fork 里 `experimental/hook-protocol` + `hooks-codex` + `hooks-claude-code` 是现成的桥，但**没有随宿主发布**（运行中的 dsh `node_modules/@deepseek-ai/` 里没有任何 `hooks-*`），所以只能**照语义自建薄桥**，不能 import。

### 4.2 接口（定稿见 design/09 §B-1）

```
AgentAdapter
  probe() / capabilities() / plan() / start() / resume()
  events(): AsyncIterable<AdapterEvent>          // 统一事件流
  hooks(): HookBridge                            // 能力协商，不支持显式降级
  materialize({ systemPrompt, roleCard, skills }): PreparedInputs
  cancel(cause)
```

能力三级：`native | emulated | unsupported`，**每一项必须带 evidence（`--help` 摘要 / 文档 URL / 宿主 file:line）与 fallback**；`unsupported` 在 admission 阶段拒绝或写 `hook/degraded` 事件，UI 标注，绝不假装。

规范 hook 事件 8 个：`session.start` / `session.end` / `prompt.submit` / `tool.pre` / `tool.post` / `turn.stop` / `error` / `before_compact`。
三列映射表与逐适配器物化方式（codex=`-c developer_instructions` + 临时 `CODEX_HOME/skills`；claude=`--append-system-prompt-file` + `.claude/skills` 或 `--plugin-dir`；DSH=`ctx.systemPrompt.section()` + `ctx.skills`）见 design/09 §A/§B。

### 4.3 团队语义（诚实版）

DSH 原生（subagent 工具族）；codex 原生 `spawn_agent` 或 N 进程 fan-out；Claude 原生 subagents 但**不可编程编排**。外部 CLI 一律**观测不到成员会话**，所以 `executor.js:202` 的 team 禁令保留，只做 `single` / `process-fanout`，不伪装原生编排。

### 4.4 handler 类型差异（影响实现工作量）

- **Claude Code 支持 `type:"http"` handler**：hook 事件直接 POST 到我们的插件端点，端点同步返回 `permissionDecision` 就能阻断/放行——**不用落脚本、不用装文件**，这是最轻的接入方式。它还支持 `mcp_tool` / `prompt` / `agent` 四类 handler。
- **Codex 只有 `command` 与 `mcp_tool`**（`prompt`/`agent` 解析后跳过）：要接我们的判定，要么生成一个受信 command 脚本（配合 `--dangerously-bypass-hook-trust`，仅当脚本确实由我们生成），要么提供一个 MCP server 让 hook 以 `mcp_tool` 调用。

结论：Claude 走 HTTP handler（零脚本），codex 走「每 run 生成 `CODEX_HOME/hooks.json` + 受信脚本」或 MCP；两条路径的差异必须在适配器里实现，而不是在引擎里特判。

### 4.4 安全边界（hook = 任意代码执行）

来源三选一（节点内联 / 仓库 `.flow-studio/hooks/` / 插件市场）、digest 信任、stdin JSON + 白名单 env、阻断型 30s / 观察型 60s、`session.end` ≤3s、失败策略 `strict|record|retry`，全部落 `hook/invoked|result` 审计事件。

## 6 风险（研究实测后重排）

**阻断级（已在 §3.1 定策，但要写进发布门禁）**

1. **FEEL 恒真 / JS 逃逸**：不装 FEEL 扩展时条件恒真且静默；内置 `language="javascript"` 用 `node:vm`，实测逃逸到 `process`。→ 只许 FEEL + 加载期语言白名单 + 反例单测。
2. **并行汇聚 + 成环提前通过**（上游 #204 open）。→ MVP 禁 parallel/inclusive join；团队走节点内 fan-out。

**高**

3. **内存与单线程**：450 KB/实例、1000 常驻 435 MB、启动同步阻塞 3.4s。→ 活跃实例 LRU + 懒恢复 + 缓存 `sourceContext`。
4. **快照不可裁剪**（#137）：裁了 recover 就坏。→ 只在 wait/end 落盘 + 去抖，别手改 state。
5. **供应链**：单人维护（paed01 贡献 598/608）、5 个 peer 里 3 个同作者、FEEL 那个周边包周下载 72。→ 锁版本、只用 `feelin` 不用 `@0dep`、关键补丁 fork 自持。
6. **hook = 任意代码执行**（design/09 §C）：必须 digest 信任 + 超时 + 白名单 + 审计，绝不能让节点配置变成宿主 RCE。
7. **迁移破坏审计口径**：现有指标建立在 15 种事件 kind 上，`reject/trigger` 退役后要重新对齐 → 硬约束「沿用既有事件模型 + 只增 `flow/taken`」。

**中**

8. 活动事件必须走 listener（`engine.on` 收不到）→ 适配层统一封装，否则「等不到事件」类 bug 频发。
9. 无「全部活动进入 wait」聚合事件（上游 #195）→ 自己按 `activity.wait` 计数判断再落盘。
10. 多实例缺 `loopCardinality`/collection 直接 fatal → 发布前做模型校验。
11. `camunda:inputOutput` 零支持 → 统一 `zeebe:ioMapping` 语义，避免作者混用两套命名空间。
12. 大版本升级会破坏 state（stateVersion/engineVersion）→ 快照入档版本号，resume 版本不符直接拒绝。
13. 双倍维护（0.13 期间老引擎/老画布并存）→ 每阶段都有回滚点；**不合规就替换，不做兼容双轨**（用户 2026-11-11 定调：没有历史数据兼容要求，不要灰度开关）。

## 9 依赖与组件决策（用户口径：**能引入组件就用组件，不自造轮子**）

**原则**：凡是社区/官方已有成熟实现的，一律用组件或它的官方扩展点；只有「我们自己的域」才自己写。

| 需求 | 用什么 | 版本 | 形态 |
|---|---|---|---|

**两条修正（推翻本计划早先的决定，原因是上述用户口径）**

1. ~~不用官方 properties-panel、自写右侧栏~~ → **改用官方 `bpmn-js-properties-panel`**，自定义字段走它的 `PropertiesProvider` 扩展点（官方支持的扩展方式，不是自己造面板）。代价：画布 chunk 从 gzip 206 KB 涨到约 **526 KB**（实测 bpmn-js+panel+CSS = 1,938,418 B）；主包不受影响（仍 ≈247 KB / gzip 72 KB），因为画布是懒加载 chunk。
2. ~~自己解析 `zeebe:ioMapping`~~ → **用 `zeebe-bpmn-moddle` 描述符**，我们只写「读出来 → 用到 adapter 入参」这一段映射。

**仍然自己写的部分与理由**（不是轮子，是域）
- 人任务表（`userTask` 的 assignee/认领/完成）——`bpmn-engine` 明说 forms/tasklist 是 host 的事；我们已有 GUI+HTTP 双入口的契约。
- `AgentAdapter` 与 hook 桥——DSH 专有（design/09），三类 agent 的能力协商没有现成组件。
- 表达式**白名单校验**（安全策略，不是求值器）、实例 LRU 之外的域隔离（定义不可变 / 实例钉版本）。
- 不引 `@0dep/bpmn-extensions`（周下载 72、Node≥22）：它提供的正是 `zeebe-bpmn-moddle` + `feelin` 的组合，直接引官方两个包更稳。

**License 义务**：`bpmn-js` 是 **bpmn.io License**（MIT + 必须保留 `https://bpmn.io` 水印且不得遮挡，自用同样适用）→ 画布保留官方水印、不加 CSS 隐藏；`bpmn-js-properties-panel` / `@bpmn-io/properties-panel` 是 MIT；`lru-cache` 是 BlueOak-1.0.0（宽松许可，但要在 `THIRD-PARTY.md` 明确列出）。

## 10 0.13.0 集成契约（待 `src/bpmn-runner.js` 落地后按实际签名微调）

### 10.1 新增 HTTP 路由（挂在现有插件路由前缀下，沿用现有鉴权与 `connection` 拒绝策略）

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/definitions` | 列定义（含每份的版本列表与最新 hash） |
| `POST` | `/definitions` | 保存一个新版本（body: `{id?, name, xml}`；返回 `{id, version, hash, created}`；同版本不同 hash → 409） |
| `GET` | `/definitions/<id>` | 读某定义的全部版本元数据 + 指定版本 XML（`?version=`） |
| `POST` | `/instances` | 建实例并启动（body: `{definitionId, definitionVersion?, variables?}`） |
| `GET` | `/instances` | 列实例（`?definitionId=&status=`） |
| `GET` | `/instances/<id>` | 实例详情（状态、变量、`pendingTasks[]`、`lastSeq`） |
| `GET` | `/instances/<id>/events` | 事件流（按 seq 合并） |
| `GET` | `/instances/<id>/tasks` | 当前待办人工任务 |
| `POST` | `/instances/<id>/tasks/<activityId>/complete` | 完成人工任务（body: `{payload, decidedBy}`）——**GUI 与外部系统同一入口** |
| `POST` | `/instances/<id>/stop` | 中止实例 |

### 10.2 服务处理器的来源（0.13.0 先薄接，0.13.1 换成正式适配器）

- `executeAgent`：0.13.0 先调现有 `src/executor.js` 的既有能力（`dsh` 走宿主会话、`codex`/`custom` 走外部进程），**不重写**；0.13.1 再包成 `AgentAdapter`。
- `executeHttp`：Node 内置 `fetch`，带 `timeoutMs` / `retries` / 变量映射 / **鉴权头脱敏后才进事件**。
- `onTaskWait`：写进 `instance.json` 的 `pendingTasks`（或由 instance-store 的 `updateInstance` 维护）。**不再另落 `task/wait` 事件**——等待本身就是 `activity/wait`，同一事实不写两条（0.13.0 实现后修正本行）。
- `onEvent`：`process/start|activity/start|activity/end|activity/wait|flow/taken|process/end|error` 直接进实例事件流（分片 `events/<activityId>/<attempt>.jsonl`）。
- **`flow/taken` 是新一等事件**（取代 `reject/trigger`）：带 `flowId` / `from` / `to` / 条件表达式与结果。

### 10.3 与老引擎的关系（替换，不双轨）

- 老 `runs/`、`src/engine.js`、老画布在 0.13.3 画布替换完成前**暂时保留可跑**，完成后删除；不做长期双轨、不做兼容适配。
- 新 `instances/` 走新引擎；**新的事件流在 0.13.0 不接老审计**，审计口径在 0.13.1 重写（沿用 0.12.3 的原则：宁可 unknown 不给假绿）。
- `GET /health` 增 `bpmnEngine: true/version` 与 `definitions/instances` 计数，便于重启后一眼确认加载的是新内核。

### 10.4 环境变量（没有开关）

不设灰度开关：新路由常开，直接替换。只保留运行期护栏：

| 变量 | 默认 | 作用 |
|---|---|---|
| `FLOW_STUDIO_BPMN_MAX_ACTIVE` | `100` | 活跃实例 LRU 上限（内存护栏） |
| `FLOW_STUDIO_BPMN_ACTIVITY_TIMEOUT_MS` | 沿用 `nodeTimeoutMs` | 单活动超时 |
| `FLOW_STUDIO_HUMAN_TASK_TTL_MS` | 不设 | 人工任务停留上限（超时策略 0.13.0 只告警不自动失败） |

`GET /health` 在开关打开时返回 `bpmn: { enabled: true, engine: '26.0.6', definitions: N, instances: M, active: K }`，重启后一眼能确认加载的是新内核。
