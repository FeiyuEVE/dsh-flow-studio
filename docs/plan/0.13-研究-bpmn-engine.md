## 2. BPMN 覆盖度

**结论：Common Executable 子集覆盖得相当完整（含成环、边界事件、多实例、事件子流程）；真正的缺口只有 4 个：复杂网关、消息关联键、camunda:inputOutput、以及「并行汇聚 + 成环」这个已知 bug。**

权威依据是作者自写的 https://github.com/paed01/bpmn-elements/blob/master/docs/Conformance.md （声明目标 = BPMN 2.0 Common Executable），下表逐项核对源码/实测：

| 元素 | 支持度 | 说明 / 证据 |
|---|---|---|
| `serviceTask`（自定义 handler） | ✅ 实测 | 两种注册：`implementation="${environment.services.x}"`（docs/ServiceTask.md）；或 extension 里 `activity.behaviour.Service = MyService`（我用的后者）。未注册 → fatal `<id> service not defined`（`bpmn-elements/src/tasks/ServiceTask.js:50`，实测报错） |
| `userTask` | ✅ 实测 | 本质是 wait-state，完成 = `execution.signal({id, executionId, ...})`（`tasks/SignalTask.js:54` 发 `activity.wait`，`accepts:['signal','error']`） |
| `manualTask` | ✅ 文档 | 与 UserTask 同实现（`ManualTask.js` 继承 `SignalTaskBehaviour`） |
| `scriptTask` | ⚠️ 部分 | 需注册 scripts 引擎；内置只跑 `language=javascript/js`，实现是 `node:vm` 的 `new Script(...).runInNewContext()`（`bpmn-engine/src/JavaScripts.js:55`）；其它语言直接返回 undefined（不报错） |
| `businessRuleTask` | ⚠️ 别名 | 等同 serviceTask，需自带 DMN（推荐同作者 `dmn-elements`，基于 feelin） |
| `sendTask` / `receiveTask` | ✅ 文档 | send = serviceTask 别名；receive = 原生 message wait，按 `messageRef` 键控 |
| `callActivity` | ⚠️ 文档 | 支持调 Process；`calledElement` 解析不到时**变成 wait-state**而非报错（Conformance「Design decisions」#3） |
| `subProcess`（embedded / event） | ✅ 文档 | Conformance 表明确 embedded + event sub-process |
| `parallelGateway` / `exclusive` / `inclusive` / `eventBased` | ✅ 实测(exclusive/parallel) | 四类都在；`complexGateway` 明确不支持 |
| `timerEventDefinition` | ✅ 实测 | `timeDate/timeDuration/timeCycle`；ISO 循环 OK，**cron 需扩展** `TimerEventDefinition`（或 `@0dep` 的 cron 版）。实测 `PT0.15S` 边界定时器 150ms 触发 |
| `messageEventDefinition` | ✅ 文档 | throw/catch，含 boundary |
| `signalEventDefinition` | ✅ 文档 | throw/catch，含 boundary |
| `errorEventDefinition` | ✅ 文档 | 仅 boundary catch（+ BpmnError 抛出） |
| `conditionalEventDefinition` | ✅ 文档 | execute 时求值，显式 `.signal()` 时重算 |
| boundary events（interrupting/non-interrupting） | ✅ 实测(interrupting) | `cancelActivity` 两种都支持；实测中断式定时器把 userTask 打断并走边界流 |
| `multiInstanceLoopCharacteristics`（并/串行） | ⚠️ 实测(并行) | 并行/串行都支持；**并行若没 `loopCardinality` 也没 collection → fatal**「cardinality or collection is required in parallel loops」（实测）；collection 写法建议走 `zeebe:loopCharacteristics`（`@0dep`） |
| `sequenceFlow.conditionExpression` | ✅ 实测 | 三种：`language="javascript"`（node:vm）、无 language 的 `${...}` 路径表达式、`${environment.services.fn}`（服务函数条件） |
| **回退边 / 成环** | ✅ 实测 | exclusiveGateway 的默认流回指上游 serviceTask，重新执行并再次进入 userTask，循环计数正确；`SequenceFlow.discard` 里有 loop 检测（`flows/SequenceFlow.js:85-95`） |

Conformance 明确「out of scope」：**消息关联键**（只按 messageRef 匹配，无 correlationKey）、ItemDefinition 强类型、Complex Gateway、Choreography、GlobalTask、participantMultiplicity。
另有两个**未修**的并行汇聚 issue：**#204（2026-11-05 开）「并行 join 在另一分支有成环时提前通过」**、#200（XOR join 变体，2026-05-29 开，据 #204 描述在 26.0.5 已修）。#204 正是「回退边 + 并行汇聚」组合，属设计红线。

## 3. 执行模型

**结论：纯进程内解释器（无独立引擎进程/服务），三层 API = `Engine`（加载与生命周期）→ `Definition`（一份 BPMN）→ `Execution`（一次运行）；挂起/恢复原生支持（`getState()`/`recover()`/`resume()`），我已在**独立进程**里跑通「等人工 → 落盘 → 重启 → resume → 继续」。

最小骨架（实测可跑，节选）：

```js
import { Engine } from 'bpmn-engine';
const engine = new Engine({
  source,                                   // BPMN XML；或 sourceContext 复用序列化结果
  variables: { score: 0.9 },
  settings: { assignOutput: 'id' },         // 把活动输出写进 environment.output
  extensions: { agent(activity) {           // 注册自定义 serviceTask handler
    if (activity.type !== 'bpmn:ServiceTask') return;
    activity.behaviour.Service = AgentService; return {};
  } },
});
const listener = new EventEmitter();        // 关键：活动事件来自 listener，不是 engine.on
listener.on('activity.wait', async (api) => {
  await fs.writeFile('state.json', JSON.stringify(await engine.getState()));
  engine.execution.signal({ id: api.content.id, executionId: api.content.executionId, approved: true });
});
engine.execute({ listener });
// 重启后：new Engine({...同 options}).recover(JSON.parse(state)).resume({ listener })
```

要点与坑（均有实测/源码依据）：
- `engine.on('activity.*')` **收不到**活动事件；`Engine` 只 `emit` `end/stop/error`（`bpmn-engine/src/index.js:600+` 的 `_complete`），活动事件必须通过 `options.listener` / `execute({listener})`（API.md「Execution listener」）。我第一次用 `engine.on('activity.wait')` 完全静默。
- 三个层次：`Engine`（1 个可装多 source/definition）→ `Definition`（含 processes、`shake()` 静态走图）→ `Execution`（`state`/`getPostponed()`/`signal()`/`getState()`）。
- `engine.getState()` 序列化整棵执行树（含 broker/queue 内部态）；`recover` 必须给**非运行中**的 engine（`index.js:157` 抛 `cannot recover a running engine`），所以重启路径=新 Engine + recover + resume。
- 变量在 **definition 的 environment 克隆**里，`engine.environment.variables` 读不到运行期写入（实测 attempts 在引擎环境里恒为 0，process 环境里才变）——查询变量要经 `execution`/activity api，别读 engine.environment。

## 4. 人任务与等待

**结论：`userTask` 就是「永远 wait 的 signal task」，推进必须外部调 API（`execution.signal(...)` 或对 `getPostponed()` 里那个 api 调 `.signal()`），没有内置任务表/认领/超时；关联键靠我们自己的 `correlationId` 自定义属性 + activityId + 实例 id。**

实测（t2b/t10 输出）：
```
[ev] wait humanTask | execId humanTask_e32dc289eb | accepts ["signal","error"]
[query] postponed = humanTask@humanTask_e32dc289eb
[api] signal {id, executionId, score:0.95} → [ev] end humanTask | output {"score":0.95}
```
- 查询「谁在等人」：`execution.getPostponed()` → 每个 api 有 `id`、`type`、`content.executionId`、`content.accepts`；并行任务全部列出（实测两个 userTask 同时在列表里）。
- 完成载荷即活动 output（`environment.output[id]`，需 `settings.assignOutput:'id'`）。
- 关联键方案（推荐）：自定义 moddle 属性 `dsh:correlationId`（实测能进 `activity.behaviour.correlationId`）+ 实例级 `executionId`（可由 `process.init('run-42')` 钉死，实测 process executionId 变成 `run-42`；但 **activity executionId 仍是自动生成的 `humanTask_xxxx`**）。所以业务侧主键 = 我方 runId（钉在 process 上）+ activityId + 我自己的 correlationId，别指望 activity executionId 稳定。
- 无「整流程进入等待」事件（issue #195），要自己在 `activity.wait` 计数 + 去抖后再快照。

## 5. 变量与表达式

**结论：默认表达式是自定义的 `${path.to.var}` 路径解析器（无 eval、无运算符）；要算数/比较只能走 `node:vm` 的 JS 条件（安全边界弱）或 `@0dep` 的 FEEL；**Camunda 8 风格 `= a > 1` 在不装扩展时会「恒真」——这是最危险的坑**。**

实测（`tests/t6.mjs`、`t6b.mjs`，同一流程图 `gw` 上 `amount=0` 应走默认流 `no`）：
```
A javascript lang    => taken: s->gw->no     # 正常
B no lang, operators => taken: s->gw->no     # ${a > 1} 被当路径解析 → undefined
C camunda7 EL ${}    => taken: s->gw->no     # 同上，静默走默认流
D camunda8 feel "= " => taken: s->gw->yes    # ❌ amount=0 仍然走 yes
FEEL no language, amount=0 => s->gw->yes     # ❌ 同上
JS vm escape probe   => s->gw->yes           # ❌ 能拿到 process
```
- 表达式实现：`bpmn-elements/src/Expressions.js`（`/^\${(.+?)}$/` → `getPropertyValue`，只解析属性路径/可调用函数，**不做运算**）。
- JS 条件：`bpmn-engine/src/JavaScripts.js:55` `script.runInNewContext({...scope, ...timers, next})`；实测可 `this.constructor.constructor('return process')()` 逃逸 → **node:vm 不是安全边界**，只能跑我们发布的流程。
- FEEL 正确姿势：`@0dep/bpmn-extensions` 的 `FeelExpressions()`（feelin 8）。实测装上后 `= result.score > 0.8` 正确求值，且 `services.xxx()` 可在 FEEL 里调用。
- 变量作用域：环境级（engine→definition 克隆，subProcess 有局部 scope）；**`camunda:inputOutput` 完全不支持**（`grep -rn "inputOutput|inputParameter" bpmn-elements/src bpmn-engine/src` = 0 命中）；IO mapping 走 `zeebe:ioMapping`（`@0dep`），实测 `input={"prompt":{"topic":...}}`、`output={"result":{"score":0.95}}` 双向映射正常。
- 建议：BDD 里禁止裸 `language="feel"`，加载期做「表达式语言白名单 + 编译失败即拒绝发布」，别让非法条件变成恒真。

## 6. 扩展点

**结论：自定义元素/属性一条龙可用，但入口名是 `moddleOptions`（不是老的 `moddleExtensions`），属性会被序列化进 `behaviour`（前缀被剥掉），`extensionElements` 以 `values[]` 原样可读。**

实测（`tests/t7.mjs`/`t7b.mjs`，自定义 `dsh:` 命名空间 + `dsh:correlationId` 属性 + `dsh:agentConfig` 子元素）：
```
behaviour keys = ['$type','id','correlationId','extensionElements','eventDefinitions']
behaviour JSON = {"$type":"bpmn:ServiceTask","id":"agent","correlationId":"run-42", ...}
ext value $type = dsh:AgentConfig | props = {nodeType,provider,adapter,skills,hooks,prompt} 全部就位
```
- 注册：`new Engine({ moddleOptions: { dsh: dshModleJson } })`（`bpmn-engine/src/index.js:331` `new BpmnModdle(this.options.moddleOptions)`）；旧的 `moddleExtensions` 名字在 26.x 已不生效。
- 三处可挂：① moddle 类型定义（`xml.tagAlias:'lowerCase'`）；② `extendFn(behaviour)`（`index.js:326`，把 extensionElements 里的数据「提升」到 behaviour，`@0dep` 就是这么做的）；③ 运行期 extension 函数 `(activity, context) => { ... }`，返回 `{activate,deactivate}` 参与生命周期。
- 我们的字段（节点类型/provider/适配器/hook/skills/角色提示词）适合做成 `dsh:` 属性或 `dsh:agentConfig` 子元素；`zeebe:taskDefinition / assignmentDefinition / formDefinition / ioMapping / executionListeners / loopCharacteristics / calledElement / subscription(correlationKey)` 已经由 `@0dep/bpmn-extensions` 提供（但该包 1.0.2、周下载 **72**、要求 Node>=22）。

## 7. 性能与并发

**结论：单实例 3.4–4.4ms 启动、约 **450KB/实例** 常驻、快照 7–18KB；1000 常驻 ≈ 435MB 堆，单线程事件循环——只能靠「活跃实例子集 + 懒加载」撑规模。**

实测（`node --expose-gc tests/t11.mjs`，复用序列化 `sourceContext`，都停在 userTask 等人工）：
```
N=200  waiting: start 797ms  (3986µs/inst) | heap +88MB  | 452KB/inst
N=1000 waiting: start 3436ms (3436µs/inst) | heap +435MB | 446KB/inst
complete all (N=1000) 2407ms
heap after dropping refs: +2.8MB            # 完成后无滞留 → 不是内存泄漏
getState() size avg = 7.0KB/instance（简单流程）；两并行人工任务 11KB；带 service+扩展 17.7KB
```
- 每实例重新解析 XML 代价翻倍：`new Engine({source})` 7.8ms/实例 → 共享 `sourceContext` 后 3.4ms/实例（差 2.3 倍）。生产必须缓存 sourceContext。
- 单线程：1000 实例启动是同步 CPU 峰值（3.4s 阻塞）；scale 要 worker_threads 或按活跃度分批。
- 已知问题：#204（并行 join 早触发，open）、#200（同类，26.0.5 修）；#137（getState 20KB 且**不可裁剪**，裁剪后 recover 会坏）、#109（2020 年「30MB/实例」，已关，说明历史上有内存争议）。无已知 leak issue（`search issues "leak"` = 0 命中，只有 #109）。

## 8. 替代品对比（一句话各）

- **`bpmn-engine` + `@0dep/bpmn-extensions`**：唯一「JS 进程内直接跑 BPMN」的成熟选择；缺人任务 UI/关联键，FEEL 靠新包补 —— 对我们是最短路径。
- **Camunda 8 self-managed**：Zeebe 引擎 + FEEL + Tasklist/表单/Operate 全都有，但 JVM + 多服务、重运维，且 Operate/Tasklist/Identity/Optimize 为**专有许可、Free Edition 只许非生产**（[licenses.md](https://github.com/camunda/camunda-docs/blob/5e623feb30690554f0dbe40baafacfe1d7b7bdab/docs/self-managed/components/orchestration-cluster/core-settings/configuration/licensing.md)）。
- **Temporal**：耐久执行最强（MIT，`@temporalio/worker` 周下载 5.86M），但**没有 BPMN/bpmn.io 模型**，等于放弃「画 BPMN」这个产品前提。
- **`bpmn-moddle` + 自写解释器**：解析免费，网关/汇聚/补偿/定时器全要自己实现（`bpmn-elements` 已把这些做成 3000+ 行）——不建议。
- **`bpmn-elements` 直接用（跳过 engine 壳）**：省一层，但 state/事件桥接要自己写；只有在我们决定 fork 时才有意义。

## 9. 落地风险清单

**阻断**
1. **FEEL 条件静默恒真** —— `language="feel"`/`= x` 不装扩展时被当字符串 → 所有条件为真，流程走错还无报错（实测 amount=0 仍走 yes）。缓解：加载期白名单 + 必须 `FeelExpressions()` + 反例单测（` = false` 必须走默认流）。
2. **回退边 + 并行汇聚 join 提前通过**（#204，2026-11-05 仍 open）—— 我们的核心模型就是「打回重跑」，一旦上层有 parallel join 就会多跑/错跑。缓解：设计约束「回退边只汇入 exclusive merge，不与 parallel join 同层」；或 fork `ParallelGateway` 用 token 计数重写；MVP 期禁并行。

**高**
3. **单实例 450KB、1000 常驻 435MB** —— 与 dsh 插件同进程会拖垮桌面端。缓解：活跃实例 LRU（上限 100–200）+ 其余只留 state JSON 懒恢复；state 落 `runs/<id>/state.json` 复用现有原子写。
4. **快照 7–18KB 且不可裁剪**（#137：裁掉 broker/queue 就 recover 不了）—— 每次 wait/end 都写会放大 IO。缓解：只在 `activity.wait`/`activity.end` 快照 + 去抖；别手改 state。
5. **单人维护 + 5 个 peer 全在同作者生态**（bpmn-elements/smqp/moddle-context-serializer，FEEL 包周下载 72）—— 供应链与长期维护风险。缓解：锁版本 + 私有 mirror + 关键补丁 fork 自持。
6. **`node:vm` 不是安全沙箱**（实测逃逸到 `process`）—— 用户/第三方 BPMN 里的 JS 条件等于任意代码执行。缓解：只跑我们发布的流程模板；用户流程禁用 `language="javascript"`。
7. **人任务能力=0**（无 assignee/认领/表单/超时，Conformance 明说 forms 是 host concern）—— 缓解：任务表用 DSH 现有会话/存储实现，字段借 `zeebe:assignmentDefinition/formDefinition`。

**中**
8. 活动事件不在 `engine.on` 上（必须 listener）——适配层统一封装，否则「等不到事件」类 bug 频发。
9. 无 `process.wait` 聚合事件（#195）——自己做「全部活动进入 wait」的判定再落盘。
10. 并行多实例缺 `loopCardinality`/collection 直接 fatal——发布前做模型校验（bpmn-moddle 遍历 + 报错）。
11. `camunda:inputOutput` 零支持——统一用 `zeebe:ioMapping`，别让作者混用两套命名空间。
12. 升级会破坏 state（stateVersion=18、engineVersion 入档；v25→v26 有迁移，跨大版本需手工迁移）——发布前跑迁移 + 拒绝 resume 版本不符的快照。
13. 单线程 CPU 峰值（1000 实例启动 3.4s 同步阻塞）——插件内分片/worker，别在主线程一次拉起。

## 2 周内跑通「最小闭环」的最小可行范围

**做（且只做）这一条竖切**：`startEvent → agentTask(serviceTask) → userTask → exclusiveGateway → 回退边(默认流回 agentTask) → endEvent`。

- **节点**：只两种——`serviceTask`（=agent，注册自定义 `Service`，`zeebe:taskDefinition type` 派发到 provider/adapter，`ioMapping` 做输入输出）+ `userTask`（=人工，`zeebe:assignmentDefinition` 带 assignee/candidates）。其余 BPMN 元素一律不支持（加载期校验拒绝），避免误用。
- **网关与回退**：只允许 `exclusiveGateway` + `${...}`/FEEL 条件 + 默认流成环；**禁用 parallel/inclusive join**（避开 #204）。
- **表达式**：只用 `FeelExpressions()`（`@0dep/bpmn-extensions`），条件写成 `= ...`；加载期把「无 language 的裸表达式」判为错误。
- **等待与关联**：`activity.wait` → 写任务表（键 = runId + activityId + 自定义 `dsh:correlationId`）；完成时 `execution.signal({id, executionId, payload})`。
- **恢复**：只在 `activity.wait` 与 `activity.end` 两个事件快照 `engine.getState()` → `runs/<runId>/state.json`（原子写，复用现有 `run.json` 机制）；重启时新建 Engine + `recover(state)` + `resume({listener})`；不追求「运行中热挂起」。
- **验收**：① 两进程脚本跑通「等人工→杀进程→重启→接着跑」；② 打回一次后重跑并二次等待，计数正确；③ FEEL `= false` 必走默认流（防恒真）；④ 100 实例常驻 < 60MB、启动 < 500ms。
- **明确不做**：timer/boundary、callActivity/subProcess、多实例、消息/信号事件、Camunda 7 兼容、表单引擎、BPMN 全量校验。2 周内这些都会把范围撑破。
