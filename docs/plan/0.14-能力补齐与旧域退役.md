## 二、跨阶段固定契约

### 1. 实例状态与完成条件

- 实例状态继续只有 `ACTIVE / COMPLETED / SUSPENDED / CANCELED`。
- 技术错误写 `lastError` 和 `error` 事件；不得产生实例 `FAILED`、`BLOCKED`、`STALLED`。
- `activity/end` 表示一次活动执行完成；`process/end` 表示 BPMN 正常结束，均不代表业务质量通过。
- agent 的成功完成必须来自 `flow_finish_node`；HTTP connector 根据自己的执行结果完成，不调用该工具。
- 人工任务收到消息不会完成，完成仍走已有人工任务完成接口。
- 保留 `finish_reminder` 默认 `maxFires:3`；提醒不是监督轮询，也不是一次新的 BPMN 活动执行。

### 2. 标识与事件

新能力统一用以下身份，避免循环重入、重试和恢复互相混淆：

```json
{
  "instanceId": "i-demo",
  "elementId": "review",
  "executionId": "review_execution_42",
  "attempt": 2,
  "invocationId": "invoke-7"
}
```

- `elementId`：BPMN 元素 ID。
- `executionId`：该元素本次激活的执行 ID，是消息投递、计时、幂等的主要定位键。
- `attempt`：该元素在实例中第几次激活；HTTP 重试、agent 提醒不增加它。
- `invocationId`：实际调用 adapter/外部服务的记录 ID。
- 当前事件中的 `activityId` 有承载执行 ID 的用法；新增聚合层必须显式归一化，不能凭字段名与路由参数直接关联。

执行事件继续由宿主分配全局 `seq`，单条不超过现有 8 KiB。新增遥测必须保留必要计数和定位字段，不能经过裁剪后默默少计。

### 3. 终态资源操作

当前 [instance-store.js](/home/feiyueve/文档/dsh/dsh-flow-studio/src/instance-store.js:808) 禁止终态后修改实例及追加执行事件。保留此保护。

C 引入独立资源记录：

- 执行事件：现有 `events/`、`seq`，终态封口。
- 资源事件：`resources/events.jsonl`、独立 `resourceSeq`，用于 worktree 清理、已受理回复的投递结果等。
- 新增 `GET /instances/<id>/resource-events?since=`。
- GUI 可以合并展示两种来源，但不伪造统一序号，不向终态实例补 `activity/end` 或 `process/end`。

新增 metrics、worktree、inbox 查询接口均为纯读取，**不调用 `_ensureRunner()`，不因查看页面而派发工作**。

### 配置与接口契约

保留 `fs:node nodeType="http"`。下例为解析后的结构：

```json
{
  "kind": "http",
  "http": {
    "method": "POST",
    "url": "https://api.example.com/orders",
    "headers": {
      "Content-Type": "application/json"
    },
    "authRef": "orders-api",
    "networkPolicyId": "orders-api",
    "timeoutMs": 10000,
    "retries": 2,
    "maxResponseBytes": 1048576,
    "idempotency": {
      "mode": "remote-key",
      "header": "Idempotency-Key"
    }
  },
  "ioMapping": {
    "input": [
      {
        "source": "= { orderId: order_id }",
        "target": "body"
      }
    ],
    "output": [
      {
        "source": "= response.status",
        "target": "http_status"
      },
      {
        "source": "= response.body.accepted",
        "target": "accepted"
      }
    ]
  }
}
```

具体约束：

- **映射只用 `zeebe:ioMapping` + 现有 `evaluateFeel()`。** 当前面板预留的 `fs:http.inputMapping/outputMapping` 在本阶段统一替换，不长期维护第二套解释器；遇到混用配置明确拒绝。
- 输入映射只构造本次请求的局部上下文，不修改实例变量。
- 输出只合并显式映射的短标量，采用 finish 变量同等级预算；不把整个响应放进变量或事件。
- URL 的 origin 固定在配置中；变量可进入经编码的路径/查询参数，不能绕过目标策略改变 origin。
- 密钥从宿主 `authRef` 解析，XML、实例变量、事件、错误文本、GUI 均不保存密钥值。
- 函数保持 `executeHttp(element, ctx)`；返回 `{output, status, headers, events}`，其中 headers 只含明确允许的响应头。
- 不新增任意 URL 的“试请求”路由，也不新增 agent HTTP 工具。定义保存、实例启动仍走原接口。

建议首版边界：请求正文上限 256 KiB；响应默认上限 1 MiB、宿主硬上限 5 MiB；默认不重试，显式重试最多 3 次。

### 执行、安全与失败语义

- 默认只允许 HTTPS；测试台内部 HTTP 必须由宿主配置精确放行。
- 禁止 URL userinfo、非 HTTP 协议、任意代理继承。
- 默认阻断 loopback、私网、link-local、metadata 等地址；内网集成必须配置明确的 host/port/CIDR 例外。
- 校验全部 DNS 结果，并让实际连接使用已验证地址，避免“校验一次、连接时重新解析”。
- 首版关闭重定向；后续若开放，每一跳重新校验，跨 origin 不转发认证头。
- 响应流按实际读取字节限制；压缩响应同时控制解压后的体积。超限立即中止。
- 重试只覆盖指定瞬时网络错误、429、502/503/504；退避和 `Retry-After` 受整体 deadline 限制。
- GET/HEAD 可按配置重试；有副作用的方法只有在远端明确支持幂等键时才允许自动重试。
- 同一次 execution 的所有 HTTP 重试共享幂等键；BPMN 循环再次激活则生成新键。

调用记录：

```json
{
  "v": 1,
  "instanceId": "i-demo",
  "elementId": "submit",
  "executionId": "submit_execution_1",
  "requestHash": "sha256...",
  "idempotencyKey": "fs-...",
  "state": "started",
  "attempts": 1,
  "result": null
}
```

发送前落盘，成功结果在回调引擎前落盘。恢复时：

- 已持久化成功结果：复用结果，不再请求远端。
- 已发送但结果不明：不因 GET/重启自动重发，记录 `HTTP_OUTCOME_UNKNOWN`。
- 重试耗尽：`ACTIVE + lastError + error`，不产生正常 `activity/end`，不走出向连线。
- 默认非 2xx 为 connector 错误；业务若要按 409 等响应分支，必须显式配置可接受状态并映射状态码，再交给 FEEL 决策。

这是本地 serviceTask 的执行策略，不冒充 Zeebe job/incident 实现。Camunda 的 job worker 同样要求处理重复投递，并将重试耗尽交给 incident 处理；本项目按既定契约表达为 `ACTIVE + lastError`。[Camunda job workers](https://docs.camunda.io/docs/components/concepts/job-workers/)

### 验收与完成判据

单测必须能抓住：

- 502→200 只完成一次活动；两个请求使用同一幂等键。
- 无幂等保障的 POST 超时不会自动重发。
- 重启落在“远端已处理、本地未记结果”窗口时不重复副作用。
- DNS 重绑定、IPv6 私网、重定向、userinfo、伪造 Content-Length、压缩超限被阻断。
- 鉴权头及其值不出现在 events、state、错误响应和日志。
- FEEL 映射错误、超限输出不污染实例变量。
- cancel/suspend 后的迟到响应不推动流程。

容器中启动受控 HTTP fixture，执行：

`start → HTTP → exclusiveGateway → human → end`

分别注入正常、重试、超时、超限、错误映射和崩溃窗口；对账 fixture 请求次数、幂等键、实例变量和事件。

**风险与非目标：**不承诺远端 exactly-once；不做 OAuth 刷新框架、通用脚本 connector、流式下载、自动故障修复或新的 BPMN 网关类型。

### 启动与资源契约

扩展已有实例创建/启动工具的执行选项：

```json
{
  "definitionId": "review-flow",
  "variables": {},
  "workspace": {
    "path": "/allowed/project",
    "worktree": {
      "mode": "auto",
      "baseRef": "HEAD",
      "cleanup": "retain"
    }
  }
}
```

- `mode:"auto|on|off"`；默认 `auto`，非 Git 工作区可退回原目录；`on` 必须成功建立 worktree。
- `cleanup:"retain|on-terminal-clean"`；默认保留。
- 启动时冻结 `baseCommit`，不在后续节点重新读取移动的 HEAD。
- 路径为 `<worktreeRoot>/<workspaceId>/<instanceId>`，分支为 `flow-instance/<instanceId>[-N]`。
- `workspaceId` 基于主仓库身份，从 linked worktree 发起也保持一致。
- 工作区解析、worktree 创建完成后才启动第一个 agent。

宿主所有权记录独立保存在 `worktree-registry/<workspaceId>/<instanceId>.json`，不放在 agent 可改写的工作树中：

```json
{
  "v": 1,
  "instanceId": "i-demo",
  "workspaceId": "ws-a",
  "repositoryRoot": "/allowed/project",
  "effectiveRoot": "/managed/worktrees/ws-a/i-demo",
  "branch": "flow-instance/i-demo",
  "baseCommit": "commit-sha",
  "cleanupPolicy": "retain",
  "resourceState": "ready",
  "createdAt": "..."
}
```

`resourceState` 是资源记录状态，不是实例状态。

**cwd 规则：**

- adapter cwd、finish gate 的文档根、消息文件根必须来自同一份已解析工作区记录。
- worktree 模式下，节点 cwd 只允许该树内的相对子目录；绝对路径和 realpath 越界拒绝。
- 不从主工作区复制未跟踪文件、`.env` 或认证资料。
- 恢复时使用已冻结记录；缺失时报告 `WORKSPACE_UNAVAILABLE`，不静默换回宿主目录。

### 路由与工具

前缀仍为 `/api/flow-studio`：

| 接口 | 契约 |
|---|---|
| `GET /instances/<id>/worktree` | 检查路径、Git 登记、branch、dirty、可清理性 |
| `DELETE /instances/<id>/worktree` | `{force:false, removeBranch:false, expectedHead?}` |
| `DELETE /instances/<id>/worktree/branch` | 仅清理记录确属本实例的分支 |
| `GET /instance-worktrees?workspaceId=` | 实例资源列表，不扫描旧 runs |
| `POST /instance-worktrees/prune` | 默认 `{dryRun:true}`；执行须带预览得到的 `planHash` |

新工具：

```text
flow_instance_worktrees({
  action: "inspect" | "remove" | "branch" | "list" | "prune",
  instanceId?,
  workspaceId?,
  force?,
  removeBranch?,
  dryRun?,
  planHash?
})
```

创建由实例启动选项触发，内部调用 `createInstanceWorktree()`；不允许实例运行中任意切换工作树。

### 清理与产物保存

- `ACTIVE`、`SUSPENDED` 一律不能清理；`force` 不能越过此限制。
- `COMPLETED/CANCELED` 默认保留；`on-terminal-clean` 仅在 agent 进程释放、工作树干净、产物已保存后执行。
- 脏树、未合并分支分别呈现风险，分支删除独立返回结果，不以“目录删了”冒充全部成功。
- 孤儿判断依据完整持久化实例集合和宿主所有权记录，不能依据内存 LRU。
- 实例目录读失败、损坏或列表不完整时停止 prune。
- 无所有权证据的目录只报告，不自动删；分支前缀本身不足以证明所有权。

为避免删除工作树后 artifact 引用失效：登记文档时利用现有安全读取过程，保存按 hash 寻址的受控副本；仍保持 `path + sha256 + bytes` 对外契约，正文不进入变量/事件。artifact 增加 `executionId/workspaceId/contentRef` 来源信息，不能继续只按 `path + sha256` 丢失不同执行的来源关系。

并发保护按**实际 agent 执行**占槽；人工等待和挂起不长期占槽。保留全局/工作区上限、队列超时和取消退队，不搬旧 run 租约语义。

### 验收与完成判据

- 两个实例从同一仓库启动，写同名文件互不影响；主工作区不变。
- 同一实例跨节点、循环、重启使用相同树和冻结 commit。
- 非 Git、Git 缺失、空仓库、linked worktree、分支冲突分别有确定结果。
- 越界路径、symlink、其他仓库目录、用户分支不能被清理。
- ACTIVE/SUSPENDED 清理返回 409；终态清理幂等。
- prune 预览后状态变化，旧 `planHash` 不能执行过期删除。
- 清理后 artifact 仍可按原 hash 读取；清理失败不改变实例状态。
- 排队取消不泄漏槽位；满载下并发数不超过配置。

容器测试台创建临时 Git 仓库，同时运行两个实例；写文件、挂起/恢复、取消/完成，再从 GUI 预览和执行清理；最后制造孤儿与损坏实例目录验证 prune 的保守行为。

**风险与非目标：**worktree 提供 Git 工作目录隔离，不替代进程沙箱；不自动 commit、merge、push，不替业务决定产物保留期限。

**目标：**外部消息能可靠到达指定 agent 执行或人工任务，并能通过受控回复目标回应。

### 文件与函数范围

- `src/instance-inbox.js`：
  `acceptInstanceMessage()`、`bindNextExecution()`、`deliverInstanceMessage()`、
  `enqueueReply()`、`dispatchReply()`。

### 消息与工具契约

```json
{
  "messageId": "external-event-42",
  "target": {
    "activityId": "review",
    "executionId": "review_execution_7"
  },
  "text": "请补充兼容性说明。",
  "replyTargetId": "operator-session"
}
```

支持两种互斥目标：

- 精确目标：`activityId + executionId`。
- 尚未激活节点：`{activityId:"review", delivery:"nextActivation"}`，只绑定后续第一次激活，不广播到所有循环。

规则：

- 同一 instance 下 `messageId` 相同、内容相同：返回原结果；内容不同：409。
- 已结束 execution：`MESSAGE_TARGET_EXPIRED`，不投递到同名节点的下一轮。
- SUSPENDED 可以受理并排队，但不唤起 agent。
- COMPLETED/CANCELED 拒绝新入站消息。
- 人工任务消息只是讨论/附件，不写完成变量，不调用 `signalTask()`。

路由：

```text
GET  /instances/<id>/messages?cursor=&limit=
POST /instances/<id>/messages
GET  /instances/<id>/messages/<messageId>/body
POST /instances/<id>/messages/<messageId>/replies
```

工具采用明确的新名字，避免与仍存在的旧工具重名：

```text
flow_instance_send_message({instanceId, messageId, target, text, replyTargetId?})
flow_instance_reply({instanceId, messageId, replyId, text?, document?})
```

agent 会话中的工具绑定本实例/执行身份，不能通过改参数跨实例投递。F 删除旧 `flow_send_message`、`flow_reply` 的 run 语义实现，不保留“最近 run”推断。

### 持久化、体积和回复

- 小消息内联上限建议 4 KiB；总正文上限 1 MiB，按 UTF-8 字节计算。
- 超过内联阈值先完整落盘，再受理；返回 `bodyRef:{path,sha256,bytes}`。
- 事件只记录 ID、目标、状态和短摘要；长正文不进入变量、提示词头部或事件。
- 给 agent 的正文文件在其有效工作区内物化，使用相对路径；人工任务通过鉴权正文接口读取。
- 默认每批注入最多 5 条，**只确认实际注入的 messageId**，剩余继续排队。
- 先 durable inbox，再投递，再持久化确认。适配器无法提供可去重确认时显示 `deliveryUnknown`，不声称 exactly-once。

适配器增加可选消息能力及 `deliverMessage(handle, message)`：

- DSH 使用现有会话投递能力。
- CLI adapter 在安全的轮次边界投递/续跑；不能向不支持的 stdin 硬塞内容。
- 冷恢复必须匹配同一 execution、同一工作区，并重新绑定 finish gate。
- 已错误封口、不可恢复的 execution 不能因收件箱消息自动复活。

回复目标只使用宿主维护的 ID：

```json
{
  "operator-session": {
    "kind": "session",
    "sessionId": "approved-session"
  },
  "ticket-hook": {
    "kind": "http",
    "url": "https://example.com/approved-hook",
    "authRef": "ticket-hook"
  }
}
```

禁止消息或模型临时提供任意 URL/session。回复先写 outbox；重试有稳定 replyId 和幂等策略。COMPLETED 后可以完成此前已受理的回复投递；CANCELED 停止未发送回复。结果写资源事件，不改终态执行流。

### 验收与完成判据

- live agent、冷会话、未来节点、人工任务四种目标均有明确结果。
- 循环重入不会收到上一 execution 的消息。
- 重复入站请求不重复排队；持久化失败不返回成功。
- 6 条消息首批只确认 5 条，第 6 条仍可投递。
- 超阈值正文逐字节一致；超硬上限返回 413 且无半文件。
- 重启后 queued/outbox 恢复；不重复确认已投递消息。
- 任意回复 URL、非白名单 session、跨实例工具调用被拒绝。
- 收到消息、发送回复均不能代替 `flow_finish_node` 或人工完成。

容器中跑“agent→human→agent”，从独立客户端投递短/长消息；重启容器，再完成任务；回复到测试 session 和 HTTP fixture，对账 messageId、replyId、完整正文和投递次数。

**风险与非目标：**这是应用收件箱，不是 BPMN message catch/start event 或完整 correlation 引擎；不恢复 supervision，不保证不支持幂等的外部通道 exactly-once。

### 指标定义

| 指标 | 口径 |
|---|---|
| 实例墙钟耗时 | `createdAt → completedAt/asOf` |

| NODE_FINISH_MISSING | 按错误事实和 execution 去重，不反复扫描 lastError 累加 |
| connector 成功率 | execution 级结果；attempt 级成功率另列 |
| connector 延迟 | 单次请求延迟与含退避的总耗时分别统计 |
| skill 使用 | 声明和实际加载分开；不可观测时为 unknown |

## E4．0.14.3：实例挂起 / 恢复（已交付：路线 1）

**交付结论（0.14.3）：**按**路线 1（quiesce 式软挂起）**落地，不做路线 2 的硬挂起：

- `POST /instances/<id>/suspend` / `POST /instances/<id>/resume`，`reason` ≤200 字符并写进事件；
- 只在实例 `ACTIVE` 且没有在飞活动（`_executionBusy()`、在飞 agent、connector 记录 `started` / `sent` / `unknown`）时允许挂起；否则 409 `INSTANCE_SUSPEND_BUSY` 并返回 `activities[]`；
- 挂起 / 恢复的状态与 `instance/suspended` / `instance/resumed` 事件在**同一次 `instance.json` 写入**里提交；挂起不杀 runner、不推进、不派发，`_ensureRunner()` 对 `SUSPENDED` 直接跳过（`GET` 不恢复），`complete` 409 `INSTANCE_SUSPENDED`，入站消息排队；`stop` 在 `SUSPENDED` 上仍可用；恢复不主动跑，之后沿用懒恢复；
- 模型工具 `flow_instance_suspend` / `flow_instance_resume` 走同一份路由，工具总数 13；
- 覆盖：两条路由、SUSPENDED 状态与事件的写入 / 幂等 / 终态拒绝、在飞 409、重启不自动恢复、恢复后完成、stop 不可逆、指标挂起区间、工具注册与错误 hint（`test/bpmn-runtime.test.mjs` / `test/instance-tools.test.mjs` / `test/host-auth.test.mjs`）；
- 路由与语义的唯一参考页：[实例域接口 · 挂起 / 恢复](../reference/instance-api.md#挂起与恢复)。

**为什么当初延后：**挂起不是旧运行域的能力（旧 `flow_*` 里没有 suspend / resume），不构成 F 的退役阻塞；而要做对，需要引擎级 quiesce 设计，不只是加一对路由。

**当时的事实：**`bpmn-engine@26` 没有 pause / resume 原语，只有 `stop()` 与按 `state` 恢复；实例状态枚举里已有 `SUSPENDED`，指标（E1）与收件箱（D）也都按 `instance/suspended|resumed` 事件准备了语义，但没有写路径能产生这两个事件。

**两条候选路线（选一条落地，不允许「只改状态不改执行」）：**

1. **quiesce 式软挂起**：只在没有在飞活动（无在跑的 agent、无在飞的 connector、无未结算 handler）时允许挂起——置 `SUSPENDED` + 写事件，不推进派发，`complete_task` / 入站消息按挂起语义拒绝或排队；恢复时置 `ACTIVE` + 写事件，下次推进沿用既有懒恢复。有在飞活动时返回明确 409（例如 `INSTANCE_SUSPEND_BUSY`）并说明原因。
2. **快照式硬挂起**：先持久化 `state`，再 `stop()` 引擎并置 `SUSPENDED`；恢复时按 `state` 懒恢复。代价是**在飞活动会被中止**（agent 中途被杀、connector 结果变 unknown），必须在响应与事件里如实标注。

**完成判据：**两条路线都要证明「挂起期间不会自己往前跑」；恢复后不重放已完成节点；`cancel` 在 `SUSPENDED` 上仍可用；终态不可挂起；指标里挂起区间与 `asOf` 对得上（E1 已支持该事件）；文档补 `instance-api.md` 路由与语义。
