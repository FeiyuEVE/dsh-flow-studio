# 2026-11-07：一条 XState 断言把 dsh-web 打成 22 GB OOM

> 事故记录。事实与数字来自当天的 systemd / 内核 OOM 记录与仓库内的测试注释（`test/flowmachine.test.mjs` 顶部「安全事故备忘」）；推断处已标注。

## 摘要

0.9.0 发布前，一条「对 XState 内部对象做 `assert.equal`」的测试在断言失败时触发了 Node 的深度 inspect + Myers diff，内存无界增长到 **22 GB**，打爆宿主 `dsh-web` 的 24 GB cgroup，systemd 在 10:17 把服务 OOM 重启。测试本身没有「跑很久」——从写入到 OOM 不到 1 分钟。

## 影响面

- 宿主 `dsh-web` 被 OOM kill 并重启一次（10:17:12 与 10:17:44 两轮 kill，10:17:51 Restart）。
- 同一进程里正在跑的会话被打断；Web UI 短时不可用。
- 没有数据损坏：run 日志是 append-only，进程重启后由 `repairRunCounters` 修计数。

## 现象

- 10:17，systemd 报 `dsh-web` 因 OOM 重启。
- 进程 RSS 从 51 MB 起步；**单次断言失败实测分配约 4 GB**（51 MB → 4126 MB），随后 45 秒内涨到 22 GB。
- 期间 CPU 并不高，内存持续上涨，属于「分配后不释放」的形态，不是死循环空转。

## 时间线

| 时间 | 事件 |
|---|---|
| 10:16:32 | 写入测试：`assert.equal(machine.states.running.initial, 'a')`（本意是断言初始子状态是 `a`） |
| 10:17:12 | 内核 OOM kill `4023991` |
| 10:17:44 | 内核 OOM kill `4026225`，同轮打死主进程 |
| 10:17:51 | systemd `Restart`，`dsh-web` 恢复 |

从写入到第一次 OOM 只有 40 秒；两次 kill 相隔 32 秒，对应「重启后测试/进程再次被拉起又撞上同一断言」的窗口（推断：同一测试仍在重跑）。

## 根因链

1. **断言对象选错**：`machine.states.running.initial` 在 XState v5 里**不是字符串**，而是 `TransitionDefinition`。期望值 `'a'` 与它永远不相等。
2. **失败路径进入 Node assert diff**：`assert.equal` 失败时，Node 用 `inspect(depth=1000, getters=true)` 展开 actual / expected。
3. **inspect 顺着引用图遍历整台状态机**：`TransitionDefinition` 带 `source` / `target`，target 又指回 `StateNode`，整张机器的状态、转移、上下文被展开。实测 inspect 文本 **27.7 M 字符**。
4. **再跑 Myers diff**：Node 对两个巨大的 inspect 文本做 Myers diff，差异矩阵分配的是**外部内存**（V8 堆外），没有上限。
5. **22 GB**：从一次约 4 GB 的失败开始，进程在 45 秒内涨到 22 GB。

## 为什么限额没拦住

- **heap cap 管不住外部内存**：进程即使带了 `--max-old-space-size`，Myers diff / 大字符串的外部内存也不在 V8 old space 的配额里，堆上限不会先触发。
- **cgroup 直到 24 GB 才动手**：`dsh-web` 的 cgroup 内存上限是 24 GB，内核 OOM killer 只在这个水位才介入——此时进程已经吃掉整机可观的可用内存，重启是唯一出路。
- **没有时间上限**：测试是直接 `node test/xxx.test.mjs` 跑的，没有 `timeout` 兜底；内存涨得比人反应快。

## 修复

1. **只对纯数据断言**：改成读 `machine.config.initial`（普通配置对象），不再碰 `StateNode` / `TransitionDefinition` / snapshot 本体。需要看结构时先降维：`Object.keys(machine.states)`、`transition.target.map(n => n.id)`、`JSON.parse(JSON.stringify(snapshot))`。
2. **加护栏 `guardUnsafeAssert`**（`test/flowmachine.test.mjs`）：断言前只读原型与少量自有属性识别 `StateNode` / `StateMachine` / `TransitionDefinition`，命中就**在进入 Node diff 之前**抛清晰错误，而不是让 Node 去遍历。`A.equal` / `A.deepEqual` 都走这道闸；`targetIds` / `actionTypes` 这类降维辅助函数保留。
3. **给测试加纪律**（写进 [CONTRIBUTING](../../CONTRIBUTING.md#测试纪律)）：
   - 一律带时间与内存上限：`timeout 300 node --max-old-space-size=2048 test/xxx.test.mjs`；
   - 需要更硬的兜底时加 `ulimit -v`；
   - 永远不要把 `StateNode` / actor 本体交给断言库。

## 遗留

- **宿主侧加固待定**：给 `dsh-web` 设 `OOMScoreAdjust`（降低被 OOM killer 选中的概率）与 `MemoryHigh`（在 24 GB 硬限之前先节流/回收）仍在讨论，未落地。当前防线是「不再产生这类无界分配 + 测试带时限」，不是「进程打不爆」。
- `guardUnsafeAssert` 只覆盖手写断言；`node:test` / 其它断言库直接调 `assert` 的路径仍可能绕过，review 时按本条检查。

## 防复发检查表

- [ ] 断言对象是字符串 / 数字 / 普通对象，不是库的内部实例。
- [ ] 测试命令带 `timeout`，必要时带 `--max-old-space-size` 与 `ulimit -v`。
- [ ] 新增状态机测试复用 `guardUnsafeAssert`。
- [ ] 看到 `machine.states.*`、`.initial`、`.transition` 出现在断言右侧时，先确认它是配置还是实例。
- [ ] 发布前在容器测试台里跑，不拿宿主 `~/.dsh` 试错。
